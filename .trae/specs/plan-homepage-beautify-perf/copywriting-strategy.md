## 1. 项目定位声明

### 1.1 一句话定位（≤30 字）

> **Factorio 无头服务端的 Web 管理面板，把命令行变成按钮。**

（共 22 字，回答"项目是什么"）

### 1.2 三段式描述

| 维度 | 描述 |
|------|------|
| **为谁服务** | 为自建 Factorio 服务器的腐竹（服主）服务——无论是一个人开私服的玩家，还是运营几十人社区服的站长，亦或在一台机器上托管多个实例的运维者。 |
| **解决什么问题** | 解决 Factorio 无头服务端只能靠 SSH + 命令行管理的痛点：改配置要敲指令、装 Mod 要手动解压、看日志要守着终端、远程管理必须带电脑、社区运营没有现成工具。 |
| **带来什么价值** | 把所有服务器管理动作收进一个浏览器界面——可视化启停、自动备份、批量管理 Mod、实时监控告警、聊天增强与 VIP 商城，5 分钟从零部署，手机也能远程掌控。 |

## 2. 目标用户画像

### 2.1 个人玩家（私服腐竹）

| 维度 | 内容 |
|------|------|
| **典型场景** | 周末约两三个朋友开荒异星工厂，自己租了一台云服务器跑无头服务端。改配置、装 Mod、回档都要自己折腾。 |
| **核心痛点** | ① 不熟悉 Linux 命令行，每次改配置都要查文档；② Mod 依赖冲突报错看不懂；③ 存档不敢删，怕丢进度但没有备份习惯；④ 出门在外服务器崩了没法远程处理。 |
| **本项目的解决方案** | 浏览器打开即用，配置可视化编辑、Mod 依赖自动解析、存档一键备份/回滚、手机浏览器远程管理。5 分钟部署，无需运维经验。 |

### 2.2 社区服运营者

| 维度 | 内容 |
|------|------|
| **典型场景** | 运营一个 30-50 人的公共 Factorio 服务器，需要处理玩家纠纷、发放奖励、维持秩序、覆盖服务器成本。 |
| **核心痛点** | ① 没有现成的 VIP / 商城工具，靠爱发电难以为继；② 玩家加入没有欢迎流程，社区感弱；③ 踢人/封禁靠手动敲命令，不够透明；④ 投票踢人等自治机制缺失。 |
| **本项目的解决方案** | 内置 VIP 等级 + 商城 + CDK 兑换码系统；P1 事件响应自动欢迎礼包；P4 投票踢人社区自治（双冷却期防滥用）；四级角色权限体系管理协作者。 |

### 2.3 多实例托管者

| 维度 | 内容 |
|------|------|
| **典型场景** | 在一台高配机器上同时托管多个 Factorio 实例——主生存服、PVP 服、创意模式服，各服独立配置独立存档。 |
| **核心痛点** | ① 多个实例的端口/存档/Mod/日志互相串味，管理混乱；② 切换实例要切目录切终端；③ 一个实例崩了影响不到判断是哪个；④ 各实例的玩家数据、商店数据需要隔离。 |
| **本项目的解决方案** | 实例中心化架构（v2.0.0+）：每个实例独立作用域（存档/Mod/配置/商店/日志），快速切换互不干扰；每实例独立资源监控与日志流；崩溃自动重启指数退避。 |

## 3. 核心价值主张

### 3.1 一句话回答"为什么选我们而非命令行"

> **命令行把人困在终端前，我们把整个服务端搬进浏览器——所见即所得，手机也能管。**

### 3.2 与命令行管理方式的 3 个本质差异

| # | 本质差异 | 论证逻辑 |
|---|---------|---------|
| 1 | **交互载体根本不同**：命令行依赖指令记忆与 SSH 会话，本项目依赖可视化界面与浏览器。命令行要求操作者记住 `--start-server saves/xxx.zip` 等参数语法，输错一个参数服务器就崩；本项目把每个操作收编为一个按钮/表单，配置可视化编辑（标签式数组编辑器、下拉分类过滤），学习成本从"1-2 周入门"降到"5 分钟上手"。 |
| 2 | **可达性根本不同**：命令行要求操作者有终端环境（带电脑 + SSH 客户端），本项目只要浏览器。命令行无法在手机上操作，半夜服务器崩了必须爬起来开电脑；本项目 PWA 支持手机添加到主屏幕（v2.15.2），任意设备任意浏览器都能远程掌控。 |
| 3 | **能力边界根本不同**：命令行只提供"启动/停止/发指令"的原子操作，社区运营所需的 VIP、商城、投票踢人、聊天增强等都需要额外开发或根本缺失；本项目把这些能力作为内置功能交付（P1-P4 四层聊天增强、VIP 等级与每日限额、CDK 兑换码、商店订单管理），开箱即用无需二次开发。 |

## 4. 差异化卖点矩阵

| 卖点 | 命令行方式 | 本项目方式 | 支撑依据 |
|------|-----------|-----------|---------|
| **多实例中心化管理** | 多实例靠多终端多目录手动切换，端口/存档易串味 | 一台机器运行多个实例，每实例独立作用域（存档/Mod/配置/商店/日志），界面化切换 | 源码 `backend/src/services/instanceManager.ts` + `instanceStateStore.ts`；README「多实例管理」章节；v2.0.0「实例中心化架构」版本记录 |
| **四层聊天增强架构** | 聊天只能进游戏看，无自动响应能力 | P1 事件响应 / P2 主动推送 / P3 被动响应 / P4 社区自治，每实例独立配置 | README「聊天增强系统（v2.4.0+）」章节四层表格；源码 `joinHandler.ts`/`periodicMessageService.ts`/`chatSettings.ts`/`voteService.ts`；版本记录 v2.4.0~v2.8.0 |
| **内置 VIP 商城与 CDK** | 社区运营需自行开发商业化工具，或没有 | VIP 等级对应购物能力、每日限额、CDK 兑换码批量生成与玩家兑换 | README「VIP 购物权限体系」「品质等级映射」章节；源码 `vipService.ts`/`shopService.ts`；版本记录 v2.3.0 / v2.15.0 CDK 系统 |
| **一键热更新与回退** | 更新靠手动 git pull + 重新构建，失败难回退 | GitHub API 版本检查 → 自动下载 → npm install → build → 优雅重启；更新前自动备份数据库与 dist，支持一键回退 | README「热更新系统」章节；源码 `updateService.ts`；版本记录 v2.9.1「一键从零部署脚本」 |
| **多数据库支持** | 命令行管理工具通常绑定单一数据库 | SQLite（默认）/ MySQL / PostgreSQL 三选一，Knex 统一迁移 | README 技术栈「SQLite（默认）/ MySQL / PostgreSQL」；源码 `backend/src/db/config.ts` + `migrations/` 目录 |
| **开源可审计** | 闭源面板无法验证安全性 | 代码全部开源，JWT + bcrypt 认证，无后门风险可审计 | GitHub 仓库 https://github.com/airxw/factorio-server-manager ；源码 `backend/src/middleware/auth.ts` |
| **PWA 移动端支持** | 命令行无法在手机操作 | 支持手机添加到主屏幕，无地址栏全屏体验 | 版本记录 v2.15.2「PWA 支持」、v2.10.0「移动端 UI 全面优化」 |

## 5. 信息架构与叙事逻辑

### 5.1 13 区块递进关系论证

主页采用**"痛点共鸣 → 方案展示 → 信任建立 → 行动转化"**四段式叙事，13 个区块按此主线递进，每个区块承担明确的叙事职能：

| 阶段 | 区块 | 叙事职能 | 为什么在这个位置 |
|------|------|---------|----------------|
| **入场** | Navbar | 导航锚定 | 顶部固定，提供全程跳转入口，用户随时知道自己在哪 |
| **入场** | Hero | 价值主张首屏传达 | 3 秒内回答"这是什么、为谁、能干嘛"，决定用户是否继续往下看 |
| **入场** | LogoCloud | 技术可信度铺垫 | 紧接 Hero 用技术栈背书，缓解"这东西靠谱吗"的疑虑 |
| **① 痛点共鸣** | Stats | 客观实力速览 | 用数字快速建立规模感，为后续痛点做铺垫（"6 大模块/4 层聊天"对应后面展开） |
| **① 痛点共鸣** | PainPoints | 共情与问题定义 | 让用户"对号入座"——你中了几个？激发"我需要解决方案"的动机 |
| **② 方案展示** | FeatureShowcase | 核心能力展开 | 痛点之后立刻给方案，6 大模块逐一回应痛点，tab 切换降低阅读负担 |
| **② 方案展示** | LiveDemo | 所见即所得 | 文字说再多不如看一眼，用仪表盘预览证明"真的可用" |
| **② 方案展示** | ChatJourney | 旗舰能力深挖 | 聊天增强是本项目最具差异化的能力（四层架构），值得独立区块讲透 |
| **② 方案展示** | Comparison | 量化对比 | 用对比表把抽象差异变成具体项，强化"命令行 vs 本项目"的认知 |
| **② 方案展示** | UseCases | 场景对号入座 | 让不同用户找到自己的使用场景，扩大受众覆盖 |
| **③ 信任建立** | TechStack | 技术透明度 | 暴露技术架构证明工程质量，开源可审计降低信任门槛 |
| **③ 信任建立** | VersionTimeline | 持续演进证据 | 用版本历史证明项目活跃、在迭代、不会烂尾 |
| **④ 行动转化** | DeployCTA | 临门一脚 | 信任建立后给出明确行动指令——一条命令部署 |
| **④ 行动转化** | Footer | 收尾与出口 | 提供次级导航、作者署名、相关链接，用户决策后的去向 |

### 5.2 叙事主线（填空并论证）

> 叙事主线：从**「腐竹被命令行折磨的日常痛点」**到**「六大模块 + 四层聊天增强的完整方案」**到**「开源透明 + 持续迭代的信任」**再到**「一条命令 5 分钟部署」**。

**论证**：
- **痛点在前**——先共情后推销。如果先讲功能，用户会想"关我什么事"；先讲痛点，用户会想"对，我就是这样"，建立共鸣后再给方案，转化率更高。
- **方案在中**——痛点激发需求后，必须立刻给出可落地的方案。FeatureShowcase → LiveDemo → ChatJourney → Comparison → UseCases 五个区块层层递进：先讲有什么能力，再展示长什么样，再深挖旗舰能力，再量化对比，最后落到"你属于哪种用户"。
- **信任在后**——用户认可方案后，下一步疑虑是"这东西靠不靠谱、会不会跑路"。TechStack + VersionTimeline 用技术透明度和迭代证据消除疑虑。
- **行动收尾**——信任建立后必须立刻给出行动出口，DeployCTA 用"一条命令"降低行动门槛，Footer 提供次级去向。

## 6. 文案风格指南

### 6.1 语调

**专业但不冷漠，技术感但不晦涩，有温度的工业风。**

- 专业：技术术语准确（"无头服务端""WebSocket 实时通信""JWT 认证"），不写外行话。
- 不冷漠：用"你"对话，不端架子；痛点描述用生活化场景（"半夜服务器炸了，还得爬起来开电脑"）而非干巴巴的技术描述。
- 有温度：体现对腐竹的理解与共情，"管理服务器本该是享受，而不是被命令行折磨"。
- 工业风：用词干净利落，像齿轮咬合——"一键""批量""实时""自动"，少用形容词堆砌。

### 6.2 人称

**第二人称"你"为主，第一人称"我们"为辅。**

- 主人称"你"：让用户代入，"你中了几个？""你的服务器"。
- 辅助人称"我们"：表达立场时使用，"我们把整个服务端搬进浏览器"。
- 禁止第三人称叙事（"用户可以……"）——拉开距离、缺乏温度。

### 6.3 句长

| 文本层级 | 字数上限 | 说明 |
|---------|---------|------|
| 主标题（h1/h2） | ≤15 字 | 一眼可读，如"让 Factorio 服务器管理像玩游戏一样简单"前半句 12 字 |
| 副标题/区块描述 | ≤30 字 | 一口气读完，如"从实例托管到社区运营，每个环节都有专业工具支撑" |
| 正文/描述 | ≤60 字 | 两行内可读完，超出则拆句 |
| 按钮 CTA | ≤6 字 | 如"立即登录体验""查看源码""复制" |
| 痛点细节 | ≤40 字 | 引号内场景化短句 |

### 6.4 禁用词清单（可执行，每个均有合规替代写法）

| 禁用词 | 禁用原因 | 合规替代写法 |
|--------|---------|-------------|
| **最强** | 主观最高级，无衡量标准，易引发争议 | "核心"/"主力"/"旗舰"（如"最强聊天系统"→"旗舰聊天增强能力"） |
| **绝对** | 绝对化用语，无例外不成立 | 删除或改"始终"/"默认"（如"绝对安全"→"默认启用 JWT 认证"） |
| **100%** | 不可验证的绝对化数字 | 删除百分比，改陈述事实（如"100% 开源免费"→"开源免费，代码可审计"） |
| **10x 提升** | 无基准无测量方法的倍数承诺 | 改为可验证对比（如"10x 效率提升"→"5 分钟上手 vs 命令行 1-2 周入门"） |
| **90% 降低** | 无基准无测量方法的百分比承诺 | 改为具体能力（如"90% 管理成本降低"→"自动备份 + 一键回滚，无需手动复制文件"） |
| **完美** | 主观无标准 | "完整"/"齐全"（如"完美覆盖"→"完整覆盖"） |
| **第一** | 排名承诺无依据 | 删除或改"首批"/"早期" |
| **领先** | 比较无对象 | 改具体能力描述 |
| **秒级** | 不可验证的时间承诺 | "毫秒级"需标注条件，或改"实时"（"WebSocket 实时同步"） |
| **无与伦比** | 主观最高级 | 删除 |
| **永久免费** | 不可承诺的未来 | "开源免费"（仅陈述当前事实） |
| **零门槛** | 绝对化 | "低门槛"/"快速上手" |
| **彻底告别** | 绝对化 | "告别"/"不再需要"（如"彻底告别手动下载"→"告别手动下载解压"） |
| **完整的**（修饰工具） | 需谨慎，除非确为闭环 | "覆盖……场景"或列举具体能力 |
| **专业的**（无依据修饰） | 主观自夸 | 删除或改"专为……设计" |

> **执行规则**：所有文案在 `/apply` 阶段落地前，需逐条对照本清单核查；出现禁用词必须替换为合规写法，不得保留。
