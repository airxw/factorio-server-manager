> **状态**：规划已确认，待实施

> **目标版本**：v2.0.0
> **创建时间**：2026-06-28
> **最后更新**：2026-06-28

## 一、背景与问题

### 当前架构痛点

v1.0.3 已完成多实例基础设施（数据库表、路径解析、实例生命周期管理），但**前端完全没有实例上下文**，导致：

- 所有管理页面（配置/存档/Mod/玩家/名单/监控/日志/备份/商城管理）固定操作 `default` 实例
- 创建第二个实例后，**无法管理其内容**（只能启动/停止/删除/切换开关）
- 实例页面只是一个"生命周期管理器"，不是真正的管理入口

### 核心认知

**实例是最大的顶层容器**，每个实例 = 一个独立的 Factorio 游戏服务器。所有资源管理（配置/存档/Mod/玩家/名单/监控/日志/备份/商城）都应归属于某个实例，在实例作用域内进行。

---

## 二、已确认的设计决策

| 决策项 | 选择 | 说明 |
|--------|------|------|
| 导航结构 | **实例中心化** | 侧边栏只留"实例"入口，点击进入详情页，详情页内有子导航 |
| 控制台 | **所有实例总览** | 首页显示所有实例卡片（状态/PID/端口），点击进入详情 |
| 用户购物 | **选实例购物** | 用户进入商城先选实例，订单归属该实例，发货到对应实例 |
| VIP 日限额 | **按实例独立** | 每个实例有独立日限额（VIP1 在实例 A、B 各可买 1 件） |
| 向后兼容 | **旧路由重定向** | `/config` → `/instances/default/config` 等 |

## 三、目标架构

### 3.1 新侧边栏结构

```
├─ 控制台 (/)                    ← 所有实例总览卡片
├─ 实例 (/instances)             ← 实例列表，点击进入详情
├─ 用户功能
│   ├─ 商城 (/shop)              ← 先选实例再购物
│   ├─ 我的订单 (/orders)        ← 跨实例订单+实例列
│   └─ 个人资料 (/profile)
└─ 管理后台
    ├─ 用户管理 (/user-admin)    ← 全局
    ├─ VIP 权限 (/vip-admin)     ← 全局
    └─ 设置 (/settings)          ← 全局
```

**移除的侧边栏项**（变为实例详情子页）：
- 玩家、名单、监控、配置、存档、Mod、日志、备份、商品管理

### 3.2 实例详情页 `/instances/:id`

子导航 10 个标签，所有 API 调用带 `instance_id`：

| 标签 | 路由 | 功能 | 后端状态 |
|------|------|------|----------|
| 概览 | `/instances/:id` | 状态/PID/端口/版本/启动停止/开关 | ✅ 已有 |
| 配置 | `/instances/:id/config` | server-settings.json 编辑 | ✅ 已支持 instance_id |
| 存档 | `/instances/:id/saves` | 上传/下载/删除/选择 | ✅ 已支持 |
| Mod | `/instances/:id/mods` | 上传/启用/禁用 | ✅ 已支持 |
| 玩家 | `/instances/:id/players` | 在线玩家/踢出 | ❌ 需加 instance_id |
| 名单 | `/instances/:id/lists` | ban/whitelist/admin | ✅ 已支持 |
| 监控 | `/instances/:id/monitor` | CPU/内存（按 PID） | ❌ 需加 instance_id |
| 日志 | `/instances/:id/logs` | factorio 输出+文件持久化 | ❌ 需加 instance_id |
| 备份 | `/instances/:id/backups` | 存档备份/恢复 | ❌ 需加 instance_id |
| 商城管理 | `/instances/:id/shop-admin` | 本实例商品/订单 | ✅ 已支持 |

### 3.3 控制台 `/`

- 每个实例一张卡片：名称、状态徽章、PID、端口、版本
- 卡片快捷按钮：启动/停止
- 点击卡片 → 进入实例详情

### 3.4 用户购物 `/shop`

1. 进入商城先选实例（下拉或卡片选择）
2. 显示该实例的商品
3. 下单时 `instance_id` 写入订单
4. 发货时 RCON 命令发到对应实例的 factorio 进程

### 3.5 VIP 日限额（按实例独立）

- `shop_orders` 已有 `instance_id` 字段（v1.0.3 完成）
- 日限额统计查询：`WHERE user_id=? AND instance_id=? AND date(created_at)=today`
- **无需新增数据库字段**，仅修改查询逻辑

## 六、数据库迁移说明

### v2.0.0 涉及的数据库变更

| 变更 | 类型 | 迁移脚本 | 备注 |
|------|------|----------|------|
| VIP 日限额按实例统计 | 查询逻辑 | `20260628140000_shop_daily_usage_per_instance.ts` | 无字段变更，仅记录逻辑变更 |

**说明**：v1.0.3 已完成 `instances` 表和 `shop_items`/`shop_orders` 的 `instance_id` 字段迁移。v2.0.0 不新增字段，仅修改查询逻辑（日限额统计加 `instance_id` 条件）。

### 迁移脚本规范

- 文件名格式：`YYYYMMDDHHMMSS_description.ts`
- 导出 `up()` 和 `down()` 函数
- 幂等设计（可重复执行）
- `up()` 中记录逻辑变更说明
- `down()` 中记录回滚说明

## 八、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 前端 8 个页面重构工作量大 | 高 | 分阶段实施，每阶段独立可部署 |
| RCON 分发改动 instanceManager 进程管理 | 中 | 保留默认实例原有逻辑，新增实例用新机制 |

| 实例日志文件持久化磁盘占用 | 低 | 默认实例沿用现有 logs 目录，自定义实例按需清理 |
