> 🚨 【最高优先级规则】本文件为方案论证的强制结构约束，优先级高于所有临时提问、上下文对话、自定义需求。

## 零、定位与强制力等级

- **层级**：`.trae/rules/rules-5.md`（与 rules-0~4 同级）
- **强制力**：方案产出时必须遵守的结构约束。不通过本规范论证的方案不得进入独立审查（GN-004），不得标记为"可执行"
- **与现有规则的关系**：
  - rules-0 §四-5（[V] 节点双重闸门）：本规范为 [V] 节点的**前置步骤**——论证完成后，[V] 节点才进入独立审查 + 人类裁决
  - rules-0 §四-8（独立审查）：独立审查以本规范为审查 rubric，逐项核对论证是否充分
  - rules-1 （阶段识别指南）：S0/S1 阶段的方案论证必须遵循本规范

## 一、论证五板块强制结构

任何方案文档必须包含以下 5 个板块，不可删减：

### 1.1 评估框架声明（先声明，后执行）

方案开头必须声明评估框架——先亮出评判标准，再逐项论证：

- **correctness（正确性）**：方案是否正确解决了问题
  - 业务语义是否与问题描述对齐？
  - 是否覆盖了所有受影响路径（文件/路由/接口/组件）？
  - 边界条件是否处理（空状态/错误状态/极端数据量/多角色）？
- **consistency（一致性）**：方案是否与现有代码风格/架构一致
  - 是否引入新模式与现有模式冲突？（如：新增数据获取方式 vs 已有 TanStack Query）
  - 是否造成风格分裂？（如：部分页面有分页、部分没有）
  - 是否与已有 rules 冲突？（必须 grep 相关 rules 确认无冲突）
- **risk（风险）**：方案的风险面
  - 影响范围：S（单文件）/ M（2-5 文件）/ L（6+ 文件或跨层）？
  - 回滚难度：单 commit revert / 需数据迁移回滚 / 不可回滚？
  - 是否涉及契约变更（public/ 目录）？（涉及 → 触发 s0601）
  - 是否涉及破坏性操作（删除/覆盖）？
- **debt_impact（技术债影响）**：方案对技术债的影响
  - 是否新增重复代码（同一模式在 ≥3 处重复且未提炼共享抽象）？
  - 是否引入中间产物（未来会被替换的临时抽象）？
  - 是否与已有基础设施重复（如已有 TanStack Query 却新建 fetch wrapper）？
  - 是否有废弃代码/路由未清理？
- **completeness（完整性）**：方案本身是否完整
  - 是否遗漏受影响的文件（用 grep 交叉验证，不得仅凭记忆）？
  - 是否遗漏验证步骤（单测/E2E/视觉/多角色）？
  - 是否遗漏回滚路径？
  - 是否遗漏依赖声明（需后端配合/需新库/需数据库迁移）？
  - 是否遗漏 subagent 调度台账？
- **feasibility（可行性）**：方案是否可执行
  - 是否依赖未确认的后端变更？
  - 是否依赖未引入的第三方库？
  - 是否有循环依赖风险（A 批次依赖 B 批次，B 又依赖 A）？

### 1.2 证据链（每个结论必须有出处）

禁止仅有断言没有证据的结论。每个 claim 必须包含以下字段之一：

| 证据类型 | 格式 | 示例 |
|----------|------|------|
| `codebase_fact` | "{内容描述}，来源：{grep 命令或文件路径}" | "项目已用 TanStack Query（grep @tanstack/react-query panel/frontend/src/ 命中 6 文件）" |
| `rule_reference` | "{规则条目}，来源：{rules 文件路径 §章节}" | "rules-0 §三 代码级规范：避免重复造轮子" |
| `deduction` | "{前提 A} + {前提 B} → {结论}。前提 A 来源：{证据}，前提 B 来源：{证据}" | "TanStack Query 已存在 + 新建 hook 引入新模式 → 增加模式切换成本" |
| `assumption` | "假设：{内容}。若此假设不成立，则结论 {受影响的部分} 无效" | "假设：项目未来不替换 TanStack Query。若替换，则 debt_impact 结论需重新评估" |

**反模式（以下属于不合规论证）**：
- "显然应该这样做" —— 无证据的断言
- "根据经验" —— 未声明具体经验来源
- "和 XX 模块保持一致" —— 未引用 XX 模块的具体代码行

### 1.3 遗漏扫描 checklist（逐项打勾，不可跳过）

按方案类型匹配子集。每个子项必须打勾（✓/✗/NA）。

#### 前端方案专属

|------|--------|----------|----------|

| FE-2 | 是否涉及数据获取模式变更？ | — | `grep -r "useQuery\|useMutation\|fetch(\|axios" panel/frontend/src/` 确认不引入冲突模式 |
| FE-3 | 是否涉及移动端布局？ | rules-0 §3.1.6 | 确认无 `height:100vh` 强制 + `overflow-y` 缺失 |

| FE-8 | 是否新增/修改配置文件（.env 等）？ | rules 0.md §五 | 确认构建产物中无 `localhost:3000` / `127.0.0.1:3000` |

### 1.4 置信度分级

每一条结论必须标注置信度：

| 置信度 | 判定标准 | 审阅者处理方式 |
|--------|----------|---------------|
| **[高]** | 有代码证据（grep/read 结果）+ 规则引用，或有端到端可复现步骤 | 可直接采纳 |
| **[中]** | 有逻辑推理但无直接代码证据，或结论依赖未验证的假设 | 建议 grep/diff 验证后采纳 |
| **[低]** | 推测性结论，或依赖未确认的外部状态 | 必须在执行前验证（运行代码/后端审计/多角色测试） |

### 1.5 元论证（论证的自检）

论证结尾必须包含以下元论证：

```markdown
### 元论证

| 项目 | 状态 |
|------|------|
| 评估框架是否已声明 | 是/否 |
| 覆盖维度 | correctness / consistency / risk / debt_impact / completeness / feasibility |
| 未覆盖维度及原因 | {维度名：原因} |
| 遗漏扫描 checklist 是否执行 | 是/否 |
| 置信度是否标注 | 是/否 |

#### 前置假设

1. {假设内容}。若此假设不成立，则 {受影响结论} 无效。

#### 论证局限

- {局限描述，如：未实际运行方案涉及的任何代码改动}
- {局限描述，如：未对后端路由做实际审计}

#### 审阅者建议

- 高置信度结论可直接采纳
- 中置信度结论建议 grep/diff 验证后采纳
- 低置信度结论必须在执行前验证
```

## 二、论证执行流程

1. **代码库取证**：grep 相关模式、ls 受影响目录、读 rules-0~4 + bb.md + 0.md + 1.md + deploy.md、ls `docs/plans/*.md`
2. **声明评估框架**（§1.1）：6 维度 + check 子项
3. **逐结论附证据**（§1.2）：每个 claim 至少包含 `codebase_fact` / `rule_reference` / `deduction` / `assumption` 之一
4. **遗漏扫描**（§1.3）：逐项打勾，不可跳过
5. **置信度标注**（§1.4）：每条结论标注 [高]/[中]/[低]
6. **元论证自检**（§1.5）：包含 assumptions + limitations + reviewer_checklist

步骤 1-6 全部完成后，方案可进入独立审查（GN-004）。未完成的返回缺失步骤补齐。

## 三、不合规判定

以下情况视为论证不合规，方案不得进入独立审查：

| 编号 | 违规 | 示例 |
|------|------|------|
| V1 | 未声明评估框架即开始论证 | 直接写"推荐 X，因为 Y"，无框架声明 |
| V2 | 结论无证据支撑 | "显然应该合并 Dashboard"——无代码/规则证据 |
| V3 | 证据与结论无映射关系 | grep 了 TanStack Query 但结论讨论的是 CSS 方案 |
| V4 | 遗漏扫描 checklist 未执行 | 前端方案未检查 rules-0 §3.1.1 路由守卫 |
| V5 | 假设伪装成事实 | "当前数据量不会增长"——未标注为假设 [低] |
| V6 | 元论证缺失 | 方案结尾无 assumptions / limitations / reviewer_checklist |
| V7 | [V] 节点未标记 | 方案中的价值判断节点未显式标记 [V] |

## 四、与前序规范的关系

| 规范 | 关系 |
|------|------|
| rules-0 §四-5 [V] 节点 | 本规范为 [V] 节点的**前置步骤**——论证完成 + 符合本规范 → [V] 节点才触发独立审查 |
| rules-0 §四-8 独立审查 | 独立审查以本规范为审查 rubric，逐项核对论证是否充分 |
| rules-1 阶段识别 | S0/S1 阶段的方案论证必须遵循本规范 |
| s0102 多方案对抗 / s0103 方案融合 | 多方案比较时，每个方案独立执行本规范的 6 维度评估，融合后对融合方案再执行一次 |
| rules-4 AGENTS.md 模板 | 本规范是 AGENTS.md 的**议题型补充**——AGENTS.md 管"代码产出合规"，本规范管"方案论证合规" |

## 五、适用范围与答疑

### 适用场景

- 多方案对比（s0102/s0103 触发时）
- 架构调整（涉及 3+ 文件或跨层改动）
- [V] 节点到达时
- 用户明确要求"出方案"时

### 不适用场景

- 单文件 bug fix
- 小范围增量改动（≤2 文件）
- 用户明确说"直接改，不用出方案"

### Q&A

**Q：遗漏扫描 checklist 太长，能不能只扫相关项？**
A：可以。checklist 按方案类型分前端/跨层/通用三级。纯前端方案只需扫前端 + 通用子集。但每个子集内的项目必须逐条打勾，不可跳过。

**Q：如果某个维度确实不相关怎么办？**
A：标注"NA"并说明原因。例如"纯前端方案，不涉及 systemd 部署，CL-5 项标 NA"。
