## 二、MSLX 关键模块逐一拆解

### 2.1 实例创建后台服务（ServerCreationService）

**位置**：`MSLX.Daemon/Services/DeployServerService/ServerCreationService.cs`

**核心机制**：

- **任务队列模式**：`_taskQueue.DequeueTaskAsync(stoppingToken)` 串行消费任务，避免多实例并发下载/解压导致 IO 抖动。
- **进度回报**：通过 `IConfigBase.ServerList` + SignalR 实时回写进度，前端订阅 `instance.{id}` group 拿到阶段更新。
- **失败熔断**：单任务异常不会拖垮整个循环，只标记该 instance 状态为 `创建流程异常中断: {message}`，退出码 -1。
- **Docker 模式特殊处理**：MSLX 自身可能运行在 Docker 容器中 → 通过 `/proc/self/mountinfo` 抓 64 位容器 ID → `docker inspect` 反查宿主机挂载点，把容器内 `/app/DaemonData` 映射回宿主机物理路径，避免 bind mount 错位。

**关键代码片段**：

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var task = await _taskQueue.DequeueTaskAsync(stoppingToken);
        try { await ProcessCreation(task, stoppingToken); }
        catch (Exception ex)
        {
            await UpdateStatusAsync(task.ServerId, $"创建流程异常中断: {ex.Message}", -1, true, ex);
        }
    }
}
```

### 2.2 MCServerService 完整实现

**位置**：`MSLX.Daemon/Services/MCServerService.cs`（约 1700+ 行）

**核心数据结构**：

```csharp
// 单实例运行上下文（线程安全）
private class ServerContext
{
    public Process Process;                          // 进程引用
    public bool IsInitializing;                      // 启动中
    public bool IsStopping;                          // 用户主动停止中
    public bool IsProcessExited;                     // 主进程已 Exited
    public bool IsStdoutClosed, IsStderrClosed;     // 流 EOF
    public bool HasTriggeredExit;                    // 退出回调防重入
    public int FinalExitCode;                        // 退出码
    public readonly object StateLock = new();        // 状态锁
    public readonly ConcurrentQueue<string> Logs;    // 环形日志缓冲
    public readonly ConcurrentDictionary<string, bool> OnlinePlayers; // 玩家表
    public bool IsBackuping;                         // 备份中
    public bool MonitorPlayers;                      // 是否启用玩家追踪
    public bool IsDocker;                            // Docker 模式
    public double CpuBaseLimitPercentage;            // CPU 性能基线
}
```

**进程退出判定（三态合并）**：

```csharp
private void CheckAndHandleTrueExit(uint instanceId, ServerContext context)
{
    lock (context.StateLock)
    {
        if (context.HasTriggeredExit) return;
        if (context.IsProcessExited && context.IsStdoutClosed && context.IsStderrClosed)
        {
            context.HasTriggeredExit = true;
            if (_activeServers.ContainsKey(instanceId))
                HandleServerExit(instanceId, context.FinalExitCode);
        }
    }
}
```

**关键设计点**：

| 机制 | 实现 | 价值 |
|------|------|------|
| **崩溃熔断** | `ConcurrentDictionary<uint, List<DateTime>> _crashHistory` + 5 次/300 秒滑动窗口 | 防止配置错误时无限重启耗死机器 |
| **重启延迟** | 固定 5s（`Task.Delay(5000)`） | 给 OS 释放端口/文件的缓冲 |
| **流关闭三态** | Exited + StdoutClosed + StderrClosed | 避免子进程残留/僵尸进程 |
| **强制关闭** | 优先 `StandardInput.WriteLine("stop")` → 等 forceExitDelay 秒 → `Kill(true)` | MC 服务器走「stop」命令能正常保存世界 |
| **EULA 暂停** | 检测到未签 → SignalR 推 RequireEULA → 用户点确认 → 写文件 + 重启 | 阻塞式等用户操作 |
| **环形日志** | `ConcurrentQueue<string> Logs` + 限 MaxLogLines 2000 行 | 内存可控 |
| **玩家正则** | `PlayerJoinedRegex` / `PlayerLeftRegex` + `AnsiColorRegex` 去 ANSI 色码 | 不依赖 RCON，日志即真相 |
| **ProcessTracker** | 全局登记表，daemon 退出时统一杀 | 防 zombie |

```csharp
private string ResolveUuid(string basePath, string name, string? uuid)
{
    if (!string.IsNullOrEmpty(uuid)) return uuid;
    // 1. 从 usercache.json 查
    var usercache = ReadJsonFile<UserCacheItem>(Path.Combine(basePath, "usercache.json"));
    var hit = usercache.FirstOrDefault(u => u.name.Equals(name, StringComparison.OrdinalIgnoreCase));
    if (hit != null) return hit.uuid;
    // 2. 调 Mojang API（异步请求）
    return MojangApi.GetUuid(name);
}
```

```csharp
private async Task BackupServer(uint instanceId, ServerContext context)
{
    if (context.IsBackuping) return;          // 防重入
    context.IsBackuping = true;
    try
    {
        // 1. 若是 MC 服务器，先发送 "save-off" 暂停自动保存
        await SendCommandAsync(instanceId, "save-off");
        await SendCommandAsync(instanceId, "save-all flush");
        await Task.Delay(2000);  // 等待刷盘

        // 2. 打包 world 目录（含 dimension 子目录）
        string worldPath = ServerPropertiesPathUtils.ResolveWorldPath(server);
        string backupDir = Path.Combine(server.Base, "backups");
        string zipPath = Path.Combine(backupDir,
            $"backup-{DateTime.Now:yyyyMMdd-HHmmss}-{instanceId}.zip");

        ZipFile.CreateFromDirectory(worldPath, zipPath, CompressionLevel.Optimal, false);

        // 3. "save-on" 恢复
        await SendCommandAsync(instanceId, "save-on");

        // 4. 轮转：保留最近 N 份（默认 10），超量删最旧
        var backups = Directory.GetFiles(backupDir, "backup-*.zip")
            .OrderByDescending(File.GetCreationTime)
            .Skip(maxBackups)
            .ToList();
        foreach (var old in backups) File.Delete(old);
    }
    finally { context.IsBackuping = false; }
}
```

### 2.7 Map 渲染（MapRenderController）

**位置**：`MSLX.Daemon/Controllers/InstanceControllers/MapRenderController.cs`

**核心流程**：

1. **拿到 spawn 坐标**：`level.dat` 是 NBT 压缩格式（gzip/zlib），用 fNbt 库读 `Data.SpawnX/SpawnZ`。
2. **Region 文件解析**：`r.{x}.{z}.mca`（Anvil 格式）每文件 32×32=1024 个 chunk，每 chunk 16×16=256 个方块柱。
3. **McaParser**：定位 chunk 偏移（4 字节 location table）→ 读出压缩数据 → gzip/zlib 解压 → fNbt 解析 chunk NBT。
4. **Heightmap 解包**：`MOTION_BLOCKING` 和 `OCEAN_FLOOR` 用 9 bits/entry 紧凑打包到 long[]，UnpackHeightmap 反算每个 (x,z) 的最高方块 Y 坐标。
5. **方块名解析**：`block_states.palette` + `data`（palette index 数组）→ 拿到每柱顶层方块的 `Name`。
6. **颜色映射**：`BlockColorMap`（100+ 常见方块硬编码颜色），匹配失败则用「上一次成功颜色」（避免模组方块渲染出现黑块）。
7. **水深化**：动态根据 `topY - floorY` 差值给水方块渲染深浅。
8. **3D 阴影**：`ApplyHillshading` 根据相邻列高度差调整亮度。
9. **输出**：`Image<Rgba32>(512, 512).SaveAsPng()` → 返回 `File(bytes, "image/png")`。

**性能**：单 region 渲染约 200-500ms，可接受；不做缓存（玩家地块变化频繁）。

- 文件大小 > 2MB 拒
- 非白名单文本后缀且 IsBinaryFile 检测为二进制的拒
- 编码自适应：UTF-8 (no BOM) / GBK / 系统默认

**压缩解压（CompressController）**：

- `zip` / `unzip` / `tar.gz` 三种格式
- 大文件流式处理（ZipArchive + Stream）

**上传（UploadController）**：

- 分块上传：前端按 5MB 切片 → POST `/files/instance/{id}/upload-chunk` → 写到 `AppData/Temp/Uploads/{uploadId}.tmp` 偏移
- 全部完成后 POST `/files/instance/{id}/save-uploaded` → 校验 magic → 移动到目标路径
- **断点续传**：上传 ID + 偏移记录

**插件/模组管理（PluginsAndModsController）**：

- 列 `*.jar` + `*.jar.disabled` 两类
- 客户端模组识别（`IsClientSideMod`）：
  - Fabric：读 `fabric.mod.json` 的 `environment` 字段 = `client`
  - Forge/NeoForge：读 `META-INF/mods.toml` 的 `[[mods]]` 块 `side=CLIENT`
  - 优先级：先 minecraft 块 side > 第一个块 side
- 操作：`disable`（改名 + `.disabled` 后缀）/ `enable`（去后缀）/ `delete`
- **特点：与 MC 客户端启动逻辑完全对齐**

**宿主机文件系统（HostFsController）**：

- `[Authorize(Roles = "admin")]` 严格限管理员
- 过滤 Hidden/System 属性的目录与文件
- 跨平台驱动列表：Windows 全部，Linux/macOS 过滤 `/Volumes/` `/mnt/` `/media/`
- 给前端一个文件选择器，用于在创建实例时直接选本机 zip modpack

### 2.10 Python / Java 扫描器

**Python（PythonController）**：

- `IPythonScannerService`（SDK 抽象）+ `PythonScannerService`（Daemon 实现）
- 扫描 `which python3` / `python` / 常见安装路径（`/usr/bin/python3`、`/opt/python*/bin/python3`、`C:\Python*`）
- `Inspect(python)`：实际 `python --version` 跑一遍确认可用
- 用于 MCDReforged 部署

**Java（JavaScannerService）**：

- 见 §2.3
- 缓存策略：`Config.json` 写 `JavaCache` 字段，下次直接读

### 2.11 路径安全（FileUtils.GetSafePath + ServerPropertiesPathUtils）

**位置**：`MSLX.Daemon/Utils/FileUtils.cs` + `MSLX.Daemon/Utils/ServerPropertiesPathUtils.cs`

**核心防越界逻辑**：

```csharp
public static (bool IsSafe, string FullPath, string Message) GetSafePath(string basePath, string relative)
{
    string fullBase = Path.GetFullPath(basePath);
    string fullPath = Path.GetFullPath(Path.Combine(fullBase, relative));

    // 关键：规范化后必须以 basePath 开头（防止 ../ 逃逸）
    if (!fullPath.StartsWith(fullBase + Path.DirectorySeparatorChar) && fullPath != fullBase)
        return (false, "", "路径越界");

    if (fullPath.Contains("..")) return (false, "", "路径含 ..");
    return (true, fullPath, "OK");
}
```

**`ServerPropertiesPathUtils.NormalizeRelativePath(value, defaultName, errorMsg)`**：

- 若用户配置的世界/插件/区域路径为空 → 用默认值
- 若为绝对路径 → 报错（必须是相对）
- 若含 `..` 或非 ASCII 字符 → 报错

**MSLX 路径规范**：

- `server.Base`：实例根目录绝对路径
- `server.WorldPath` / `PluginsPath` / `ModsPath` / `RegionPath`：相对路径，存到 `server.properties` 风格字段
- 运行时通过 `NormalizeRelativePath` + `GetSafePath` 解析

## 三、与 gameserver-panel 横向对比

### 3.1 架构对比

| 维度 | MSLX | gameserver-panel |
|------|------|------------------|
| **进程模型** | 单 daemon（C#/.NET 8 ASP.NET Core） | daemon (Node.js TS) + panel-backend (Koa) + panel-frontend (React) 三进程 |
| **API 通信** | SignalR（WebSocket + Server-Sent Events） | WebSocket（daemon ↔ backend）+ REST HTTP（backend ↔ frontend） |
| **鉴权** | JWT Bearer + Roles | daemon: Bearer Token / WS query token；backend: JWT；前端: session |
| **实时事件** | SignalR Groups（按 instanceId 分组） | WS 自定义事件 + 后端代理到 frontend |
| **数据存储** | JSON + LiteDB（部分） | SQLite (better-sqlite3) + JSON 配置 + 业务表 |
| **Docker 隔离** | 内建支持（docker-java / docker-custom） | 无（P0 单机模式直跑） |
| **跨平台** | Win/Linux/macOS 完整支持 | Linux 优先（P0） |
| **语言/栈** | C# + .NET 8 + SignalR + ImageSharp + fNbt | TypeScript + Node.js + ws + child_process + React |

### 3.2 实例管理关键路径对比

| 流程 | MSLX | gameserver-panel |
|------|------|------------------|
| **创建** | `ServerCreationService` 任务队列 + 异步 Deploy | `panel-backend` 调 daemon `POST /api/instances` + `bootstrapInstance()` 同步初始化 |
| **启动命令构造** | `MCServerService.InternalStartServerAsync`（600+ 行集中） | `manager.ts:start()` 调 `bootstrapInstance()` → `ProcessDriver.spawn()` |
| **崩溃检测** | `exitCode != 0` + `_crashHistory` 滑动窗口（5/5min） | `restartPolicy.ts`：指数退避（1s→2→4→…→30s 上限，最多 5 次） |
| **自动重启** | 固定 5s 延迟 | `calculateDelay(attempt)` 指数退避 |
| **进程退出判定** | Exited && StdoutClosed && StderrClosed 三态合并 | child_process `exit` 事件（单事件） |
| **玩家追踪** | 日志正则 `PlayerJoinedRegex` / `PlayerLeftRegex` | RCON `list` 轮询（依赖 `protocol/factory.ts`） |
| **EULA** | 显式暂停 + SignalR `RequireEULA` 事件 | gameserver-panel 当前未集成 EULA 检测/同意流程 |
| **备份** | `BackupManagerController` + `save-off/save-all/save-on` 协议 + zip + 轮转 | 已有 `BackupService`（需对照实现细节） |
| **白名单/封禁** | JSON 文件直读写 | 经 RCON 走 MC `whitelist add/remove` 命令 |
| **Map 渲染** | fNbt + ImageSharp 自研 | 未实现 |

### 3.3 关键差异点解读

#### 差异 A：进程退出判定

- **MSLX** 用三态合并，避免「子进程残留管道导致 WaitForExit 永远返回 false」或「主进程 Exited 但 stdout 还在 flush 导致重启请求和原进程 stdout 抢状态锁」。
- **我们**只听 `exit` 事件，简单可靠，但如果 `kill -9` 强杀后 stdout 还在写日志（罕见但存在），可能错过。

#### 差异 B：崩溃熔断 vs 指数退避

| 维度 | MSLX (5次/5分钟) | 我们 (5次指数退避) |
|------|-------------------|---------------------|
| **总耗时** | 5 次间隔 5s ≈ 25s | 1+2+4+8+16+30 = 61s 上限 |
| **熔断条件** | 时间窗口内计数 | 失败次数累计 |
| **恢复机制** | 用户必须手动重启 | 永远停在 stopped 状态 |
| **适用场景** | 偶发 OOM 闪退能自动恢复 | 配置错误必须人介入 |

**trade-off**：MSLX 的策略更激进（用户配错 → 5 次崩 → 熔断），我们的更保守（配错 → 指数退避 → 满 5 次停）。**MSLX 的优势是「故障自愈」**，我们的优势是「防雪崩更彻底」。

#### 差异 C：玩家追踪方式

- **MSLX**：纯日志正则解析（不依赖 RCON 协议）
  - 优点：MC 日志格式稳定（vanilla/forge/fabric 都有 `Player X joined the game`），零协议握手开销
  - 缺点：必须开 MonitorPlayers；正则改版要跟进 MC 版本
- **我们**：走 RCON（`protocol/factory.ts` 实现的 MinecraftProtocol）
  - 优点：权威（直接问服务器）、支持命令执行
  - 缺点：依赖 RCON 端口连通、协议握手失败会断流

**互补思路**：可以日志正则做实时追踪 + RCON 做权威校准（每 30s 调一次 `list` 比对）。

#### 差异 D：Docker 隔离

- **MSLX**：内建 `docker-java` / `docker-custom` 两模式 + 容器内 daemon 反查宿主机路径 + 网络限速（tc qdisc）
- **我们**：P0 单机直跑，无 Docker

> 我们的多实例隔离目前靠「不同端口 + 不同 instance_root + system user 隔离」。Docker 是更彻底的隔离方式，但需要 daemon 能 spawn docker（当前部署在 `/opt/gameserver-panel/` 容器外的可能性需要评估）。

#### 差异 E：EULA 处理

- **MSLX**：阻塞式暂停 + SignalR 推 RequireEULA + 用户前端点确认 → 后端写 eula.txt → 重启
- **我们**：**未集成 EULA 流程**

> MC 1.7.6+ 不签 EULA 启动会立即退出。当前我们的 daemon 启动命令直接传 `eula=true` 绕过（`-jar` 参数或提前写 eula.txt），但没给用户一个「显式同意 EULA」的交互流程。**这是合规缺口**（Mojang EULA 要求用户明确同意）。

#### 差异 F：备份策略

- **MSLX**：MC 协议命令 `save-off / save-all / save-on` → zip world 目录 → 轮转 N 份
- **我们**：已有 `BackupService`（需对比实现细节；推测也走 RCON save flush）

> 核心差异：MSLX 走 zip 备份目录，我们可能走快照或 tar.gz。zip 兼容性好但不支持增量。

## 四、可借鉴机制清单（按落地难度排序）

> **评分标准**：
> - **P0**（立即可做，1-3 天）：架构无侵入，改动局部
> - **P1**（短期可做，1-2 周）：需要小幅架构调整或新增模块
> - **P2**（中期规划，1-2 月）：需要较深架构调整
> - **P3**（远期愿景）：需要大改造或等基础设施就绪

### P0（立即落地）

#### 1. 进程退出三态判定 + ProcessTracker 注册表
**借鉴点**：MSLX 的 `IsProcessExited && IsStdoutClosed && IsStderrClosed` 防僵尸机制 + `ProcessTracker.Track(process, false)` 全局登记防止进程泄漏。

**落地步骤**：
1. `daemon/src/instances/processDriver.ts` 增加 `stdoutClosed` / `stderrClosed` 标记
2. `manager.ts` 把判定从「单 exit 事件」改为「exit + stdout close + stderr close 三态合并」
3. 新增 `processTracker.ts`（全局 Map<pid, ChildProcess>），daemon 启动时清空，spawn 时注册，exit 时注销，收到 SIGTERM 时统一杀

**收益**：杜绝僵尸进程，daemon 自身被 kill 时所有子进程一并清场。

#### 2. 崩溃熔断保护（5次/5分钟）
**借鉴点**：MSLX `_crashHistory` 滑动窗口 + 熔断后用户必须手动重启。

**落地步骤**：
1. `restartPolicy.ts` 增加 `crashWindowMs` + `maxCrashesInWindow` 配置
2. `manager.ts` 在 `autoRestart` 分支前判断熔断
3. 熔断后通过 `state.change` 事件推 `error` 状态 + 原因「已熔断，请手动启动」

**收益**：配置错误时不会耗死 CPU/磁盘，比单纯指数退避多了「时间窗口维度」。

#### 3. 路径安全工具（FileUtils.GetSafePath 等价物）
**借鉴点**：MSLX 的 `GetSafePath` 防越界 + `NormalizeRelativePath` 强制相对路径。

**落地步骤**：
1. 在 `daemon/src/utils/` 新增 `pathSafety.ts`：`safeJoin(base, relative)` 函数
2. 现有所有 controller 涉及路径的入参（file_path、destination 等）走 `safeJoin` 校验
3. 加单元测试覆盖 `../` / 绝对路径 / 符号链接场景

**收益**：彻底杜绝路径遍历攻击（OWASP A01:2021 Broken Access Control）。

#### 4. 玩家日志正则 + RCON 双源追踪
**借鉴点**：MSLX 纯日志正则（不依赖 RCON）。

**落地步骤**：
1. `daemon/src/instances/playerTracker.ts` 已存在（用 recordJoin/Leave 驱动），新增 `logParser.ts`
2. `processDriver.ts` stdout 每一行调 `logParser.parse(line)` 触发 join/leave
3. RCON 协议层（`protocol/factory.ts`）每 30s 调 `list` 做权威校准
4. 双方结果合并到 PlayerTracker 的内存表

**收益**：不依赖 RCON 也能实时追踪玩家；RCON 断流时不丢事件。

#### 5. EULA 显式同意流程
**借鉴点**：MSLX 的 RequireEULA 暂停 + 写 eula.txt + 重启模式。

**落地步骤**：
1. `daemon/src/instances/bootstrap.ts` 启动命令前检查 eula.txt 状态
2. 缺失/未同意 → 返回 409 + EULA 未签错误码（而非 500）
3. 前端弹出 Mojang EULA 全文 + 「我已阅读并同意」复选框
4. 同意后 POST `/api/instances/{id}/eula/agree` → daemon 写 eula.txt + 重新启动
5. audit log 记录「用户 X 同意 EULA 于 Y 时间」

**收益**：Mojang EULA 合规；前端体验对齐 MCSManager / 1Panel。

### P1（短期落地）

#### 6. 任务队列化创建流程
**借鉴点**：MSLX `_taskQueue.DequeueTaskAsync` 串行化创建任务避免 IO 抖动。

**落地步骤**：
1. `daemon/src/instances/manager.ts` 新增 `creationQueue: PQueue`（concurrency=1）
2. 实例创建请求入队而非同步执行
3. 前端订阅 `instance.create.progress` 事件（WS 推送 step 1-5）
4. 失败入死信队列，admin 可重试

**收益**：避免多用户同时创建实例时磁盘 IO 抖动；进度可视化。

#### 7. 离线下载（自研 ParallelDownloader）
**借鉴点**：MSLX 不依赖 aria2，自研 HTTP Range 8 并发分片。

**落地步骤**：
1. `daemon/src/services/offlineDownload.ts` 新增
2. 用 Node.js 内置 `http` + `stream.pipeline` + Range 头实现分片下载
3. 进度回报走现有 WS 事件（`download.progress` / `download.complete`）
4. TTL 30 分钟的内存缓存任务状态

**收益**：避免引入 aria2 二进制依赖（容器化部署友好）；可控性高。

#### 8. 插件/模组 .disabled 重命名机制
**借鉴点**：MSLX 的 `PluginsAndModsController` 用 `.jar ↔ .jar.disabled` 改名代替删除（可逆）。

**落地步骤**：
1. `panel-frontend` 实例详情页「插件/模组」Tab 增加「启用/禁用/删除」三按钮
2. 后端 daemon 接收 action 走 `fs.rename` 实现
3. 列出时同时扫 `*.jar` + `*.jar.disabled`
4. 客户端模组检测（Fabric / Forge 的 side 字段）作为 P1 增强项

**收益**：操作可逆；用户能直接看到启用 vs 禁用列表。

#### 9. 备份轮转 + 自动触发
**借鉴点**：MSLX 的 save-off/save-all/save-on 协议 + zip + 保留 N 份。

**落地步骤**：
1. `daemon/src/services/backup.ts` 增加 `rotate(maxBackups: number)`
2. 备份前通过 RCON 走 `save-off` / `save-all flush` / 等 2s / `save-on`
3. 默认保留 10 份
4. cron 任务（已有）每天 4:00 触发一次自动备份

**收益**：磁盘空间可控；用户能配置保留策略。

#### 10. Docker 镜像伪协议（MSLX:// 风格）
**借鉴点**：MSLX 的 `MSLX://Java/21` / `MSLX://DockerImage/Java/21` 伪协议在配置里用语义化字符串。

**落地步骤**：
1. `public/schema/instance-schema.ts` 增加 `runtime` 字段，值如 `runtime:java21` / `runtime:python3.11` / `runtime:steamcmd`
2. daemon 启动时解析为绝对路径
3. 避免存绝对路径导致换机失效

**收益**：配置可移植；语义化。

### P2（中期规划）

#### 11. Docker 容器化启动 + 路径反查

## 五、关键风险与注意事项

### 5.1 借鉴时的兼容性陷阱

| 借鉴点 | 风险 | 缓解 |
|--------|------|------|
| 崩溃熔断 5/5min | 配置错误时用户看到「无法启动」不知所措 | 前端显示熔断原因 + 「点此查看日志」CTA |
| EULA 流程 | 用户嫌麻烦，跳过弹窗 | 一次性弹窗 + localStorage 记住已读 |
| 日志正则玩家追踪 | MC 版本更新改日志格式 | 多正则备选 + RCON 校准兜底 |
| Docker 模式 | 部署环境必须支持 docker；嵌套 docker 路径映射复杂 | 文档写清楚；提供「非 docker」回退开关 |
| 自研 ParallelDownloader | 大文件内存峰值（8 并发 × chunk 大小） | 限制最大 4 并发；chunk 大小自适应（5-10MB） |
| Map 渲染 | 超大世界（>10GB）渲染慢 | 限制单 region 渲染；异步 + 缓存 |

### 5.2 AC 范式契约约束

```typescript
  const fullBase = path.resolve(base);
```

## 八、最终结论

**MSLX 的核心优势**（可借鉴）：

1. **严谨的进程生命周期管理**（三态退出 + 熔断 + 容器内路径反查）
2. **极致的文件路径安全**（GetSafePath + NormalizeRelativePath）
3. **完整的 EULA/玩家/白名单/封禁合规流**（JSON 直读写 + UUID 解析）
4. **跨平台抽象做得到位**（PlatFormServices + 进程关闭 Windows/Linux 分支）
5. **MSLX:// 伪协议设计**（语义化配置，可移植）

**我们 gameserver-panel 的核心优势**（应保留）：

1. **前后端分离架构**（daemon/backend/frontend 三段式）→ 易扩展、清晰边界
2. **公共契约（public/）约束** → 禁止模块间私导，演进更可控
3. **Koa + TypeScript + Node.js 生态** → 开发速度快、工具链丰富
4. **与 P0 单机部署对齐** → 无 Docker 复杂度，生产稳定
5. **AC 范式规则体系** → 任务交接/审查/锚点文档可追溯

**落地建议**：

- **第一周**：路径安全工具（#3）+ 崩溃熔断（#2）+ 进程退出三态（#1）
- **第二周**：EULA 流程（#5）+ 备份轮转（#9）
- **第三周+**：离线下载（#7）+ 插件/模组 disabled 机制（#8）+ 任务队列化创建（#6）
- **Q3 后期**：Docker 模式评估 + Map 渲染（视用户需求）
- **Q4+**：跨平台 + 自研 UUID 解析

> **关键原则**：借鉴不是复制。MSLX 用 C#/.NET，我们用 TypeScript/Node.js。借鉴「机制」而非「实现」——三态判定逻辑相同，但实现可以是 EventEmitter；熔断策略相同，但数据结构可以是 Map<Date, number> 而不是 List<DateTime>。
