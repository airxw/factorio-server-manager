## 一、问题诊断

### 1.1 根目录污染

| 文件 | 大小 | 类型 | 性质 |
|------|------|------|------|
| `游戏专用服务器调研报告.md` | 94KB | 调研报告 | 一次性长文，应归档 |
| `游戏专用服务器调研报告2-Valheim-Zomboid.md` | 55KB | 调研报告 | 一次性长文，应归档 |
| `GSP项目升级评估报告.md` | 28KB | 升级评估 | 阶段性产物，应归档 |
| `Tebex开发者文档分析报告.md` | 20KB | 第三方分析 | 一次性调研，应归档 |
| `version.md` | 138KB / 2001行 | 版本历史 | 严重膨胀，需拆分 |
| `AGENTS.md` / `README.md` / `version.json` | — | 常驻锚点 | 合法 |

**问题本质**：
- 根目录同时承担了"代码仓入口"与"草稿落地区"两种职能
- 任何下载/检索都会先命中这些大文件，污染浏览体验
- `version.md` 因每版本追加详细变更未做归档，导致单文件超过 100KB

### 1.2 分类混乱

| 现状 | 问题 |
|------|------|
| `docs/` 下同时存在"正式文档"和"执行计划"和"调研报告" | 同一目录承担多种职能 |
| `.trae/documents/` 已积累 50+ 文件，命名风格混杂（`YYYYMMDD_主题.md`、`主题-plan.md`、`主题-合并.md`） | 缺乏命名规范 |
| `docs/archive/` 与 `docs/` 同级，缺少 `archive/reports/` `archive/plans/` 子分类 | 历史归档粒度不够 |
| `.trae/documents/test_reports/` 与 `screenshots/` 等子目录 | 已经在自发分层，但无规则约束 |

### 1.3 规则缺失

- `.trae/rules/rules-5.md` 定义了锚点体系，但**未规定"调研报告"和"分析报告"应该放在哪**
- `bb.md` 只规定 `version.md` 在根目录，**未规定 version.md 的体量上限**
- `AGENTS.md` 提到"写入前必读"清单，但**未约束写入位置**

## 二、目标文档分类

将项目所有 `.md` 文档（含计划/调研/分析/历史）划分为五类，每类有唯一落点：

| # | 类别 | 落点 | 生命周期 | 示例 |
|---|------|------|---------|------|
| ① | **常驻锚点** | 项目根目录 | 永久，每次更新同步 | `README.md`、`AGENTS.md`、`version.md`（精简版）、`version.json` |
| ② | **正式用户文档** | `docs/` | 长期维护，结构稳定 | `production-deployment.md`、`runbook.md`、`pack-development-guide.md` |
| ③ | **报告与调研** | `docs/reports/` | 历史性，沉淀后只读 | 调研报告、对比分析、升级评估、第三方分析 |
| ④ | **执行计划（活态）** | `docs/plans/` | 进行中可编辑，完结后归档 | `v4.0.0-execution-plan.md`、`remote-node-deploy-plan-E.md` |
| ⑤ | **AC 范式锚点** | `.trae/` | 跨断面交接 | `documents/`（变更留痕）、`specs/`（任务约束）、`rules/`（规则） |

### 2.1 各类详细定义

**① 常驻锚点（根目录）**
- 进入项目 5 秒内能读懂的入口
- 文件数量 ≤ 6 个（README、AGENTS、version、version.json、CHANGELOG 如有、说明 1 个）
- 单文件大小上限：50KB（`version.md` 单独约束见下文）

**② 正式用户文档（`docs/`）**
- 面向最终用户/运维
- 内容稳定，更新频率低
- 文件名：`<主题>-<类型>.md`（如 `production-deployment.md`）

**③ 报告与调研（`docs/reports/`）**
- 阶段性调研、对比、评估、第三方分析
- 一旦产出不再修改
- 子分类：
  - `docs/reports/research/` — 通用调研（如游戏服务器调研）
  - `docs/reports/evaluation/` — 升级/重构评估
  - `docs/reports/analysis/` — 第三方产品/竞品分析
  - `docs/reports/INDEX.md` — 索引文件

**④ 执行计划（`docs/plans/`）**
- 仍在进行或可重用的执行方案
- 完结后由执行人手动迁入 `docs/archive/plans/`
- 文件名：`<版本号或主题>-<类型>-plan.md`

**⑤ AC 范式锚点（`.trae/`）**
- `documents/`：变更与过程留痕（每变更一文，YYYYMMDD 命名）
- `specs/`：spec 三件套（任务级约束）
- `rules/`：AI 行为规则
- `skills/`：Skill 定义

> 待写入 `.trae/rules/docs-archiving.md`（语义化命名，用户决策 2026-07-23）。

```yaml
# docs-archiving.md 草稿：文档归档与分类规则

project_doc_classification:
  tier_1_resident_anchors:                # ① 常驻锚点
    location: Project_Root/
    allowed:
      - README.md                          # 用户入口
      - AGENTS.md                          # AI 代理入口
      - version.md                         # 版本历史（精简版）
      - version.json                       # 机器可读版本号
    constraints:
      max_files: 6
      max_size_kb:
        version.md: 50                     # version.md 体量上限
        other: 20
      no_research_reports: true            # 根目录严禁出现调研/分析/评估/计划类文档

  tier_2_formal_docs:                     # ② 正式用户文档
    location: docs/
    naming: "<主题>-<类型>.md"
    types: [guide, deployment, runbook, tutorial]
    examples: [production-deployment.md, runbook.md]
    update_frequency: low                  # 内容稳定，季度级更新

  tier_3_reports:                         # ③ 报告与调研
    location: docs/reports/
    subdirs:
      research/: 通用调研
      evaluation/: 升级/重构评估
      analysis/: 第三方产品/竞品对比分析
    naming: "<主题>-<类型>.md" 或 "<主题>.md"
    examples:
      - docs/reports/research/game-dedicated-server-survey.md
      - docs/reports/analysis/tebex-developer-doc-analysis.md
    update_frequency: never                # 一次性产出，沉淀后只读

  tier_4_plans:                           # ④ 执行计划（活态）
    location: docs/plans/
    naming: "<版本或主题>-<类型>-plan.md"
    examples:
      - docs/plans/v4.0.0-execution-plan.md
      - docs/plans/remote-node-deploy-plan-E.md
    lifecycle:
```

## 九、风险与说明

- **`version.md` 不拆分的好处**：保留完整历史、`git blame` 不被切断、外链不失效。**代价**：单文件持续膨胀。
- **`version.md` 软上限 100KB 当前已超出（138KB）**：`npm run check` 将输出告警但不阻断；下次超过 200KB 时强制启用分卷归档。
- **外链失效风险**：如果文档被外部链接（如 wiki、issue），重命名会导致链接失效。**缓解**：在 `docs/reports/INDEX.md` 与 `docs/version-history.md` 中保留旧文件名注释，必要时创建 `.md` 重定向文件（GitHub 支持 `<meta http-equiv="refresh">`）。
- **`docs/version-history.md` 定位**：仅作索引文件（不复制 version.md 内容），避免双份维护成本。
- **批量重命名的提交合并策略**：建议每个步骤单独提交（如 `chore: move research reports`、`chore: archive old version history`），便于回滚。
- **frontmatter 引入历史成本**：现存的 50+ 报告/计划文件需补全 frontmatter，建议分批执行（先新建的，后历史的）。
- **`.trae/documents/` 改名风险**：若其他文档（含本文件）通过相对路径引用了 `.trae/documents/20260721_MSLX...md`，迁移后路径失效。**缓解**：步骤 13 全面搜索更新。
