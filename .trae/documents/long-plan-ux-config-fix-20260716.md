# GameServer Panel 3.0 — UX与配置体系深度差距分析报告

> 日期：2026-07-16 | 状态：仅分析，不修改代码 | 作者：GN-001 分析
>
> 本文档基于对 `gameserver-panel` 与参考项目 `factorio` 的完整代码审查生成，聚焦前端用户体验、中文本地化、配置引导、功能链路完整性。

***

## 一、整体结论

`gameserver-panel` 的前端代码在**组件层面**是完整实现的——所有页面均有实际渲染逻辑，无一页是空壳。但存在**三层断裂**导致用户感知"空空荡荡"：

| 断裂层               | 问题本质                                                    |
| ----------------- | ------------------------------------------------------- |
| **第1层：Pack名称英文化** | 5个Pack的`display_name`全部英文，用户在创建服务器时无法识别游戏               |
| **第2层：背包端功能链路不通** | Daemon无法自动下载Factorio等4款游戏的二进制，配置/MOD/存档等Tab虽有界面但后端数据流断裂 |
| **第3层：配置编辑器零引导**  | 配置文件是裸JSON textarea，无表单、无中文标签、无Schema可视化、无空数据解释         |

三层叠加的效应：用户创建服务器 → 看到英文游戏名不知道选哪个 → 选了之后进入实例详情 → Daemon无法启动（无二进制）→ 所有Tab展示空数据 → 想手动配置又面对裸JSON编辑器无从下手。**每一步都在劝退用户。**

***

## 二、Pack名称与中文本地化

### 2.1 当前Pack display\_name（全部英文）

| Pack ID             | display\_name                     |
| ------------------- | --------------------------------- |
| `palworld-vanilla`  | `Palworld (Dedicated Server)`     |
| `minecraft-vanilla` | `Minecraft Java (Vanilla)`        |
| `factorio-vanilla`  | `Factorio (Vanilla)`              |
| `rust-vanilla`      | `Rust (Vanilla)`                  |
| `ark-vanilla`       | `ARK: Survival Evolved (Vanilla)` |

### 2.2 创建服务器时用户看到的Pack下拉选项

```
Palworld (Dedicated Server) — palworld/vanilla (v1.0)
Minecraft Java (Vanilla) — minecraft/vanilla (v1.0)
Factorio (Vanilla) — factorio/vanilla (v1.0)
Rust (Vanilla) — rust/vanilla (v1.0)
ARK: Survival Evolved (Vanilla) — ark/vanilla (v1.0)
```

**问题**：

* 完全无中文。不懂英文的用户无法辨认游戏。

* `palworld` 对非游戏玩家无法联想到"幻兽帕鲁"。

* `vanilla` 是技术术语（原版），普通用户不理解。

* `v1.0` 是Pack版本号而非游戏版本号，但用户很可能误解。

### 2.3 深层内容的中文覆盖情况（已有但未使用）

Pack YAML文件的**深层内容**已经有完整中文翻译：

* 物品列表 `items.static_list[].display_name`：铁板、铜板、帕鲁球、钻石镐、三角龙鞍... **全部中文**

* 配置文件schema `config_files[].schema.*.description`：服务器名称、最大玩家数、启用RCON... **全部中文**

* 命令帮助 `GameCommandHelp.tsx`：10个游戏内命令 **全部中文**

**结论**：中文翻译工作已经做了，但最关键的入口层（Pack名称）被遗漏了。更深层的问题：**前端代码没有从Pack API读取物品中文名**，而是使用静态映射表 `ITEM_NAME_ZH`，该映射表仅覆盖Minecraft风格物品名，导致Palworld/Factorio/ARK/Rust的物品在商城中全部显示为英文原文。

### 2.4 商城物品名称断层

| 游戏        | Pack中物品名格式      | 物品display\_name(中文) | 前端映射表是否覆盖 | 用户看到                  |
| --------- | --------------- | ------------------- | --------- | --------------------- |
| Minecraft | `diamond_sword` | 钻石剑                 | ✅ 有映射     | **钻石剑**（中文）           |
| Factorio  | `iron-plate`    | 铁板                  | ❌ 无映射     | `iron-plate`（灰色英文）    |
| Palworld  | `pal-sphere`    | 帕鲁球                 | ❌ 无映射     | `pal-sphere`（灰色英文）    |
| ARK       | `stone-pickaxe` | 石镐                  | ❌ 无映射     | `stone-pickaxe`（灰色英文） |
| Rust      | `can.beans`     | 豆罐头                 | ❌ 无映射     | `can.beans`（灰色英文）     |

**根因**：前端 `utils/gameItemName.ts` 的 `ITEM_NAME_ZH` 映射表是硬编码的静态Map，而Pack YAML中的物品 `display_name` 是动态可配置的。这两套数据源没有打通——**前端没有从后端API读取Pack物品列表及其中文display\_name**。

## 三、创建服务器体验分析

### 3.1 表单现状

当前 `CreateServer.tsx` 表单仅有4个字段：

| 字段      | 类型     | 说明                     |
| ------- | ------ | ---------------------- |
| 服务器名称   | text   | placeholder "例如：我的生存服" |
| Pack    | select | 英文游戏名下拉                |
| 游戏端口    | number | 留空自动分配                 |
| RCON 端口 | number | 留空自动分配                 |

### 3.2 缺失的引导信息

与Factorio参考项目对比：

| 引导维度   | Factorio项目  | GameServer Panel                | 差距           |
| ------ | ----------- | ------------------------------- | ------------ |
| 游戏选择帮助 | 无（单游戏，不需要）  | 无任何解释"Pack是什么"                  | **多游戏场景必需**  |
| 端口说明   | 显示默认端口34197 | 无默认值提示、无建议范围                    | **用户不知道填什么** |
| RCON说明 | 不需要（自动配置）   | 无解释RCON用途                       | **普通用户不理解**  |
| 版本选择   | 有版本下拉       | 无                               | **缺失关键字段**   |
| 存档选择   | 可选已有存档或新建   | 无                               | **缺失**       |
| 节点选择   | 无（单机）       | `node_id`硬编码为`'node-local'`，不可见 | **多节点场景断裂**  |
| 创建后反馈  | 有状态展示       | 直接跳转，无"创建成功"确认                  | **体验割裂**     |

### 3.3 node\_id硬编码问题

`CreateServer.tsx` 第94行：`node_id: 'node-local'` 硬编码。这意味着：

* 即使以后添加了远程Daemon节点，用户也无法在创建时选择

* UI上没有节点选择器，用户甚至不知道实例将部署在哪个节点上

### 3.4 JSX中残留"服务器"术语

虽然路由已从 `/servers` 迁移到 `/instances`，但 `CreateServer.tsx` 的JSX中仍大量使用"服务器"一词（"创建服务器"、"服务器名称"、"创建成功"等），与导航栏的"实例"术语不一致。

## 四、实例详情页逐Tab体验分析

### 4.1 控制台 (RconConsole)

| 项目     | 状态                | 评价                      |
| ------ | ----------------- | ----------------------- |
| 日志显示   | ✅ 已实现             | WebSocket实时推送，显示stdout行 |
| 命令输入   | ✅ 已实现             | 回车发送                    |
| 命令历史   | ❌ 缺失              | 无上下箭头历史记录               |
| 命令参考   | ❌ 缺失              | 仅有示例"list"（英文），无帮助文档    |
| WS状态   | ⚠️ 显示"WS 已连接/未连接" | "WS"是技术术语，应改为"实时连接"     |
| 空状态    | "暂无日志输出，等待服务器启动…" | 合理                      |
| 未运行时提示 | "服务器未运行，无法发送命令"   | 合理                      |

### 4.2 配置文件 (ConfigFiles)

**这是最大的UX黑洞**。配置文件编辑器是一个裸 `<textarea>`，用户直接面对原始JSON：

```
现状：
┌─────────────────────────────────┐
│ 配置文件列表          │ 编辑器   │
│ ┌─────────────────┐  │         │
│ │ palworld-settings│  │{"Server │
│ │ server-auto-cfg │  │Name":"",│
│ │ game-user-sett   │  │"Server  │
│ └─────────────────┘  │Desc...  │
│                      │}        │
│  [查看 Schema ▼]    │[保存]   │
│  { "type": "object",│         │
│    "properties": {} │         │
│  }                  │         │
└─────────────────────────────────┘
```

问题清单：

* **无表单字段**：用户必须手动编辑原始JSON，一个逗号错误就导致保存失败

* **文件名无翻译**：显示的是原始name如 `palworld-settings`、`server-auto-cfg`，无中文标签

* **Schema不可见**：JSON Schema隐藏在 `<details>` 折叠面板中，标签是"查看 Schema"（技术术语）

* **无空数据解释**：空状态显示"暂无配置文件。"，不说明原因（服务器未启动？需要手动创建？）

* **无格式提示**：仅显示`format`标签（json/ini/properties），不提示编辑注意事项

* **只读标记**：橙色"只读"徽章显示，但无解释为什么只读

### 4.3 商城 (Shop)

* 商品列表可用，物品名问题见2.4节

* 订单管理可用

* CDK兑换可用

* 商城管理Tab是**导航枢纽**（3个按钮跳转子页面），而非真正的管理界面，可能让用户困惑

### 4.4 Mod管理 (Mods)

* 列表/创建表单可用

* 空状态"暂无 Mod 记录。点击「添加 Mod」创建。"——但**没有解释Mod是什么、从哪获取、如何安装**

* Mod依赖检测为P0 stub（`conflicts`恒为空），用户看不到真实的兼容性信息

* Mod下载功能仅返回URL不实际下载

### 4.5 存档管理 (Saves)

* 列表/创建/激活可用

* 激活功能仅更新DB标记，不会实际切换服务器存档（后端P0 TODO）

* 大问题：用户点击"激活"看到一个存档，但进入游戏后发现不是这个存档，完全无法理解

### 4.6 监控 (Monitor)

* 仅管理员可见

* **无实际采集能力**：monitorService只存储外部推送数据，没有主动采集

* 用户看到"暂无监控快照"但不知道为什么没有

### 4.7 地图生成 (WorldGen)

* 表单可用

* 生成后无进度反馈

* 地图设置编辑器同样面临裸JSON编辑器的问题

### 4.8 更新检查 (UpdateCheck)

* 功能可用，两种模式（自动/手动）已实现

* 但前提是Daemon有可运行的二进制文件——对于Factorio等4款游戏，二进制尚未下载，更新功能形同虚设

## 五、功能链路断裂图

以下展示从"创建服务器"到各功能Tab的端到端链路完整性：

```
创建服务器（CreateServer.tsx）
  │
  ├─ 选择 Pack（5个英文名，无引导）         ← 断裂点1：用户不明所以
  │
  ├─ 提交 → Panel API → Daemon
  │
  ├─ Daemon bootstrap
  │   ├─ Minecraft：自动下载server.jar       ✅ 链路通
  │   │   └─ spawn → 就绪检测 → RCON连接     ✅
  │   │
  │   └─ Factorio/Palworld/ARK/Rust：写README  ← 断裂点2：4/5游戏无法自动启动
  │       └─ spawn → ENOENT → error          ❌ 启动失败
  │
  └─ 进入实例详情页
      │
      ├─ 控制台 Tab                            ✅ 界面可用，但服务器可能未启动
      ├─ 配置文件 Tab
      │   ├─ 显示文件名（英文）                 ← 断裂点3：裸JSON编辑器，无引导
      │   └─ Server未启动时文件为空              ← 断裂点4：无解释原因
      │
      ├─ Mod Tab
      │   ├─ CRUD界面可用                      ✅
      │   ├─ 依赖检测为stub                     ← 断裂点5
      │   └─ 下载不执行                          ← 断裂点6
      │
      ├─ 存档 Tab
      │   ├─ CRUD界面可用                      ✅ 
      │   └─ 激活不实际切换存档                 ← 断裂点7
      │
      ├─ 商城 Tab                              ✅ 界面可用
      │   └─ 非Minecraft物品名全英文            ← 断裂点8
      │
      ├─ 监控 Tab                              ❌ 无数据（无采集能力）
      ├─ 地图生成 Tab                          ⚠️ 可用但无进度反馈
      └─ 更新 Tab                              ⚠️ 依赖有可执行二进制
```

**8个断裂点**中，有6个是Daemon端功能缺失导致的（断裂点2/4/5/6/7 + 监控），2个是前端本地化缺失（断裂点1/8），1个是编辑器设计问题（断裂点3）。

## 六、配置规范缺失的具体表现

### 6.1 Pack配置无规范文档

* 无文档描述每个Pack字段的含义、取值范围、必填性

* `pack-template.yaml`存在于`public/config_template/`，但用户无法通过UI访问

* Pack的`commands`字段（broadcast/give\_item/kick\_player等）需要用户了解游戏命令行，但无指导

### 6.2 配置文件无格式规范

* 用户面对裸JSON不知道哪些字段必填、哪些可选

* Schema仅以技术角度展示（JSON Schema原文），没有转换为用户可理解的中文描述

* 同一游戏可能有多配置文件（Palworld有4个），用户不知道每个文件的用途和关系

### 6.3 添加新游戏无指导

如果要添加一款新游戏（如Terraria、Valheim），用户面临：

* Pack YAML格式复杂（350+行Factorio的pack.yaml），无任何逐字段说明

* `pack-template.yaml`虽有模板，但注释是英文且不充分

* 不知道`protocol.type`该选`rcon`还是`stdin`

* 不知道`ready_pattern`正则该怎么写

* 不知道`event_parsers`正则的各group含义

* 不知道`commands`里的`{{player}}`等变量有哪些可用

### 6.4 商城物品配置断裂

* 商城中添加物品时，物品名需要手动输入（没有从Pack物品列表自动补全）

* Shopify需的品质系统（`quality_tiers`）在Factorio Pack中设为0，但商城界面仍显示品质选择

* 物品价格单位不明确（点券？金币？），无货币说明

## 七、"新底座空空荡荡"的根因总结

用户感知的"空空荡荡"不是某个页面没写，而是**三个层次叠加的体验塌缩**：

### 层次一：入口层（用户看到的第一眼）

1. Pack名称全英文 → 不认识游戏
2. 创建表单无引导 → 不知道怎么填
3. 创建后无确认 → 不知道成功没有

### 层次二：功能层（进入实例后）

1. 4/5的游戏Daemon无法启动 → 控制台无输出
2. 配置文件无数据 → "暂无配置文件"
3. 存档切换不生效 → 功能看起来坏了
4. Mod依赖检测为假 → 安全假象
5. 监控无数据 → "暂无监控快照"

### 层次三：运营层（配置和管理时）

1. 配置文件裸JSON编辑器 → 不会改
2. 非Minecraft物品名全英文 → 商城不可用
3. 添加新游戏无文档 → 不敢扩展

**7/11的问题根在Daemon端功能不完整，3/11在Pack中文本地化缺失，1/11在前端编辑器设计。**

***

## 八、修复优先级建议（仅分析，不执行）

### P0（阻塞用户使用）

1. Pack `display_name` 中文化 — 改5个YAML文件，30秒
2. Factorio二进制自动下载 — Daemon `bootstrap.ts` 扩展，利用已有 `download_pattern`
3. 配置文件编辑器表单化 — 根据JSON Schema自动生成表单字段（已有Schema数据）

### P1（核心体验修复）

1. 创建服务器引导文本 — 解释Pack/端口/RCON
2. Daemon崩溃自动重启 — `manager.ts` 增加重启逻辑
3. 存档实际激活 — Daemon提供"带存档重启"能力
4. 商城物品名从Pack API读取中文 — 前端放弃静态映射表

### P2（完整性修复）

1. 日志文件持久化 — Daemon stdout写入文件
2. 监控数据采集 — scheduler + daemonClient周期性采集
3. Mod依赖检测 — 读取mod info.json
4. 添加新游戏配置指南文档
