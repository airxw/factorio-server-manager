# 经济系统改造

## 第一章：问题分析

### 问题现象

原商城系统以"VIP 能买啥"为核心，缺少价格机制与货币体系。需求方要求：

1. 给每个物品定价（price 字段）
2. VIP 改为每天获取一定点券（Points），在商城购买时扣款
3. 保留每日购买上限设置（vip_permissions.daily_limit 不变）
4. 鼓励升级 VIP（VIP 越高每日领取金额越多，阶梯式）

### 影响范围

- 后端：DB 迁移 / 数据契约 / 服务层 / 路由层
- 前端：Shop 页面 / Profile 页面 / ShopItems 管理页
- 5 个 Pack YAML 不受影响（价格是 server 级配置，不硬编码到 Pack）

### 根因分析

原 shop_items 表无 price 字段，shop_orders 无 total_price 字段，shop_order_items 无价格快照。
原 VIP 体系只有 daily_limit 概念，没有"每日领取金额"概念。
缺少钱包表（user_wallets），无法存储用户余额。

## 第二章：修复方案

### 方案描述

引入"点券（Points）"作为虚拟货币：

1. **钱包按实例作用域**：`user_wallets` 表 UNIQUE(user_id, server_id)，与 VIP 按实例绑定设计一致
2. **每日领取阶梯金额**：VIP0=100 / VIP1=200 / VIP2=400 / VIP3=800 / VIP4=1600 / VIP5=3200
3. **价格快照**：shop_order_items 保存下单时单价，防止后续改价影响历史订单
4. **扣款事务**：先扣款（原子 UPDATE WHERE balance >= amount）再创建订单，事务失败时退款
5. **保留 vip_level_required 与 daily_limit**：作为门槛与每日购买上限，与价格系统并存
6. **价格是 server 级配置**：不硬编码到 Pack YAML，由管理员通过 ShopItems 管理页设置

### 替代方案

- **方案 B（已否决）**：价格放在 Pack YAML 中作为默认值。否决理由：价格是业务配置而非物品属性，应允许每个实例独立定价
- **方案 C（已否决）**：全局钱包（不按实例）。否决理由：与 VIP 按实例绑定设计不一致，用户在 A 服的点券不应能在 B 服使用

### 风险评估

- **副作用**：原有 shop_items 数据 price 默认为 0（免费），不影响存量订单
- **退款逻辑**：事务失败时调用 walletService.refund，若退款失败仅记录日志不掩盖原错
- **原子扣款**：UPDATE ... WHERE balance >= amount 影响行数 0 即余额不足，避免并发竞态

## 第四章：预期效果

### 验证方式

使用 admin@local.dev（server_admin 角色，融合为 VIP5）登录测试：

1. **钱包查询**：GET /api/servers/:id/wallet → 返回 balance=0, can_claim_daily=true, daily_reward_amount=3200 ✅
2. **每日领取**：POST /api/servers/:id/wallet/claim-daily → balance=3200, total_earned=3200, can_claim_daily=false ✅
3. **重复领取**：再次 POST → 409 Conflict (DAILY_REWARD_ALREADY_CLAIMED) ✅
4. **上架带 price 物品**：PUT /shop-items body 含 price=100 → 返回 item.price=100 ✅
5. **下单扣款**：POST /shop-orders 买 3 个 iron-plate → order.total_price=300, items[0].price=100（快照）, wallet.balance=3200-300=2900, total_spent=300 ✅
6. **余额不足**：POST 买 30 个 iron-plate (3000 > 2900) → 400 BadRequest (INSUFFICIENT_BALANCE) ✅

### 回滚方案

- 迁移回滚：`npm run migrate:rollback`（knex 回滚最近一次迁移，删除 user_wallets 表 + 移除新增列）
- 代码回滚：git revert 本次提交（无破坏性文件操作，所有改动均为新增或追加字段）

### 经验教训

1. **shop.ts 路由的 isAdminRole 漏识别 server_admin 角色**：原实现仅识别 'admin' / 'system_admin'，导致 server_admin 无法上架物品。修复后补全 'server_admin' 识别。
2. **价格不应硬编码在 Pack YAML**：价格是业务配置，应允许每个实例独立定价。Pack YAML 仅声明物品池的可用性。
3. **事务失败退款要包 try-catch**：退款失败不应掩盖原错，仅记录日志。
4. **每日领取判断基于日期字符串**：用 YYYY-MM-DD（本地时区）判断今日是否已领，避免时区歧义。
