# 任务前提与项目实际冲突 — L3 阻塞报告

## 第一章：问题分析

### 问题现象

主线程下发子任务"前端添加用户注册入口 + 三级权限管理入口"。子任务文本声明了 3 个**与项目实际状态不一致**的前提：

1. **"后端已有 `/api/v1/auth/register` 接口（POST { email, username, password }）"** → 经 Grep 确认**不存在**。
2. **"项目已有三级权限：server_admin / instance_admin / user"** → 后端内部用 3 级，但**公共契约 `UserRole` 仍为 `admin | user` 二级**。
3. **"必要时实现创建/删除用户"** → 后端 users 路由**没有 POST/DELETE 端点**。

子任务文本同时要求"如未确认请通过 Read+Grep 确认"——子代理已按指示完成确认，三处前提**均与项目实际冲突**。

### 影响范围

- **子任务本身**（"前端添加注册入口 + 三级权限管理"）无法在不破坏契约 / 不造假闭合的前提下闭合。
- **模块间契约**：后端已通过 migration `20260714100000_migrate_roles_to_3level.ts` 完成 DB 角色 3 级化，但 `public/schema/panel-api-types.ts` 中 `UserRole` 未跟随升级，前端契约与后端存储存在漂移。
- **功能可达性**：若仅完成前端占位（无后端调用），用户访问 `/register` 后永远无法完成注册；权限管理页缺少创建/删除能力，与"三级权限管理"语义不符。

### 根因分析（按发现顺序）

#### 冲突点 ①：后端无 Web 端 register 端点

**证据**：

- `panel/backend/src/index.ts:663` 唯一显式 `app.post(...)` 路由为 `app.post('/api/auth/login', ...)`。
- `panel/backend/src/index.ts:711` 仅有 `app.get('/api/version', ...)` 与 `app.get('/api/health', ...)`。
- `panel/backend/src/index.ts:715-720` 为 `app.get('/api/auth/me', ...)`。
- 注册仅在游戏内 `!register` 命令路径：`panel/backend/src/index.ts:218-235`（`createInGameCommandService` 内部回调调用 `userService.registerFromGame`）。
- `panel/backend/src/services/userService.ts:296` 仅暴露 `registerFromGame`，无 Web 端 register 函数。
- `public/schema/panel-api-types.ts` 中**不存在** `RegisterRequest` / `RegisterResponse` / `Register` 相关类型（Grep 验证）。

**结论**：后端**未提供** Web 端 `POST /api/v1/auth/register`（或 `/api/auth/register`）端点。前端 `Register.tsx` 提交时**没有可调用的真实后端**。

#### 冲突点 ②：公共契约 UserRole 仍为二级

**证据**：

- `public/schema/panel-api-types.ts:10` `export type UserRole = 'admin' | 'user';` —— **二级**。
- `panel/backend/src/core/auth/roles.ts:12-16` `export const Role = { SERVER_ADMIN, INSTANCE_ADMIN, USER }` —— **三级**（后端内部）。
- `panel/backend/src/core/auth/roles.ts:53-55` `toContractUserRole(role: Role): 'admin' | 'user'` —— 后端**主动把 3 级降级为 2 级**返回给前端。
- `panel/backend/src/db/migrations/20260714100000_migrate_roles_to_3level.ts` —— DB 角色已升级到 3 级。
- 前端 `Layout.tsx:108-109` / `utils/role.ts:5-6` 用 `server_admin || system_admin || admin` 兼容写法，**实际能识别 3 个值**，但契约类型只允许 `admin | user`。

**结论**：
- 真实数据中**存在** `server_admin / instance_admin / user` 三种角色值（DB 已迁移）。
- 但前端 `UserRole` 类型是 `admin | user` —— 把 3 级"压缩"为 2 级，前端**无法表达** `server_admin` 与 `instance_admin` 的区分。
- 子任务要求"实现角色编辑下拉（admin / instance_admin / user 三级）"会**违反**前端契约（`UpdateUserRequest.role: UserRole`）。

#### 冲突点 ③：后端 users 路由无 POST / DELETE

**证据**：

- `panel/backend/src/api/routes/users.ts:94-153` 完整已读：仅暴露 `GET /`、`GET /:id`、`PATCH /:id`。
- `panel/backend/src/index.ts:789` `app.use('/api/users', authenticateToken, requireAdmin, createUsersRouter())` —— 路由前缀为 `/api/users`（注意：不是 `/api/v1/users`，**任务文本路径表述与项目实际不一致**）。

**结论**：后端**没有** `POST /api/users`（创建用户）和 `DELETE /api/users/:id`（删除用户）。前端 Users.tsx 即使加 UI 按钮，点击后**没有后端响应**。

### 关键判断（按 EC-7 / rules-0 §四-7.1）

1. **信息不充分** —— 子任务描述与项目实际冲突，子代理无法在不请示的情况下做"对"的实现。
2. **能力边界** —— 前端子代理无 `public/` 契约修改权（rules-4 §4.3 + 任务明确要求），无法独自修复 UserRole 二级问题；也无后端修改范围。
3. **不可逆 + 假闭合风险** —— 若按"前端能 typecheck 通过"标准交付，会留下：
   - 永远 404 的 `/api/auth/register` 调用
   - 永远 405 的 `POST/DELETE /api/users` 调用
   - 与契约不符的"三级下拉"硬编码
4. **[V] 节点** —— 注册功能 + 权限管理功能都属于核心价值判断点（rules-0 §四-5 双重闸门）。

## 第二章：修复方案（待人类裁决后选其一）

### 方案 A：先打通后端契约，再接入前端（推荐）

1. **后端子代理** 任务清单：
   - `panel/backend/src/index.ts` 新增 `app.post('/api/auth/register', ...)`（无需鉴权，复用 `userService.registerFromGame` 逻辑或新建 `register` 方法，**不入 DB game_player_name 字段**）。
   - `panel/backend/src/api/routes/users.ts` 新增 `POST /`（创建用户，需 server_admin 鉴权）和 `DELETE /:id`（删除用户，需 server_admin 鉴权）。
   - `panel/backend/src/services/userService.ts` 新增 `register` / `createUser` / `deleteUser` 方法。
2. **契约层（需主线程授权修改 `public/`）**：
   - `public/schema/panel-api-types.ts` `UserRole` 升级为 `'server_admin' | 'instance_admin' | 'user'`。
   - 新增 `RegisterRequest` / `RegisterResponse` / `CreateUserRequest` / `DeleteUserResponse` 类型。
   - 同步 `public/interface_stub/user-service.ts` 接口签名。
3. **后端路由**：`/api/auth/register` 与 users 路由都用 `requireRole(Role.SERVER_ADMIN)`（除 register 公开）。
4. **前端子代理** 后续任务清单（依赖后端契约就位）：
   - `src/api/client.ts` 新增 `register()` 与 `createUser/deleteUser`。
   - `src/api/auth.tsx` 新增 `register` 方法到 `useAuth()`。
   - `src/pages/Register.tsx` 接入 `useAuth().register`。
   - `src/components/Layout.tsx` ADMIN_LINKS 添加"权限管理"。
   - `src/pages/admin/Users.tsx` 升级角色下拉为 3 级 + 顶部说明卡片。

**优点**：契约一致 + 功能真实可用 + 严格遵守 AC 范式。
**缺点**：需主线程授权修 `public/` 契约 + 跨子代理协调（估计 +30 分钟）。

### 方案 B：前端先做无后端占位（不推荐 — 假闭合）

仅前端可见层做改动：
- Login.tsx 添加"立即注册"链接。
- App.tsx 添加 `/register` 路由。
- Layout.tsx 添加"权限管理"入口。
- Users.tsx 顶部说明卡片。
- Register.tsx **创建但提交逻辑仅弹 alert/console.warn**："注册功能待后端接入"。
- **不创建删除/新建用户按钮**（按"必要时"原则，最小占位）。

**优点**：typecheck/build 必过，子代理可独立完成。
**缺点**：
- 用户体验差（点了注册就弹个提示）。
- **明显假闭合** —— GN-004 审查必标记不合规。
- 违反"修复前必写文档"+ 不可逆锁定警告。

### 方案 C：仅做不依赖后端的部分

仅完成：
- Layout.tsx ADMIN_LINKS 添加"权限管理"。
- Users.tsx 顶部说明卡片（已有 list/update）。

**优点**：100% 可闭合，无假闭合。
**缺点**：50% 任务未完成（注册入口完全没做）。

### 方案 D：完全停止 — 等主线程重新下发任务（最保守）

按 EC-7"信息不充分"分支：当前掌握的信息不足以给出可靠实现，子代理不擅自降级或推进。挂起等待主线程。
