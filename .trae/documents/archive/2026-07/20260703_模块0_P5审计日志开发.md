# P5 Webhooks + AuditLogs 开发

## 第一章：问题分析

### 问题现象
GameServer Panel 3.0.0 平台在 P1-P4 阶段已完成核心商业化能力 + 运维管理能力，但缺少：
- Webhook 事件订阅机制（外部系统无法订阅服务器事件）
- 审计日志查询能力（管理员无法追溯操作历史）

### 影响范围
- 外部集成：第三方系统无法接收服务器事件通知
- 合规审计：缺少操作追溯能力

### 根因分析
S4 阶段最后一个子阶段 P5，负责 Webhooks + AuditLogs。本次完成 P5 全部开发与整合，标志着 S4 并行开发阶段全部完成。

## 第二章：修复方案

### 方案描述
按 AC 范式 s0203 拓扑化拆分原则，P5 拆分为两个并行 subagent：
- **subagent A**：webhookService（含 triggerTest 真实投递）+ 路由 + 前端页面
- **subagent B**：auditLogService + 路由 + 前端页面

主线程负责：
1. 公共契约扩展（panel-api-types.ts 添加 ~15 个 P5 类型 + errors.ts 添加 2 个 P5 错误类）
2. 整合 index.ts（import + 服务初始化 + app.locals + 路由挂载）
3. 整合 api/client.ts（添加 6 个 P5 API 方法）
4. 整合 App.tsx（注册 2 个新路由）
5. 整合 Layout.tsx（添加 2 个管理菜单链接）
6. typecheck 验证 + 启动验证 + curl 端到端测试

### 关键设计决策
1. **webhook_deliveries 表暂不创建**：migration 20260703000012 只创建了 webhooks + audit_logs 两张表。为保持契约与实现一致，删除了 WebhookDeliverySummary 类型。triggerTest 不持久化投递记录，只返回即时结果。后续如需投递历史追踪，可新增 migration + 类型。
2. **triggerTest 真实投递**：使用 Node 20 全局 fetch + AbortController（10s 超时），向 webhook.url 发 POST 请求，header 含 X-Webhook-Secret。返回 delivered/status_code/error 三字段。
3. **auditLogs 路由挂载在 /api/audit-logs**（全局资源，不绑定特定服务器），而非 /api/servers 下。
4. **audit_logs 表暂无数据**：审计日志的写入需要在各个业务 service 中注入 auditLogService.create。当前 P5 只实现了查询端点，写入接入属于后续增强。

### 风险评估
- triggerTest 向外部 URL 发请求：有 SSRF 风险，但当前仅 admin 可调用，且用于测试目的。后续可加 URL 白名单校验。
- audit_logs 无数据：不影响端点可用性，空列表是合法响应。

## 已知限制（非阻断，记录待后续增强）

1. **webhook_deliveries 表未创建**：triggerTest 不持久化投递记录，只返回即时结果。后续如需投递历史追踪，需新增 migration + WebhookDeliverySummary 类型。
2. **audit_logs 表暂无数据写入**：当前只实现查询端点。审计日志的写入需要在各个业务 service（如 shopService.claimOrder、userService.login 等）中注入 auditLogService.create 并调用。这属于后续增强工作。
3. **enabled 字段返回数字 1/0**：SQLite boolean 存储为 integer，返回时未强制转换为 boolean。前端 truthy/falsy 判断不受影响，但严格类型校验可能报错。后续可在 service 层用 `Boolean(row.enabled)` 转换。
4. **triggerTest SSRF 风险**：当前允许任意 URL，仅 admin 可调用。后续可加 URL 白名单或内网地址过滤。
