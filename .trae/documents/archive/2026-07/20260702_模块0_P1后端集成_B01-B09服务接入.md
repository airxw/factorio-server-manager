# P1 后端集成：B01-B09 服务接入

## 第一章：问题分析

### 问题现象
S4 P1 后端开发阶段，9 个核心服务模块（B01-B09）实现完毕但未在 Panel Backend 入口（`index.ts`）中接入，导致：
- 服务实例未初始化，无法被路由层调用
- `createTables` 仍是旧的 schema.ts 幂等创建，未切换到 Knex migrations
- shutdown 流程未清理 scheduler 定时器，存在资源泄漏

### 影响范围
- 模块0（Panel Backend 入口）
- P2-P5 后续模块依赖 P1 服务实例
- 任何调用 userService/vipService/systemConfigService 等的前端页面将无法工作

### 根因分析
P1 后端开发按 s0203 模块拆分独立实现 9 个服务，每个服务仅完成单元实现 + typecheck，未在入口集成。需要 P1 集成阶段统一：
1. 切换 DB schema 初始化方式（schema.ts → migrations）
2. 实例化所有 P1 服务
3. 注入 scheduler executor（依赖反转）
4. 挂载到 app.locals 供路由层读取

## 第二章：修复方案

### 方案描述
分 4 步在 `index.ts` 完成 P1 集成：
- **Step 1**：import 块修改——删除 `createTables` import，添加 `runMigrations` + 8 个新服务 import
- **Step 2**：替换 `await createTables(db)` 为 `await runMigrations()`
- **Step 3**：在 PackRegistry 初始化后添加 P1 服务实例化 + `scheduler.setExecutor` + 挂载 `app.locals`
- **Step 4**：shutdown 函数添加 `scheduler.destroy()`（在 daemonEventStream.close() 之前）

### 替代方案
- 直接在 index.ts 内联各服务实现 → 否决：违反 s0203 模块拆分边界
- 通过 DI 容器统一管理 → 否决：P1 阶段过重，YAGNI

### 风险评估
- app.locals 类型扩展：P1 阶段使用 any 兜底，P2 路由开发时再补 TypeScript 类型声明
- 5 个 P1 服务暂未在路由中暴露：app.locals 挂载等价于"已使用"，避免 TS6133
- migrations 替换 schema.ts：B00 已验证 migrations 可在 panel.db 上幂等执行
