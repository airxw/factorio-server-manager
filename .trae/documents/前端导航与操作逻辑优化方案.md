## 二、路径与参数错误（核心功能可用性）

### 2.1 修复 `useParams` 参数名错位

- **位置**：`src/pages/ShopOrders.tsx`、`src/pages/CdkRedeem.tsx`
- **现状**：路由定义为 `/instances/:id/shop-orders` 和 `/instances/:id/cdk-redeem`（见 `src/App.tsx` 路由表），React Router 实际返回的 params key 为 `id`。但两个文件使用 `const { serverId } = useParams<{ serverId: string }>();`，TS 泛型只影响类型推断、不影响运行时——`serverId` 恒为 `undefined`。后续 `const id = serverId ?? ''` 始终为空字符串，API 请求会落空。
- **步骤**：
  1. 将 `ShopOrders.tsx`、`CdkRedeem.tsx` 中的 `useParams<{ serverId: string }>()` 改为 `useParams<{ id: string }>()`。
  2. 同步统一变量命名为 `id`。
  3. 对照 `Shop.tsx`（已使用 `useParams<{ id: string }>()`）作为基准。
  4. 验证：访问 `/instances/<真实id>/shop-orders`、`/instances/<真实id>/cdk-redeem` 不再显示"缺少 serverId 参数"。

### 2.2 替换历史路径 `/servers/*` 为 `/instances/*`

- **位置**：
  - `src/pages/Servers.tsx`（创建按钮、行点击、详情按钮）
  - `src/pages/ServerDetail.tsx`（返回列表、删除成功后跳转）
  - `src/pages/CreateServer.tsx`（成功跳转、取消按钮）
  - `src/pages/ShopOrders.tsx`（返回详情、去商店）
  - `src/pages/Login.tsx`（默认跳转目标）
- **现状**：路由系统已统一为 `/instances/*`，但上述位置仍硬编码 `/servers/*`，依赖 `App.tsx` 的兜底重定向，造成浏览器历史栈污染。
- **步骤**：
  1. 全部硬编码 `/servers/*` 替换为 `/instances/*`。
  2. 保留 `App.tsx` 中的 `/servers/*` 重定向兜底，并在文件头注释中标明"仅用于历史链接兼容，未来版本可移除"。
  3. `Layout.tsx` 侧边栏激活态判定避免对 `/servers` 进行硬编码匹配。

### 2.3 路由参数命名统一

- **位置**：所有调用 `useParams` 的实例级子页
- **现状**：路由层使用 `:id`，但 `ShopOrders.tsx` / `CdkRedeem.tsx` 内部又将其重命名为 `serverId`。
- **步骤**：
  1. 路由层统一使用 `:id` 作为实例级动态段。
  2. 页面组件内部统一使用 `id` 变量。
  3. `Shop.tsx` 中 `serverId` / `id` 混用统一为 `id`。

### 2.4 实例详情子路由对齐 Tab

- **位置**：`src/App.tsx`（路由表）、`src/pages/ServerDetail.tsx`（TAB_LABELS、BASE_TABS、子页映射）
- **现状**：
  - `App.tsx` 仅注册了 `shop / shop-orders / cdk-redeem / player-histories / gift-claims` 五个子路由。
  - `ServerDetail.tsx` 实际渲染的 Tab 包含 `chat-triggers / player-join-settings / vote-settings / game-command-help / mods / saves / config-files / world-gen / chat-logs / update / log-files`，未在 `App.tsx` 注册独立路由。
  - `TAB_LABELS` 声明了 `players`，但 `BASE_TABS` 与默认 `ui_tabs` 中无 `players`。
- **步骤**：
  1. 移除未实际使用的 `TAB_LABELS.players`，或显式加入 `BASE_TABS`。
  2. 对每个 Tab 对应的子页：要么在 `App.tsx` 注册独立路由（带 `:id` + `?tab=`），要么仅作为内部组件渲染、严禁直接 URL 访问。
  3. 制定"内部 Tab"与"独立页面"的统一判断标准（建议：以是否能跨实例复用为标准）。
  4. 对未注册的 Tab，统一在 `ServerDetail` 内部以状态方式管理，禁止通过 `<Link>` 跳转。

### 2.5 Shop 双模式组件拆分

- **位置**：`src/pages/Shop.tsx`
- **现状**：单一组件根据 `useParams().id` 同时承担 `/shop`（聚合）和 `/instances/:id/shop`（单实例）两种视图，聚合页缺 `id` 时静默退出。
- **步骤**：
  1. 拆分为 `ShopAggregate.tsx`（`/shop`）和 `ShopInstance.tsx`（`/instances/:id/shop`）。
  2. 聚合页内 `navigate('/instances/${id}/shop', { state: { from: 'aggregate' } })` 透出上下文。
  3. 单实例页接收 `id` 校验失败时显式返回"未提供实例 ID"错误，而非静默空白。

### 2.6 注释与实际路由同步

- **位置**：所有页面文件头部注释
- **步骤**：
  1. `Dashboard.tsx` 注释"路径：/" → 改为"路径：/dashboard"。
  2. `ShopOrders.tsx` / `CdkRedeem.tsx` 注释"路径：/servers/..." → 改为"路径：/instances/:id/..."。
  3. 建立 PR 检查：路由变更时自动同步文件头注释（或用脚本扫描对账）。

### 2.7 `/servers/:serverId/*` 重定向边界保护

- **位置**：`src/App.tsx`（`ServerSplatRedirect`）
- **步骤**：
  1. 当 `serverId` 为空字符串或 `splat` 为空时，跳转到 `/instances` 而非拼成 `/instances//`。
  2. 校验 `serverId` 必须是有效格式（字母数字 + 连字符 + 下划线）。

## 三、导航结构与上下文保留

### 3.1 实例详情 Tab 状态持久化到 URL

- **位置**：`src/pages/ServerDetail.tsx`
- **步骤**：
  1. 用 `useSearchParams` 把 `activeTab` 同步到 `?tab=console` 形式。

## 四、数据流与生命周期

### 4.1 WebSocket 自动重连

- **位置**：`src/hooks/useDaemonEvents.ts`
- **现状**：`onclose`/`onerror` 仅 `setConnected(false)`，无任何重连。
- **步骤**：
  1. `onclose` 触发指数退避重连（1s, 2s, 4s, 8s, 16s, 30s 上限）。
  2. 最多重试 10 次，超过后提示用户手动刷新。
  3. 重连成功后重新发送 `subscribe` 消息并重置计数。

### 4.2 WebSocket 心跳

- **位置**：`src/hooks/useDaemonEvents.ts`
- **步骤**：
  1. `onopen` 后每 25s 发送 `{ type: 'ping' }`。
  2. 30s 未收到任何消息主动关闭并触发重连。
  3. 后端协议配套（需在 `daemon-ws-events.ts` 增加 `pong` 类型）。

### 4.3 401 触发导航到登录

- **位置**：`src/api/client.ts`、`src/components/AuthProvider`（或 `App.tsx`）
- **现状**：`onUnauthorized` 仅调用 `logout()` 清空状态，无导航动作。
- **步骤**：
  1. `onUnauthorized` 改为统一入口函数 `handleUnauthorized()`。
  2. `handleUnauthorized` 内：`logout()` + `navigate('/login', { state: { from: currentPath } })`。
  3. `navigate` 通过 `useNavigate` hook 获取，封装到 `AuthProvider` 内部。

### 4.4 统一 API 客户端

- **位置**：`src/api/client.ts`
- **现状**：`listMyBindings`、`bindInstance`、`unbindInstance`、`listInstanceBindings`、`updateBindingVip`、`reloadPacks` 是独立 fetch 函数，绕过 `request()`。
- **步骤**：
  1. 全部合并到 `PanelApiClient` 接口。
  2. 删除文件末尾独立 fetch 函数。
  3. `Profile.tsx`、`Shop.tsx`、`Packs.tsx` 改为从 `useAuth().api` 调用。

### 4.5 Layout 通知轮询改造

- **位置**：`src/components/Layout.tsx`
- **现状**：使用裸 `fetch('/api/notifications')` 与硬编码 `Authorization`，且 30s 轮询在标签页不可见时未暂停。
- **步骤**：
  1. 替换裸 `fetch` 为 `api.listNotifications()`。
  2. `document.visibilityState === 'hidden'` 时暂停 setInterval。
  3. 可见时立即补一次拉取。

### 4.6 `api.me()` 缓存与去重

- **位置**：`src/api/auth.tsx`
- **现状**：登录成功后 `setUser(res.user)`，紧接着 `useEffect` 因 token 变化再次 `api.me()`。
- **步骤**：
  1. 登录成功后 `setUser(res.user)`，且将 token + user 写入 sessionStorage。
  2. 刷新页面时优先从 sessionStorage 恢复 user，并异步 `api.me()` 校验。
  3. 避免每次 token 变化都强制重拉。

### 4.7 请求取消（AbortController）

- **位置**：所有列表/详情页 `useCallback refresh`
- **步骤**：
  1. `useEffect` 内部创建 `AbortController`。
  2. cleanup 中 `controller.abort()`。
  3. `request<T>` 接受 `init.signal` 并接入 `fetchWithTimeout`。
  4. 已被 abort 的请求不再 `setState`。

### 4.8 ServerDetail 状态双源同步

- **位置**：`src/pages/ServerDetail.tsx` + `src/hooks/useDaemonEvents.ts`
- **现状**：`displayState = liveState ?? server?.status` 同时依赖 REST 与 WS。
- **步骤**：
  1. `displayState = liveState ?? server?.status` 保留，但 `useDaemonEvents` 暴露 `state` 作为受控值。
  2. WS 断线时（`connected === false`）不覆盖 `server.status`，仅当收到事件时更新。
  3. WS 重连成功后，强制 `refresh()` 拉取一次最新状态。

### 4.9 退出登录清理业务状态

- **位置**：`src/api/auth.tsx`
- **步骤**：
  1. 登出时 `setNotice(null)`、`setWalletNotice(null)` 等业务状态依赖 `key` 变化强制重置。
  2. 或在 `Layout` 渲染时检查 `user === null` 时显示骨架屏。

## 五、表单与上下文辅助

### 5.1 端口冲突与重名校验

## 六、交互一致性（Toast / Confirm / Loading）

> 目标：所有用户操作都有可预期的反馈，反馈形式全局统一。参考 Factorio 的 `ToastContext` + `ConfirmContext` 模式，以及 Ant Design / Element Plus 的全局反馈范式。

### 6.1 全局 Toast 系统建设

- **位置**：新建 `src/context/ToastContext.tsx`
- **现状**：项目内没有统一的 Toast 机制，错误/成功反馈散落——有的页面 `setError` 显示顶部文字，有的静默，有的 `alert`。
- **步骤**：
  1. 创建 `ToastContext`，提供 `success / error / info / warning` 四个方法。
  2. 每个 Toast 支持 3 秒自动消失 + 手动关闭。
  3. 错误 Toast 附带"查看详情"展开（显示完整错误堆栈或错误码）。
  4. 最多同时显示 5 条，超出时底部追加 + 顶部移除。
  5. 在 `App.tsx` 的 `AuthProvider` 外层包裹 `ToastProvider`。
  6. 封装 `useToast()` hook。

### 6.2 全局 Confirm 对话框（Promise 化）

- **位置**：新建 `src/context/ConfirmContext.tsx`、`src/components/ConfirmDialog.tsx`
- **现状**：删除实例有时 `window.confirm`、有时行内模态、有时表单内二次确认，三种模式并存。
- **步骤**：
  1. 创建 `ConfirmContext`，提供 `confirm(options) => Promise<boolean>`。
  2. options 支持：`title / message / confirmText / cancelText / danger / type`。
  3. 危险操作（删除/停机/解绑）强制 `danger: true` 红色样式。
  4. 支持键盘 ESC 取消、Enter 确认。
  5. 支持点击遮罩关闭（可配置）。
  6. 在 `App.tsx` 包裹 `ConfirmProvider`。
  7. 替换所有 `window.confirm` 调用。

### 6.3 操作按钮 Loading 态统一

- **位置**：所有含提交操作的页面
- **现状**：部分按钮有 loading，部分没有；用户不知道点击是否生效，容易重复提交。
- **步骤**：
  1. 封装 `LoadingButton` 组件，支持 `loading / disabled / icon` 三态。
  2. 所有提交类按钮（创建、删除、保存、充值等）统一使用。
  3. 操作期间按钮置灰 + 旋转图标 + 文案变为"操作中..."。
  4. 操作成功/失败后恢复。

### 6.4 页面级加载态（骨架屏）

- **位置**：列表页、详情页
- **步骤**：
  1. 提取 `SkeletonCard` / `SkeletonTable` / `SkeletonDetail` 骨架屏组件。
  2. 首次加载数据时显示骨架屏，而非"加载中..."文字。
  3. 二次刷新不显示骨架屏，仅显示顶部进度条或静默刷新。

### 6.5 操作成功反馈标准化

- **位置**：所有数据提交操作
- **范式**：操作反馈三段式 = **loading → success toast → 结果可见**。
- **步骤**：
  1. 操作中：按钮 loading + 禁用。
  2. 成功：绿色 Toast + 文案（如"实例创建成功"）+ 3 秒自动消失。
  3. 结果：列表自动刷新 / 跳转到详情页 / 数据更新可见。
  4. 所有 API 调用的成功路径必须有 Toast（或等价反馈）。

### 6.6 操作失败反馈标准化

- **位置**：所有数据提交操作
- **步骤**：
  1. 失败：红色 Toast + 错误信息 + "重试"按钮（针对可重试的操作）。
  2. 网络错误：Toast 显示"网络异常，请检查网络连接" + 重试。
  3. 权限错误（403）：Toast 显示"无权限操作" + 联系管理员。
  4. 服务端错误（5xx）：Toast 显示"服务器错误，请稍后重试" + 错误码。
  5. 表单校验错误：字段下方红色提示，不弹 Toast。

## 七、表单与数据操作（校验/批量/撤销）

> 目标：表单操作高效、安全、可恢复。参考大厂表单范式（Ant Design Form / 飞书多维表格 / 阿里云控制台）。

### 7.1 表单即时校验 + 服务端错误映射

- **位置**：所有表单页面（`CreateServer.tsx`、`Login.tsx`、`Register.tsx`、`Profile.tsx` 等）
- **现状**：多数表单只有提交时校验，错误信息位置不统一，没有服务端字段错误映射机制。
- **步骤**：
  1. 制定校验时机规范：失焦（blur）校验必填/格式，输入（input）实时校验长度/强度。
  2. 错误信息统一显示在对应字段下方，红色小字 + 错误图标。
  3. 提交按钮在所有字段合法前置灰。
  4. 服务端返回的字段级错误（如 `{"errors": {"email": "邮箱已被注册"}}`）自动映射到对应字段下方。
  5. 服务端非字段错误显示在表单顶部红色提示条。

### 7.2 批量操作能力

- **位置**：`src/pages/Servers.tsx`、用户管理、订单管理等列表页
- **现状**：只有单实例操作，多实例场景下效率低。
- **步骤**：
  1. 列表每行加复选框，顶部加"全选"复选框。
  2. 勾选后顶部显示批量操作栏：批量启动、批量停止、批量重启、批量删除。
  3. 批量操作前使用 Confirm 对话框二次确认，显示选中数量。
  4. 批量操作结果按条目显示成功/失败统计。
  5. 支持"选中 X 项 / 共 Y 项"计数。

### 7.3 危险操作三重防护

- **位置**：删除实例、删除用户、停机、充值扣款等危险操作
- **范式**：**红色按钮 + 确认弹窗 + 输入名称二次确认**（三层防护）。
- **步骤**：
  1. 危险操作按钮使用 `danger` 样式（红色）。
  2. 点击后弹出 Confirm 对话框。
  3. 对极高风险操作（删除实例、删除用户），要求输入完整名称才能点击"确认删除"。
  4. 确认按钮在名称匹配前置灰。
  5. 删除过程中显示进度（异步删除场景）。

### 7.4 撤销 / 软删除机制

- **位置**：删除类操作
- **步骤**：
  1. 删除成功后 Toast 显示"已删除" + "撤销"按钮（5 秒内可恢复）。
  2. "撤销"调用恢复接口（后端需支持软删除或回收站机制）。
  3. 5 秒后自动执行真正删除（或标记为已确认删除）。
  4. 操作日志中记录"撤销删除"事件。

### 7.5 表单草稿自动保存

- **位置**：复杂表单页面（创建实例、配置修改等）
- **步骤**：
  1. 表单内容变更后自动保存到 `localStorage`。
  2. 页面刷新或意外关闭后，重新进入时提示"发现未提交的草稿，是否恢复？"。
  3. 提交成功后清除草稿。
  4. 用户主动"重置表单"时清除草稿。

### 7.6 配置修改预览与对比

- **位置**：实例配置、Mod 列表、系统设置等
- **步骤**：
  1. 修改配置后，保存前显示"变更预览"：列出改动字段的旧值/新值。
  2. 支持"重置为原值"按钮。
  3. 保存时二次确认变更清单。
  4. 修改历史记录（操作日志中可查最近 N 次修改）。

### 7.7 表格操作体验

- **位置**：所有列表/表格组件
- **步骤**：
  1. 行悬停显示操作按钮（编辑/删除/详情）。
  2. 右键菜单：复制 ID、查看详情、启动/停止、删除。
  3. 列宽可拖拽调整（可选）。
  4. 列显示/隐藏自定义（用户偏好保存在 localStorage）。
  5. 支持导出 CSV/JSON（数据量较大的列表）。

  1. 顶栏显示当前版本号（如 v3.0.0），点击打开版本信息弹窗。

  4. 有新版本时显示：新版本号、更新内容列表、"立即更新"按钮。
  5. 更新过程中显示进度条 + 当前步骤文字。
  6. 更新完成后 3 秒自动刷新页面。
  7. 后端需配套：检查更新接口、执行更新接口、更新状态查询接口。

## 十二、关联约束（仅本方案范围内）

以下为执行上述开发事项时**应同步遵守**的约束，不属本方案但需要提及：

1. 路由表（`App.tsx`）与 Tab 表（`ServerDetail.tsx`）必须在同一 PR 中同时修改，否则视为不合规。
2. `useParams<{ key }>` 的 key 必须与路由段 `:key` 一致，PR review 时强制对照。
3. 任何新增的跳转目标应避免引入新的 `/servers/*` 路径。
4. 任何修改 `Layout.tsx` 激活态判定的 PR，必须同时核对 `MAIN_LINKS` / `ADMIN_LINKS` 是否覆盖。
5. 涉及 `client.ts` 中独立 fetch 函数的合并，合并后需补单元测试覆盖。
6. WebSocket 协议变更（重连/心跳）必须后端配合，单独前端改动无效。
7. 全局 Toast / Confirm 作为基础设施，新增页面必须调用，不得自行实现弹窗/提示。
8. 所有表单提交操作必须有 loading 态，防止重复提交。
9. URL 状态化是强制规范：Tab、筛选、搜索、分页必须同步到 query。
10. 移动端适配与桌面端同步迭代，不得只做桌面端。
11. 可访问性要求：新增交互元素必须带 `aria-label` 或可见文本，图标按钮不例外。
12. 版本更新/操作日志等自助运维功能必须后端接口配套，前端不得裸奔。
