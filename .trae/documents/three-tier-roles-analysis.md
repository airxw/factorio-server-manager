# 三级角色视角分析报告

> 依据：`panel/backend/src/core/auth/roles.ts`、`panel/frontend/src/components/Layout.tsx`、`panel/frontend/src/App.tsx`、各路由的 `requireAdmin` / `requireInstanceAdmin` / `requireInstanceAccess` 中间件保护策略
> 对标：多租户三级权限体系（系统管理员 / 租户管理员 / 租户用户）、RBAC 角色继承与数据范围控制
> 范围：分析"三个角色想看什么、需要看什么"，并指出当前实现与行业最佳实践的差距

## 一、当前项目三级角色定义

### 1.1 角色等级（[roles.ts](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/core/auth/roles.ts#L17-L32)）

| 内部角色 | 等级 | 公共契约 UserRole | 中文 | 定位 |
|---------|------|------------------|------|------|
| `server_admin` | 3 | `server_admin` | 服务器管理员（系统管理组） | 系统总运营者，管全局资源与全局配置 |
| `instance_admin` | 2 | `instance_admin` | 实例管理员 | 实例的运营者，管实例的业务与玩家 |
| `user` | 1 | `user` | 普通用户 | 实例的消费者，玩游戏、用商城 |

历史兼容：`system_admin → server_admin`、`admin → instance_admin`、`operator/viewer → user`（[roles.ts L78-93](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/core/auth/roles.ts#L78-L93)）

### 1.2 中间件权限分层（[middleware/auth.ts](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/middleware/auth.ts)）

| 中间件 | 允许角色 | 用途 |
|--------|---------|------|
| `requireAdmin` | `server_admin` | 系统级操作（用户管理、系统配置、Pack、SSL、隧道、审计、清理） |
| `requireInstanceAdmin` | `instance_admin` + | 实例级业务配置（ Mods、配置文件、备份、聊天、投票、CDK、商店物品、VIP 权限） |
| `requireInstanceAccess` | `user`（仅自有实例）+ `instance_admin`+（所有实例） | 实例详情查看、控制台、商城购物、CDK 兑换 |

### 1.3 前端导航分组（[Layout.tsx L71-122](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/components/Layout.tsx#L71-L122)）

| 分组 | 可见角色 | 入口 |
|------|---------|------|
| 主导航（控制台 / 实例 / 版本管理 / 商城VIP / 消息 / 个人设置） | 所有登录用户 | 6 项 |
| 实例管理（VIP管理） | `instance_admin` +（非 server_admin） | 1 项 |
| 系统管理 6 分组（用户与权限 / 系统监控 / 配置管理 / 审计与日志 / 运维清理 / 业务运营） | `server_admin` 独有 | 12 项 |

## 二、系统管理员（server_admin）— 运维者视角

### 2.1 角色定位
**系统的总运营者**，关心"系统是否健康、资源是否够用、有没有人搞破坏"，**不直接干预单个实例的业务数据**（除非应急）。等价于多租户架构中的"平台管理员"。

### 2.2 想看的内容（用户主观诉求）

| 维度 | 想看什么 | 为什么想看 |
|------|---------|-----------|
| **系统健康** | CPU / 内存 / 磁盘 / 网络的实时曲线 + 历史趋势 | 担心系统挂了 / 资源耗尽 |
| **节点状态** | 所有 daemon 节点的连通性、版本、负载 | 一个节点挂了会影响一片实例 |
| **实例总览** | 全平台所有实例的运行/停止/异常状态分布 | 需要全局视图，不关心单个实例细节 |
| **告警与异常** | 崩溃熔断触发、磁盘告警、SSL 到期、证书异常 | 出事要第一时间知道 |
| **用户行为** | 谁在什么时候做了什么敏感操作（审计日志） | 出问题要能追责 |
| **资源水位** | 磁盘用量 TopN 实例、数据库大小、日志增长 | 防止某个实例把磁盘吃光 |
| **版本与更新** | 系统自身版本、Pack 版本、有无新版本可升级 | 需要主动升级而非被动等 |

### 2.3 需要看的内容（客观必需）

| 功能 | 当前是否提供 | 路由/接口 |
|------|------------|----------|
| 用户管理（CRUD、角色分配、改密、禁用） | ✅ | `/admin/users` |
| 系统底座配置 | ✅ | `/admin/system-config` |
| 面板设置（结构化） | ✅ | `/admin/settings` |
| Pack 管理 | ✅ | `/admin/packs` |
| 系统监控仪表盘（CPU/内存/磁盘实时） | ✅ v4.4.0 K1/K2 | `/admin/system-health` |
| 一键诊断 | ✅ | `/admin/system-health?tab=diagnostics` |
| 审计日志 | ✅ | `/admin/audit-logs` |
| Webhooks 管理 | ✅ | `/admin/webhooks` |
| 实例清理（磁盘回收） | ✅ | `/admin/cleanup` |
| 运维清理聚合 | ✅ | `/admin/maintenance` |
| 玩家绑定管理 | ✅ | `/admin/player-bindings` |
| 站内消息 / 通知 | ✅ | `/admin/notifications` |
| **SSL 证书状态与管理** | ✅ v4.4.0 L1 | `/api/system/ssl/*` |

### 2.4 server_admin 视角缺口

| 缺口 | 严重度 | 说明 |
|------|-------|------|
| **资源配额管理** | 🟡 中 | 无法为 instance_admin 或 user 设置"最多创建 N 个实例"、"最多用 N GB 磁盘"的配额 |
| **多租户隔离视图** | 🟡 中 | 当前 instance_admin 能看到所有实例，缺乏"按 instance_admin 分组查看其管辖实例"的运维视图 |
| **告警通道** | 🟡 中 | 异常（崩溃熔断、SSL 到期、磁盘告警）目前仅日志，无邮件/Webhook 主动推送 |
| **节点负载均衡视图** | 🟢 低 | 多节点场景下缺乏"哪个节点该分配新实例"的决策视图 |
| **操作审批流** | 🟢 低 | 敏感操作（删除实例、清空数据）无二次审批，仅靠审计日志事后追溯 |

## 三、实例管理员（instance_admin）— 服务提供者视角

### 3.1 角色定位
**实例的运营者**，关心"我的实例跑得怎么样、玩家是否满意、收入如何"，等价于多租户架构中的"租户管理员"。**核心痛点是"我管理的实例"这一边界**——当前实现是 instance_admin 能看所有实例，这与"租户管理员只管本租户"的多租户范式不一致。

### 3.2 想看的内容

| 维度 | 想看什么 | 为什么想看 |
|------|---------|-----------|
| **实例健康** | 我管理的所有实例的运行状态、CPU/内存、在线玩家数 | 一眼看出哪个实例出问题 |
| **玩家活跃度** | 每个实例的在线玩家曲线、历史玩家数、留存 | 评估实例是否值得续费/扩容 |
| **收入流水** | 商店订单、CDK 兑换、钱包消费的统计 | 评估实例的商业价值 |
| **VIP 用户** | 当前实例的 VIP 用户列表、等级、特权使用情况 | VIP 是核心用户，要重点维护 |
| **告警通知** | 实例崩溃、玩家举报、Mod 加载失败 | 出事要第一时间知道 |
| **配置概览** | 实例的关键配置（端口、版本、Mods 数、白名单数）一眼可见 | 快速定位配置问题 |
| **备份状态** | 最近一次备份时间、备份大小、是否成功 | 防止数据丢失 |

### 3.3 需要看的内容（实例详情 Tab，[ServerDetail.tsx](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/pages/ServerDetail.tsx)）

| Tab | 当前是否提供 | 说明 |

| VIP 权限 | ✅ | 实例级 VIP 配置 |
| 商店物品 | ✅ | 实例级商店物品配置 |
| 物品同步 | ✅ | 跨服物品同步 |
| CDK 兑换码 | ✅ | 实例级 CDK 配置 |
| 聊天设置 | ✅ | 聊天触发器、关键词 |
| 投票设置 | ✅ | 投票奖励配置 |
| 定时消息 | ✅ | 自动广播 |

| **游戏命令帮助** | ✅ | GameCommandHelp |

### 3.4 instance_admin 视角缺口

| 缺口 | 严重度 | 说明 |
|------|-------|------|
| **🔴 实例归属边界** | 🔴 高 | 当前 instance_admin 能看所有实例，缺乏"我管辖的实例"过滤视图。多租户语义下应只能看自己被分配的实例 |
| **🔴 收入统计仪表盘** | 🔴 高 | 缺乏跨实例的收入汇总视图（商店订单数、CDK 兑换数、钱包消费总额），目前只有单实例的明细 |
| **🟡 玩家活跃度曲线** | 🟡 中 | 单实例有在线玩家数，但缺乏跨实例的玩家活跃度对比、留存分析 |
| **🟡 备份健康度** | 🟡 中 | 缺乏"最近 N 天是否成功备份"的仪表盘，目前需要逐个实例查看 |
| **🟡 告警通道** | 🟡 中 | 实例崩溃、Mod 失败等仅控制台日志，无主动通知（邮件/Webhook/站内信） |
| **🟡 资源配额视图** | 🟡 中 | instance_admin 不知道自己能创建多少实例、用了多少磁盘 |
| **🟢 批量操作** | 🟢 低 | 缺乏"批量启停"、"批量备份"、"批量更新"操作 |

## 四、用户（user）— 消费者视角

### 4.1 角色定位
**实例的消费者**，关心"我能玩什么、我的特权是什么、怎么花钱、怎么反馈"，等价于多租户架构中的"租户用户"。**核心痛点是"消费体验"**——用户不应看到任何管理配置界面，只看到"游戏入口 + 我的资产 + 我的特权"。

### 4.2 想看的内容

| 维度 | 想看什么 | 为什么想看 |
|------|---------|-----------|
| **我的服务器** | 我能玩的服务器列表、状态、在线人数 | 决定现在玩哪个 |
| **我的 VIP** | VIP 等级、特权列表、到期时间 | 知道自己有什么权益 |
| **商城** | 可购买的物品、价格、我买过的物品 | 想花钱买东西 |
| **我的钱包** | 余额、消费记录、每日领取 | 知道自己有多少钱 |
| **CDK 兑换** | 可用 CDK、兑换记录 | 用 CDK 拿奖励 |
| **投票奖励** | 今日是否已投票、投票奖励 | 通过投票拿奖励 |
| **玩家身份** | 我绑定的游戏角色、验证状态 | 没绑定不能玩 |
| **聊天与社区** | 服务器内聊天、玩家列表 | 社交需求 |
| **我的礼包** | 可领取的礼包、领取记录 | 拿福利 |
| **个人设置** | 改密、改邮箱、绑定信息 | 账号管理 |

### 4.3 需要看的内容

| 功能 | 当前是否提供 | 路由 |
|------|------------|------|
| 控制台 Dashboard | ✅ | `/dashboard` |
| 我的实例列表 | ✅ | `/instances`（requireInstanceAccess 过滤） |
| 实例详情（Console Tab） | ✅ | `/instances/:id` |
| 商城 | ✅ | `/shop` + `/instances/:id/shop` |
| 订单记录 | ✅ | `/instances/:id/shop-orders` |
| CDK 兑换 | ✅ | `/instances/:id/cdk-redeem` |
| 个人设置 | ✅ | `/profile` |
| 玩家验证（绑定游戏角色） | ✅ | `/profile/verify` |
| 站内消息 | ✅ | `/admin/notifications` |
| 版本管理（查看可用版本） | ✅ | `/versions` |
| 玩家历史（自己） | ✅ | `/instances/:id/player-histories` |
| 礼包领取 | ✅ | `/instances/:id/gift-claims` |

### 4.4 user 视角缺口

| 缺口 | 严重度 | 说明 |
|------|-------|------|
| **🔴 我的资产聚合页** | 🔴 高 | 缺乏"我的钱包 + 我的 VIP + 我的订单 + 我的 CDK + 我的礼包"的一站式聚合页，目前要分别进入多个实例页才能查看 |
| **🔴 跨实例统一入口** | 🔴 高 | 用户绑定了多个实例时，需要逐个实例页面切换，缺乏"我绑定的所有实例"的统一视图 |
| **🟡 我的 VIP 特权详情** | 🟡 中 | 知道自己是 VIP3，但不知道 VIP3 具体有什么特权（商店折扣？聊天颜色？） |
| **🟡 消费流水** | 🟡 中 | 钱包消费记录缺乏跨实例汇总，不知道一共花了多少 |
| **🟡 投票入口** | 🟡 中 | 投票奖励配置在实例详情，但用户侧缺乏"今日可投票的实例列表"聚合 |
| **🟡 服务器推荐** | 🟢 低 | 缺乏"热门服务器"、"新开服"推荐位 |
| **🟡 玩家社交** | 🟢 低 | 无好友系统、无玩家档案页 |
| **🟢 移动端体验** | 🟢 低 | 移动端底部导航已有，但实例详情页 Tab 在小屏下可能拥挤 |

## 六、与行业最佳实践对比

### 6.1 多租户三级权限范式（参考 CSDN《多租户架构的三级权限体系》）

| 范式要素 | 行业最佳实践 | 本项目现状 | 差距 |
|---------|------------|----------|------|
| **第一级（系统管理员）** | 管系统、管租户、不管租户内部 | ✅ 符合 | — |
| **第二级（租户管理员）** | 管本租户、管内部用户、管权限规则 | ⚠️ 管所有实例，非"本租户" | 🔴 缺租户边界 |
| **第三级（租户用户）** | 仅使用分配的功能 + 仅访问自己的数据 | ✅ 基本符合 | — |
| **资源配额** | 按套餐/角色分配资源上限 | ❌ 无配额系统 | 🟡 中 |
| **数据范围控制** | 按"组织层级 + 数据范围"精细化授权 | ⚠️ 仅按 instance_id 过滤 | 🟡 中 |
| **操作留痕** | 所有管理员操作必须记录日志 | ✅ 审计日志完备 | — |
| **应急数据操作** | 通过只读接口，不直接改业务数据 | ⚠️ server_admin 可直接改 | 🟢 低 |

### 6.2 RBAC 角色继承（参考 jamesrossjr.com RBAC 指南）

| RBAC 要素 | 行业最佳实践 | 本项目现状 | 差距 |
|----------|------------|----------|------|
| **角色继承** | editor 继承 viewer，admin 继承 editor | ✅ 通过 ROLE_LEVEL 数值比较实现 | — |
| **资源范围授权** | 用户在不同 project 可有不同 role | ❌ 角色是全局的，不按实例分 | 🟡 中 |
| **权限粒度** | 细粒度操作权限（project:create / project:delete） | ❌ 仅按角色整体授权 | 🟡 中 |
| **会话约束** | 互斥角色、基数约束 | ❌ 无 | 🟢 低 |
| **服务端强制** | 每个端点必须检查权限 | ✅ 中间件强制 | — |
| **客户端隐藏** | UI 隐藏不可见功能 | ✅ Layout 角色判断 + RequireRole | — |

|----------|----------|------|

## 七、关键发现与改进方向

### 7.1 三个核心痛点

#### 痛点 1：instance_admin 的"租户边界"缺失（🔴 高优先级）
- **现象**：当前 instance_admin 能看到所有实例，包括其他 instance_admin 管辖的实例
- **影响**：无法支撑"多个服主共用一个面板"的真实业务场景
- **行业对比**：多租户架构中"租户管理员只管本租户"是硬约束
- **改进方向**：引入 `instance_owner` 或 `instance_admins` 关联表，instance_admin 只能看自己被分配的实例

#### 痛点 2：user 的"我的资产"聚合页缺失（🔴 高优先级）
- **现象**：用户要看钱包余额、VIP 等级、订单、CDK、礼包，需要逐个进入实例页面
- **影响**：用户体验差，消费路径过长
- **行业对比**：任何 C 端产品都有"我的"聚合页
- **改进方向**：新建 `/me` 或 `/dashboard/my-assets` 聚合页，整合钱包 + VIP + 订单 + CDK + 礼包

#### 痛点 3：跨实例运营仪表盘缺失（🟡 中优先级）
- **现象**：instance_admin 和 server_admin 都缺乏"跨实例"的统计视图
- **影响**：无法评估整体运营情况
- **行业对比**：运营后台标配
- **改进方向**：为 instance_admin 提供"我管辖的实例"汇总仪表盘，为 server_admin 提供"全平台"汇总仪表盘

### 7.2 角色视图理想态

#### server_admin 理想视图
```
[系统总览仪表盘]
  ├── 全平台实例状态分布（运行/停止/异常饼图）
  ├── 节点健康度列表
  ├── 系统资源曲线（CPU/内存/磁盘 24h）
  ├── 告警时间线（最近 24h）
  ├── 用户活跃度（DAU/MAU）
  └── 资源水位 TopN（磁盘用量最大的 10 个实例）

[管理功能]
  ├── 用户与权限（含角色分配、配额设置）
  ├── 系统配置（底座 + 面板 + Pack）
  ├── 系统监控（实时 + 诊断）
  ├── 审计与日志（操作日志 + Webhooks）
  ├── 运维清理（磁盘回收 + 维护模式）
  ├── 业务运营（玩家绑定 + VIP 管理）
  └── 安全管理（SSL + 隧道 + API Key）
```

#### instance_admin 理想视图
```
[我的实例仪表盘]
  ├── 我管辖的实例列表（运行状态 + 在线人数 + CPU）
  ├── 跨实例玩家活跃度曲线
  ├── 跨实例收入统计（商店订单 + CDK 兑换 + 钱包消费）
  ├── 备份健康度（最近成功备份时间）
  └── 告警通知（崩溃 + Mod 失败 + 玩家举报）

[实例详情]（仅自己管辖的）
  ├── 控制台 / 设置 / 存档 / Mods / 配置文件
  ├── 玩家管理 / 白名单 / OP / 封禁
  ├── 业务配置（商店 / CDK / VIP / 聊天 / 投票 / 定时消息）
  └── 文件管理 / 备份 / 日志
```

#### user 理想视图
```
[我的主页]（聚合页）
  ├── 我的服务器（绑定的实例列表 + 状态 + 在线人数 + 一键进入）
  ├── 我的 VIP（等级 + 特权列表 + 到期时间）

  ├── 我的 CDK（可兑换 + 已兑换）
  ├── 我的礼包（可领取 + 已领取）

[实例详情]（仅自己绑定的）
  ├── 控制台（查看日志 + 发命令）
  ├── 在线玩家列表
  ├── 商城购物入口
  ├── CDK 兑换入口
  ├── 投票入口
  └── 礼包领取入口

[个人设置]
  ├── 账号信息（用户名 + 邮箱 + 绑定状态）
  ├── 修改密码
  └── 玩家验证（绑定游戏角色）
```

### 7.3 改进优先级建议

| 优先级 | 改进项 | 价值 |
|-------|-------|------|

| 🔴 P0 | user "我的资产"聚合页（/me 或 /dashboard/my-assets） | 提升用户体验 |
| 🟡 P1 | instance_admin 跨实例运营仪表盘 | 运营决策支撑 |
| 🟡 P1 | 资源配额系统（按角色/用户分配实例数 + 磁盘配额） | 防止资源滥用 |

| 🟢 P3 | 移动端体验优化 | 移动端可用性 |
| 🟢 P3 | 服务器推荐 + 玩家社交 | 用户增长 |

## 八、结论

### 8.1 当前权限体系成熟度评估

| 维度 | 评分 | 说明 |
|------|:---:|------|
| 角色定义清晰度 | 9/10 | 三级角色 + 等级比较 + 历史兼容，定义清晰 |
| 路由层权限保护 | 9/10 | 中间件强制 + 前端 RequireRole 双层保护 |
| 功能覆盖完整度 | 8/10 | 后端 API 完备，v4.4.0 补齐 SSL/隧道/API Key |
| **多租户隔离** | **4/10** | 🔴 instance_admin 无租户边界，是最大短板 |
| **用户体验聚合** | **5/10** | 🔴 user 缺乏"我的"聚合页，instance_admin 缺乏跨实例视图 |
| 数据范围控制 | 5/10 | 仅按 instance_id 过滤，无配额、无范围授权 |
| 审计与可观测 | 8/10 | 审计日志完备，系统监控 v4.4.0 已补齐 |
| 告警与通知 | 5/10 | 仅站内信 + 日志，无主动推送 |

**综合评分：6.6/10** — 权限定义与功能覆盖优秀，但多租户隔离与用户聚合视图是核心短板。

### 8.2 核心建议

1. **短期（下个版本）**：补齐 user 的"我的资产"聚合页 + instance_admin 的跨实例运营仪表盘
2. **中期（2-3 个版本）**：引入 instance_admins 关联表实现租户边界 + 资源配额系统
3. **长期**：按实例范围授权（RBAC1 资源范围）+ 告警主动通知 + 移动端优化
