# P4 运维功能开发（Mods / Saves / Backups / Monitor / Lists）

## 第一章：问题分析

### 问题现象
GameServer Panel 3.0.0 平台在 P1-P3 阶段已完成核心商业化能力（商店/CDK/聊天/投票/玩家/定时消息），但缺少运维管理能力：
- 无法管理游戏 Mods（启用/禁用/版本）
- 无法管理存档（激活/删除）
- 无法管理备份（创建/状态机）
- 无法查看监控快照（CPU/内存/Tick/玩家数）
- 无法管理白名单/封禁列表

### 影响范围
- 服务器运维：管理员无法在 Panel 内完成日常运维操作
- 与 factorio 参考项目对比：缺少 mods/saves/backups/monitor/lists 等核心竞争力模块

### 根因分析
S4 阶段拆分为 P1-P5 五个优先级，P4 专门负责运维功能。本次完成 P4 全部 5 个子模块的开发与整合。

## 第二章：修复方案

### 方案描述
按 AC 范式 s0203 拓扑化拆分原则，P4 拆分为两个并行 subagent：
- **subagent A**：modService + saveService + backupService（3 服务 + 3 路由 + 3 前端页面）
- **subagent B**：monitorService + listService（2 服务 + 2 路由 + 2 前端页面）

主线程负责：
1. 公共契约扩展（panel-api-types.ts 添加 ~30 个 P4 类型 + errors.ts 添加 8 个 P4 错误类）
2. 整合 index.ts（import + 服务初始化 + app.locals + 路由挂载）
3. 整合 api/client.ts（添加 17 个 P4 API 方法）
4. 整合 App.tsx（注册 5 个新路由）
5. 整合 Layout.tsx（添加 5 个管理菜单链接）
6. typecheck 验证 + 启动验证 + curl 端到端测试

### 替代方案
- 单线程串行开发：被否决，效率低
- 全部由 subagent 完成：被否决，整合文件（index.ts/client.ts/App.tsx/Layout.tsx）由主线程统一修改避免冲突

### 风险评估
- subagent 间契约不一致风险：通过主线程预先扩展公共契约规避
- 整合冲突风险：subagent 不修改整合文件，主线程统一整合

## 已知契约偏差（非阻断，记录待后续对齐）

1. **MonitorSnapshotSummary.json_extra**：契约字段名为 `json_extra`（DB 列名一致），后端 service 自动 JSON.parse/JSON.stringify 转换。前端 Monitor.tsx 使用 `s.json_extra` 访问。
2. **ListMonitorSnapshotsQuery**：契约类型用 `start`/`end` 字段，但实际实现（前端 + 后端路由）用 `from`/`to`。client.ts 的 `listMonitorSnapshots` 方法参数类型使用内联 `{ from?, to?, limit? }` 而非契约类型。后续需统一契约或代码。
3. **CreateMonitorSnapshotRequest**：契约无 `timestamp` 字段，后端始终使用 `now()` 作为 timestamp。
4. **DeleteListEntryResponse**：契约为 `{ player_name, deleted }`（含 player_name），实现已匹配。
5. **req.user.userId**：JWT 中间件设置的字段名为 `userId`（非 `id`），listService 的 create 方法已正确读取。
