## 二、安全加固任务（S1-S10）

### S1：Helmet 安全头中间件
- 在 `panel/backend/src/index.ts` 顶部 import `helmet from 'helmet'`
- 在 `app.use(cors(...))` 之前挂载 `app.use(helmet())`（Helmet 必须在所有路由之前）
- 配置项：`contentSecurityPolicy: false`（避免破坏 React 内联样式，CSP 后续版本再细化）、`crossOriginEmbedderPolicy: false`
- 保留 HSTS / X-Frame-Options / X-Content-Type-Options / Referrer-Policy 默认值
- 验证：`curl -I http://192.168.5.14:3000/api/health` 响应头包含 `X-Frame-Options: SAMEORIGIN` 等

### S2：Rate Limiting 中间件
- 新建 `panel/backend/src/middleware/rateLimiter.ts`
- 导出三个限流器工厂函数：
  - `createAuthLimiter()`：5 次/15 分钟（按 IP），针对 `/api/auth/login`、`/api/auth/register`
  - `createCdkRedeemLimiter()`：10 次/小时（按 IP + 用户 ID），针对 `/api/cdk-redeem`
  - `createGlobalLimiter()`：50 次/秒（按 IP），挂载到全局
- 使用 `express-rate-limit` 库（若已用 Koa 则改用 `koa-ratelimit`，需先确认 Panel 是否仍为 Express）
- 超限返回 HTTP 429 + `{ error: 'RATE_LIMITED', retry_after: <秒> }`
- 在 `index.ts` 全局挂载 createGlobalLimiter；在 auth/cdk-redeem 路由内单独挂载对应限流器
- 验证：连续 6 次 POST /api/auth/login 第 6 次返回 429

### S3：密码强度校验
- 在 `panel/backend/src/api/routes/auth.ts` register 路由（约 index.ts:1101）插入前置校验
- 复用 `modules/模块13_用户安全/passwordService.ts` 中的 zxcvbn 评分逻辑
- 校验规则：长度 ≥ 8 + 必含字母与数字 + zxcvbn score ≥ 2
- 失败返回 400 + `{ error: 'WEAK_PASSWORD', suggestions: [...] }`
- 同步在 `panel/frontend/src/pages/Register.tsx` 前端实时校验：显示强度条 + 不满足规则时禁用提交按钮
- 同步 S13 初始化向导第 2 步管理员密码校验规则（`panel/backend/src/api/routes/settings.ts` 的 POST /api/init）

### S4：密码找回流程
- 新建 `panel/backend/src/api/routes/passwordReset.ts`
- 新建迁移 `panel/backend/src/db/migrations/20260728000000_create_password_resets.ts`：
  - 表 `password_resets`：`id` TEXT PK / `user_id` TEXT FK / `token_hash` TEXT / `expires_at` TEXT / `used_at` TEXT NULL / `created_at` TEXT
  - 索引：`idx_password_resets_token_hash`、`idx_password_resets_user_id`
- 路由：
  - `POST /api/auth/password-reset/request`：接收 email，生成 token（crypto.randomBytes(32)），存 token_hash（sha256），发邮件（含 `https://<site>/reset-password?token=xxx`），无论用户是否存在均返回 200（防止账号枚举）
  - `POST /api/auth/password-reset/confirm`：接收 token + new_password，校验 token 有效性 + 密码强度（复用 S3），更新密码（复用 passwordService.updatePassword 但跳过 old password 校验），标记 token used_at
- token 有效期 1 小时，使用后立即失效
- 前端新建 `panel/frontend/src/pages/PasswordReset.tsx`：
  - 路由 `/forgot-password`：输入邮箱提交
  - 路由 `/reset-password`：读取 `?token=` 参数，输入新密码 + 确认，提交
  - 两个页面均为公开路由，在 App.tsx 注册
- 在 Login.tsx 添加"忘记密码？"链接 → `/forgot-password`

### S5：注册邮箱验证
- 新建 `panel/backend/src/api/routes/emailVerify.ts`
- 新建迁移 `panel/backend/src/db/migrations/20260728000001_create_email_verifications.ts`：
  - 表 `email_verifications`：`id` TEXT PK / `user_id` TEXT FK / `token_hash` TEXT / `expires_at` TEXT / `verified_at` TEXT NULL / `created_at` TEXT
- users 表新增字段 `email_verified` BOOLEAN DEFAULT 0：新建迁移 `20260728000002_add_email_verified_to_users.ts`
- 路由：
  - `POST /api/auth/email-verify/request`：登录用户可主动重发验证邮件
  - `POST /api/auth/email-verify/confirm`：接收 token，校验后 UPDATE users SET email_verified=1
  - `GET /api/auth/email-verify/status`：返回当前登录用户的 email_verified 状态
- register 流程修改：注册成功后自动发送验证邮件
- login 流程修改：若 `registration.require_email_verify` 设置为 true 且用户 email_verified=0，返回 `{ error: 'EMAIL_NOT_VERIFIED', verify_url_hint: '/verify-email' }`
- 在 settingSchemaService 新增设置项 `registration.require_email_verify`（默认 false，公网部署时管理员可开启）
- 前端新建 `panel/frontend/src/pages/EmailVerify.tsx`：路由 `/verify-email`，显示"验证邮件已发送"提示 + 重发按钮 + 验证成功跳转

## 三、灾备与运维任务（D1-D4）

### D1：数据库自动备份 scheduler
- 在 `panel/backend/src/services/scheduler.ts` 新增任务类型 `DB_BACKUP`（若 v3.6.0 已有 BACKUP 则区分命名）
- 新建 `panel/backend/src/services/dbBackupService.ts`：
  - `backupDatabase()`：使用 SQLite `.backup()` API（better-sqlite3）或 `cp panel.db panel.db.bak.<timestamp>`（Knex 驱动判断）
  - 备份位置：`${DATABASE_URL}.backup/<yyyy-mm-dd-HHMMSS>.db`
  - 保留策略：默认 7 天滚动，通过 `backup.db_retention_days` 配置
  - `cleanupOldBackups(retentionDays)`：删除超过 retention 的备份文件
- 在 settingSchemaService 新增设置项 `backup.db_enabled`（默认 true）/ `backup.db_retention_days`（默认 7）/ `backup.db_schedule_cron`（默认 '0 3 * * *' 每日 3 点）
- 在 `index.ts` 注册 DB_BACKUP scheduler executor
- 首次执行延迟 60s（避开 v3.6.0/v3.6.2/v3.8.0 已占用的 10/15/20/25/30/35s 启动期时间窗）

### D2：磁盘空间监控告警
- 在 `panel/backend/src/services/scheduler.ts` 新增任务类型 `DISK_SPACE_MONITOR`
- 新建 `panel/backend/src/services/diskMonitorService.ts`：
  - `checkDiskUsage()`：调用 `df -B1 /` 解析磁盘使用率（复用 v3.6.1 nodes.ts 已有的 df 解析逻辑）
  - 阈值：85% 触发 warning 通知，95% 触发 critical 通知
  - 通知方式：调用 `notificationService.createNotification({ user_id: <所有 server_admin>, level: 'warning'|'critical', title: '磁盘空间告警', message: '当前使用率 XX%' })`
  - 去重：同一级别 4 小时内不重复通知（在 system_config 表记录 `disk_monitor.last_notify_<level>_at`）
- 调度：每小时执行一次，首次执行延迟 45s
- 在 settingSchemaService 新增设置项 `disk.monitor_enabled`（默认 true）/ `disk.warning_threshold`（默认 85）/ `disk.critical_threshold`（默认 95）

### D3：备份恢复文档化
- 新建 `docs/ops-manual.md`：
  - 第一章：数据库备份恢复流程（手动恢复步骤 + 演练记录模板）
  - 第二章：代码回滚流程（基于 deploy.sh `update --rollback`）
  - 第三章：实例备份恢复流程（基于 backupService）
- 包含演练记录模板：演练时间 / 执行人 / 备份来源 / 恢复目标 / 耗时 / 结果 / 备注
- 包含常见问题 FAQ：备份文件损坏 / 恢复后版本不一致 / 备份目录权限

### D4：故障 Runbook 文档
- 新建 `docs/troubleshooting.md`：
  - 场景 1：Daemon 不可达（fetch failed / ECONNREFUSED）—— 排查 systemd status / 端口 / .env DAEMON_TOKEN 一致性
  - 场景 2：数据库失败 —— 排查 panel.db 文件权限 / 磁盘空间 / 迁移状态
  - 场景 3：磁盘满 —— 排查 instances/versions/backups 目录大小，引导使用运维清理页
  - 场景 4：实例启动失败 —— 排查 install_command 日志 / SteamCMD 路径 / 端口冲突 / Java 版本
