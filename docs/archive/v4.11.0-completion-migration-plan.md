# v4.11.0 收尾与三基座承接旧业务迁入执行方案

## 背景与方向决策

- bug1.md / bug2.md 诊断结论：v4.11.0 当前为假闭合。三个核心模块（后端 asset_service、前端 commercial、daemon execution_engine）均为"有代码、有单测、零接线"的孤岛；7 处运行时版本源仍为 4.10.1；三基座子路由空挂；新旧路由分裂。
- 假闭合根因：闭合判据为"单测通过 + build 通过"，GN-004 审查与 s0602 扫描均未校验"模块是否接入运行时"。
- **方向决策（已确认）**：三基座（`/admin`、`/store`、`/guild`）承接旧业务迁入，作为新主壳；旧控制台 `<Layout>` 下的近 50 个业务页逐步迁入对应基座。

## 旧业务页 → 三基座 迁入映射（建议）

| 基座 | 承载职责 | 迁入的旧页面 |
|------|---------|-------------|
| `/admin` (AdminLayout) | 系统管理 + 商业化后台 | dashboard(作 index)、users、system-config、settings、system-health、packs、player-bindings、audit-logs、webhooks、notifications、cleanup、maintenance、quotas、platform、ssl、tunnel、api-keys、nodes、instance-vip、operations、commercial/* |
| `/store` (StoreLayout) | 商城与资产消费 | shop、instances/:id/shop、shop-orders、cdk-redeem、me(我的资产)、versions |
| `/guild` (GuildLayout) | 玩家社交与服务器发现 | friends、discover、players/:userId、profile、profile/verify、profile/alerts、instances(服务器浏览/加入入口) |

> 映射为建议方案，迁入实施前需逐页确认归属，存在跨基座引用的页面以主职责归属为准。

### 三、孤岛模块接入运行时

11. 后端 asset_service 接入：在 [routes-registry.ts](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/routes-registry.ts) 注册 asset/commercial REST 路由（CRUD + Merge + UGC），在 services-init 注入 AssetService 实例，暴露 `/api/admin/assets/*` 端点并加 `requireAdmin` 门控。

### 四、旧业务页迁入三基座

16. 按映射表分批迁移：系统管理类页面迁入 `/admin/*`，商城资产类迁入 `/store/*`，玩家社交 / 发现类迁入 `/guild/*`；每批迁完即配置旧路径重定向。
17. 迁移时为每个页面套对应基座 Layout（替代旧 `<Layout>`），保留页面内部逻辑不动，仅替换外壳与菜单归属。
18. 实例详情页（`/instances/:id` 及其子 Tab）需明确归属：建议作为 `/admin/servers/:id` 或保留独立路径但纳入 `/admin` 基座导航，避免与服务器浏览入口冲突。
19. 迁移完成后移除旧 `<Layout>` 下已迁出的路由注册，保留重定向路由；最终旧 `<Layout>` 仅保留过渡期必要的兼容入口，或整体废弃。

## 关键建议

- **渐进式迁入**：旧业务页分批迁入，每批迁完即构建 + 验证，避免再次出现"一次性替换近 50 个路由"的破坏性操作（bug1.md 教训）。
- **保留旧路径重定向**：所有迁出路径配置 301，保证外部链接与用户书签在过渡期可用。
- **先接线后迁业务**：步骤三（孤岛接入）必须在步骤四（业务迁入）之前完成，确保新基座已有真实能力承接业务，而非空壳。
- **闸门前置**：步骤五的质量闸门修复建议在步骤三开始前先完成判据升级，使后续每一步接入都按新判据校验，而非事后补扫。
- **不可逆操作授权**：涉及 public/ 契约变更（如 commercial_config.schema.json 扩展）须走 s0601 契约变更流程并经人类显式授权；涉及删除旧 `<Layout>` 路由须确认无残留引用后再执行。
