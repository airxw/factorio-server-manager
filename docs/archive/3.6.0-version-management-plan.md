# v3.6.0 版本规划：存储清理统一治理（版本池 + 实例 + 日志死代码激活）

> 本文档为 v3.6.0 的方案规划，仅包含开发事项与执行步骤，不区分优先级、不计人力工期。
> 本版本核心主题：**存储清理统一治理**——统一修复三处"删 DB 不删磁盘"或"清理代码未激活"的同根问题。
> 涉及的核心页面：
> - `http://gsp.ecsrz.com:3000/versions` —— 版本管理页（核心增强）
> - `http://gsp.ecsrz.com:3000/admin/cleanup` —— 实例清理页（同步修复）
> 涉及的后端服务：
> - `panel/backend/src/api/routes/versions.ts`
> - `panel/backend/src/api/routes/cleanup.ts`
> - `panel/backend/src/services/chatLogService.ts` + `scheduler.ts`
> 关联数据表：`game_versions` / `servers` / `chat_logs`

## 一、背景与目标

### 1.1 背景

当前系统存在**三处同根问题**——"删除/清理只走 DB 层，磁盘文件成孤儿"或"清理代码写了但从未被调用"。三者分散在不同路由/服务，但本质都是存储生命周期不完整：

| # | 位置 | 现状 | 危害 |
|---|------|------|------|
| 1 | `/versions` DELETE（[versions.ts:315](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/api/routes/versions.ts#L315)） | 只删 DB 行，不删 `download_path` 指向的磁盘文件 | ARK 20GB 版本变孤儿，多次重装耗尽节点磁盘 |
| 2 | `/admin/cleanup` confirm-delete（[cleanup.ts:143](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/api/routes/cleanup.ts#L143)） | 只删 DB 行，不删 `instance_root` 目录 | 实例删除后 20GB 目录残留，用户完全无感知 |
| 3 | `chatLogService.cleanupOldLogs`（[chatLogService.ts:178](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/services/chatLogService.ts#L178)） | service 方法写了，但 scheduler / index.ts 从未注册调用 | chat_logs 表永久累积，查询越来越慢 |

此外，VersionsPage 前端 UI 缺三件事：
- `file_size_bytes` 字段表结构已存在（[migration:15](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/db/migrations/20260718000000_create_game_versions.ts#L15)），但下载完成时**未回填**
- 已下载版本表格**未渲染大小列、未渲染删除按钮**——DELETE 接口存在但前端没调用
- 缺"被实例引用时禁用删除按钮"的 UX 防护（仅后端报 409）

### 1.2 目标

本版本聚焦存储清理的"全链路闭环"，分三个目标域：

**目标域 A：版本池闭环（/versions）**
- 可见：每个已下载版本显示真实磁盘占用（字节 + 人类可读）
- 可删：前端有删除按钮，server_admin 角色可见
- 真删：删除时同时清理 DB 记录 + 磁盘文件，避免"DB 删了磁盘还在"
- 防误删：被实例引用时禁用删除按钮 + 提示引用数，而非允许点击后报错
- 可感知：删除前弹确认框，明示"将释放 X GB 磁盘"

**目标域 B：实例清理闭环（/admin/cleanup）**
- 同步修复 confirm-delete 缺磁盘清理的问题（与目标域 A 共用同一套路径白名单 + daemon rm 公共函数）
- 删除实例前清 `instance_root` 目录
- 删除成功后返回 `freed_bytes`，前端 toast 显示释放空间

**目标域 C：日志清理激活（chat_logs）**
- 激活 `chatLogService.cleanupOldLogs` 死代码——在 scheduler 注册每日定时任务
- 按 Pack 的 `chat_log.retention_days` 自动清理过期记录
- 不做前端页面（v3.7.0 再上 `/admin/maintenance` 聚合页）

## 三、执行步骤

### 3.1 后端：下载完成时回填 `file_size_bytes`

**位置**：`panel/backend/src/api/routes/versions.ts` 的 `executeVersionDownload()` 函数

**当前问题**：[versions.ts:450-462](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/api/routes/versions.ts#L450-L462) 的 insert 语句未包含 `file_size_bytes` 字段。

**改动事项**：
1. 在 `daemonClient.execCommand(curl ...)` 完成后，立即调用 daemon exec 统计下载结果大小：
   - 单文件（`server-jar` / `binary`）：`stat -c %s <download_path>` → 字节数
   - 目录（`steamcmd`）：`du -sb <download_path>` → 字节数（取第一列）
2. 解析 daemon exec 的 stdout，转成 integer
3. 在 `db('game_versions').insert({...})` 时带上 `file_size_bytes: parsedSize`
4. stat/du 失败时：`file_size_bytes: null`，不阻断下载流程（降级策略），但写日志告警
5. daemon exec 加超时（10s），避免大目录 du 卡死

**建议**：
- 封装一个 `getFileSize(daemonClient, nodeId, path, isDir)` 辅助函数
- 同步在 `downloadProgressStore` 中更新 `phase: 'completed'` 时附上 `file_size_bytes`，便于前端进度查询时一并拿到

### 3.2 后端：DELETE 接口补磁盘清理

**位置**：`panel/backend/src/api/routes/versions.ts` 的 `DELETE /:packId/versions/:versionId` 路由

**当前问题**：[versions.ts:315](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/api/routes/versions.ts#L315) 只删 DB 行，不删磁盘文件。

**改动事项**：
1. 查询 `game_versions.download_path`，得到待删除路径
2. **路径白名单硬校验**（防穿越攻击）：
   - download_path 必须以 `instances/_versions/<pack_id>/<version>/` 结尾
   - 必须是绝对路径（`path.isAbsolute()`）
   - 不允许包含 `..`
   - 校验失败直接 500 + 告警日志，不执行删除
3. 调 daemon exec `rm -rf <download_path>`：
   - 命令：`rm`，参数：`['-rf', download_path]`
   - 超时：60s（大目录可能慢）
4. 校验 daemon exec 退出码：
   - 成功 → 继续 DB 删除
   - 失败 → 不删 DB，返回 500 + 错误信息（保证一致性：DB 删了磁盘没删 ≠ 磁盘删了 DB 没删，但前者更糟——文件成孤儿）
5. DB 删除成功后返回 `200 + { deleted: true, freed_bytes: <原 file_size_bytes> }`
6. 异常路径：daemon exec 失败但文件已部分删除 → 记录告警，建议人工介入

**建议**：
- 在响应中返回 `freed_bytes`，前端可在 toast 中显示"已释放 20.3 GB"
- 删除流程全程写日志（请求者、版本、路径、字节数、耗时），便于审计
- 考虑加 `cleanup_in_progress` 内存锁（防并发删除同一 versionId），同一 versionId 第二次请求返回 409

### 3.9 后端：抽取公共"安全删除目录"服务（目标域 A+B 共用）

**位置**：`panel/backend/src/services/safeRemoveService.ts`（新增）

**理由**：3.2（versions DELETE）和 3.8（cleanup confirm-delete）都需要做"路径白名单 + daemon exec rm + 错误处理"，抽公共函数避免重复。

**改动事项**：
1. 新建 `safeRemoveService.ts`，导出：
   ```ts
   interface SafeRemoveOptions {
     daemonClient: DaemonClient;
     nodeId: string;
     targetPath: string;
     pathPattern: RegExp;       // 路径白名单正则
     timeoutMs?: number;        // 默认 60_000
   }
   interface SafeRemoveResult {
     success: boolean;
     freedBytes: number | null;  // 失败时为 null
     error?: string;
   }
   async function safeRemoveDirectory(opts: SafeRemoveOptions): Promise<SafeRemoveResult>
   ```
2. 内部流程：
   - 校验 `targetPath` 是否绝对路径、是否匹配 `pathPattern`、不含 `..`
   - 调 daemon exec `du -sb <path>` 拿到字节数（10s 超时，失败时 freedBytes = null 但不阻断）
   - 调 daemon exec `rm -rf <path>`（60s 超时）
   - 返回 `{ success, freedBytes, error? }`
3. versions DELETE 和 cleanup confirm-delete 都调用此服务

**建议**：
- 路径白名单正则作为参数传入，不写死——versions 和 cleanup 的白名单不同
- 此服务不依赖任何业务表，纯函数式，便于单测
- 单测覆盖：合法路径、非法路径（`/etc`、`..`、相对路径）、daemon rm 成功/失败、du 失败但 rm 成功等场景

       for (const s of servers) {

     }
   });

## 五、安全与边界校验

### 5.1 路径白名单（DELETE 接口）

**强制校验**（[versions.ts](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/api/routes/versions.ts) DELETE 路由）：

```ts
const ALLOWED_DELETE_PATTERN = /^\/.+\/instances\/_versions\/[a-z0-9-]+\/[^/]+\//;
const downloadPath = row.download_path;
if (!ALLOWED_DELETE_PATTERN.test(downloadPath) || downloadPath.includes('..')) {
  // 拒绝删除，返回 500 + 告警
}
```

**校验失败时的处理**：
- 不执行 rm
- 不删 DB
- 返回 `500 + { error: { code: 'PANEL_PATH_VALIDATION_FAILED', message: 'download_path 不符合白名单' } }`
- 写 error 级日志，包含请求者 userId、versionId、可疑路径

### 5.2 并发删除锁

同一 versionId 的并发 DELETE 请求可能导致 daemon exec 重复执行。建议加内存锁：

```ts
const deletingVersions = new Set<string>();
if (deletingVersions.has(versionId)) {
  return res.status(409).json({ error: { code: 'PANEL_VERSION_DELETING', message: '该版本正在删除中' } });
}
deletingVersions.add(versionId);
try { ... } finally { deletingVersions.delete(versionId); }
```

**注意**：此锁是进程内锁，不支持多实例 Panel 部署。当前单 Panel 部署够用。多实例场景需上 Redis 分布式锁，超出 v3.6.0 范围。

### 5.3 daemon exec 超时

- stat / du：10s
- rm -rf：60s（大目录可能慢，特别是机械硬盘节点）

超时后：
- stat/du 超时：file_size_bytes 置 null，不阻断下载完成流程
- rm 超时：返回 500 + 提示"删除超时，请人工检查节点磁盘"，**不删 DB**——让用户重试或人工处理

### B.1 当前实例详情页问题

**位置**：[panel/frontend/src/pages/ServerDetail.tsx](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/pages/ServerDetail.tsx)

**问题清单**：

1. **顶部信息卡片不可折叠**（[L414-458](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/pages/ServerDetail.tsx#L414-L458)）
   - 9 行 info-row 平铺（状态 / 游戏 / Pack / 版本 / 游戏端口 / RCON端口 / 节点 / 归属者 / 创建时间）
   - 桌面端尚可，移动端占满近一屏，要往下滚才能看到 Tab
   - 信息密度低——每行只占一字段，无主次区分

2. **Tab 全部平铺，无语义分组**（[L460-496](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/pages/ServerDetail.tsx#L460-L496)）
   - 当前有 13 个 Tab 候选：console / shop-admin / chat-triggers / player-join-settings / vote-settings / game-command-help / mods / saves / config-files / world-gen / chat-logs / players / update / log-files
   - 按 Pack 的 `ui.tabs` 声明动态渲染，但只是平铺一长条
   - 移动端 Tab 条横向滚动，超过 6 个 Tab 后用户难以定位
   - 无主次区分——"控制台"和"投票设置"在视觉上等权重，但前者是高频核心，后者是低频管理

3. **无"启动必要 vs 启动后可改"的语义区分**
   - 例如"world-gen 地图生成"只在首次启动前有意义，启动后基本不再用，但与"config-files"平级
   - "update 服务端版本"在 running 状态下应禁用，但视觉上与其他 Tab 等同
   - "saves 存档管理"在 stopped 状态才有意义，但与其他 Tab 一样平铺

4. **无"状态跟踪 vs 配置管理 vs 业务运营"的语义区分**
   - 状态跟踪类：console / chat-logs / players / log-files（启动后高频查看）
   - 启动配置类：config-files / world-gen / update（启动前/停止时操作）
   - 运行管理类：saves / mods（运行中也可改，但有风险）
   - 业务运营类：shop-admin / chat-triggers / player-join-settings / vote-settings / game-command-help（业务侧管理）
   - 这四类在 UI 上完全平铺，用户认知负担大

### B.2 重构方案讨论（v3.7.0 候选）

#### 方案 A：顶部信息卡片折叠 + Tab 分组（推荐）

**信息卡片改造**：
- 默认折叠为一行摘要：`状态徽章 + 游戏名 + 版本 + 端口`——`运行中 · Minecraft · 1.21.4 · 25565`
- 点击展开后显示完整 9 行信息
- 移动端默认折叠，桌面端可记忆展开状态（localStorage）

**Tab 按语义分组**，用分组标题或 Tab Group 组件实现：

```
┌─ 运行时（高频，启动后常用）─────────────┐
│ [控制台] [聊天日志] [玩家历史] [日志文件]  │
└───────────────────────────────────────┘
┌─ 配置（启动前/停止后）────────────────┐
│ [配置文件] [地图生成] [服务端版本]       │
└───────────────────────────────────────┘
┌─ 运维（运行中也可改但有风险）──────────┐
│ [存档管理] [Mod 管理]                  │
└───────────────────────────────────────┘
┌─ 业务运营（管理员可见）───────────────┐
│ [商店管理] [聊天触发] [加入设置] [投票] [命令帮助] │
└───────────────────────────────────────┘
```

**状态相关的 Tab 联动**：
- `update` 在 running 状态下隐藏或禁用 + tooltip "请先停止实例"
- `world-gen` 在 running 状态下隐藏（避免误操作覆盖存档）
- `saves` 在 running 状态下显示警告条 "运行中操作存档有风险"
- `config-files` 在 running 状态下显示警告条 "修改后需重启生效"

#### 方案 B：左侧导航树替代 Tab 条

适合 Tab 数量爆炸的场景（>15 个），但本项目 13 个 Tab 还在 Tab Group 可承载范围。**不推荐**，会增加一次导航跳转，违背"详情页一屏内完成主要操作"原则。

#### 方案 C：保留平铺 Tab，仅做信息卡片折叠

最小改动，但未解决"Tab 平铺无分组"的核心问题。**不推荐**。

### B.3 移动端体验专项

当前移动端的问题：
1. Tab 条横向滚动，13 个 Tab 滚动距离过长
2. 顶部信息卡片占满首屏，用户每次进入都要先下滑
3. Tab 切换后内容区无 loading 骨架屏（已有，确认是否覆盖全部 Tab）

**移动端建议**：
- 顶部信息卡片默认折叠
- Tab 分组在移动端用"折叠式抽屉"——点击分组标题展开该组 Tab，避免横向滚动
- 或者用"底部固定操作栏"——把"启动/停止/删除/控制台"4 个高频操作放底部，释放顶部空间
- Tab 切换支持左右滑动手势（[L13 useSwipe](file:///home/airxw/Documents/gsp/gameserver-panel/panel/frontend/src/pages/ServerDetail.tsx#L13) 已有，确认是否生效）

### B.5 数据契约层面需要补的元数据

当前 pack.yaml 的 `ui.tabs` 只是字符串数组：

```yaml
ui:
  tabs: [console, config-files, ...]
```

需要扩展为对象数组，支持分组和状态约束：

```yaml
ui:
  tabs:
    - id: console
      group: runtime          # runtime / config / ops / business
      order: 1
      require_state: []       # 空=任何状态可见
    - id: world-gen
      group: config
      order: 2
      require_state: [stopped]  # 仅 stopped 状态可见
    - id: update
      group: config
      order: 3
      require_state: [stopped]
    # ...
```

**向后兼容**：字符串数组形式仍支持（降级为 group=runtime, order=默认）。pack-schema.ts 的 `InstanceTabSchema` 需扩展为 union 类型。
