## Slide 1 — 行业痛点

### 1.1 行业现状

游戏私服/游戏服务器租赁是一个**长期存在但被忽视的中型市场**：

- 仅 Minecraft 一款游戏，全球就有数十万活跃服主
- 头部面板 Pterodactyl 累计下载量超千万
- 服主群体从硬核运维爱好者，正在向"小生意人"演变——他们关心的不是 `systemd`，而是"这个月能赚多少"

### 1.2 现有方案的局限

| 竞品 | 定位 | 缺什么 |
|------|------|--------|
| **Pterodactyl** | 开源运维面板（PHP + React） | 没有商业化层，服主还得自建 Tebex 等外挂商店 |
| **AMP (CubeCoders)** | 商业运维面板（Windows/.NET 跨平台） | 闭源、按实例数收费，依然停在"管服务器" |
| **LinuxGSM** | 脚本化管理工具 | 没有面板，更没有商业化 |
| **PufferPanel** | 轻量开源面板 | 功能薄，无商业化设计 |
| **Tebex** | 反向——只做商业化 | 不管服务器，服主需要双套系统 |

### 1.3 真实痛点：三方都被卡住

游戏私服生态有**三方都在痛**，根子在于"钱流动不起来"：

| 角色 | 痛点 | 后果 |
|------|------|------|
| **服主** | **为爱发电**——开服要自掏腰包买服务器、花时间维护，但没有变现渠道 | 烧不起钱就关服，社区流失 |
| **玩家** | **有钱没地方消费**——想支持服主、想要特权道具，但没有正规充值渠道 | 只能去灰色平台买 CDK，被骗风险高 |
| **平台方** | **赚不到增长红利**——现有面板只卖工具收订阅费，服主赚多赚少和面板无关 | 市场萎缩，平台收不到钱 |

**根因**：行业缺的不是"又一个面板"，而是**一个让交易发生的市场**——让服主能赚钱、让玩家能消费、让平台能从增长里分成。传统面板（Pterodactyl/AMP）只解决"如何管理服务器"，不解决"如何让钱流动起来"。

**结论**：行业需要一套"**创造三方共赢市场**"的商业化操作系统——服主帮平台运营，服主赚钱了平台才能赚钱。

## Slide 2 — 解决方案：B2B2C 三角

### 2.1 三角角色模型

GSP 把游戏私服生态抽象成**供应链—零售商—消费者**三角：

```
        系统管理员（平台方）
            ▲
          供应链
        ▼       ▼
   全局资产     算力资源
   标品库
        ▼       ▼
  实例管理员 ← 普通用户（玩家）
   （服主）    充值消费
   改价即营业
```

- **系统管理员（平台方 = 供应链）**：提供算力资源 + 预设游戏变现"标品"（全局资产库）。一个管理员可同时支撑 N 个服主。
- **实例管理员（服主 = 零售商）**：一键继承平台标品，零代码改价即可开门营业；高阶用户可用指令沙箱做 UGC，支持冷门 Mod 的深度变现。
- **普通用户（玩家 = 消费者）**：纯粹的"自助充值门户"，账号绑定 → 充值 → 物品/特权自动下发一气呵成。

### 2.2 差异化定位

| 维度 | 传统面板 | GSP |
|------|---------|-----|
| 核心问题 | 如何管理服务器 | **如何帮服主赚钱** |
| 用户模型 | 单一管理员 | **三角角色（平台/服主/玩家）** |
| 商业化 | 无 | **内置商店/CDK/VIP/提现** |
| 多游戏支持 | 每游戏硬编码 | **Pack YAML 配置驱动** |
| 安全 | 命令字符串拼接 | **RCON 指令沙箱** |
| 集群扩展 | 单机或手工 | **Panel-Daemon 主从集群** |

### 2.3 评委会问

> Q：B2B2C 听起来很美，但平台到底怎么赚钱？
> A：平台是**市场制造者（market-maker）**，不是收割者——让服主从"为爱发电"变成"可持续经营"，让玩家从"有钱没处花"变成"有地方消费"。平台从增长的市场里分一杯羹：卖服务器给服主（VPS 预付费）+ 服主提现抽成。**服主帮平台运营，服主赚钱了平台才能赚钱。** 详见 Slide 4.3 三方共赢模型。

## Slide 4 — 市场与目标用户

### 4.1 目标用户画像

| 角色 | 典型画像 | 付费意愿 | 核心诉求 |
|------|---------|---------|---------|
| **平台方** | 游戏 IDC、私服联盟、社区站长 | 高（按节点付费） | 多租户、可扩展、能管 N 个服主 |
| **服主** | 小团队/个人站长（1-3 人） | 中（按实例付费） | 一键开业、零代码、能赚钱 |
| **玩家** | 游戏社区成员 | 低（按消费付费） | 自助充值、即时到账、特权可见 |

### 4.2 市场规模（粗略）

- **TAM**：全球游戏服务器托管市场，2025 年规模约 $20-30 亿（含 IDC + 自建）
- **SAM**：可被商业化面板替代的部分，约 $5-8 亿
- **SOM**：私服生态 + 中文社区 + 中小 IDC，三年内可达 $50-100M

### 4.3 商业模式：创造三方共赢的市场（最精彩的部分）

GSP 的商业本质不是"卖工具收订阅费"，而是**创造一个让交易发生的市场**——让服主从"为爱发电"变成"可持续经营"，让玩家从"有钱没处花"变成"有地方消费支持服主"，平台从增长的市场里分一杯羹。

#### 三方共赢模型

```
   ┌─────────────────────────────────────────────────┐
   │  服主：从「为爱发电」→「可持续经营的小商家」        │
   │  • 平台提供算力（VPS 式预付费）                    │
   │  • 平台提供变现工具（商店/CDK/VIP/物品自动下发）     │
   │  • 平台提供资金通道（提现码审批）                   │
   └─────────────────────────────────────────────────┘
                          ↓
              服主能赚钱 → 持续投入 → 服务质量↑
                          ↓
   ┌─────────────────────────────────────────────────┐
   │  玩家：从「有钱没处花」→「有地方消费支持服主」       │
   │  • 自助充值门户（账号绑定 + 自动下发）              │
   │  • 特权/道具/VIP 即时到账                          │
   │  • 资金安全（平台余额 + 提现审批，告别灰色 CDK）     │
   └─────────────────────────────────────────────────┘
                          ↓
              玩家愿意消费 → 服主收入↑ → 平台分一杯羹
                          ↓
   ┌─────────────────────────────────────────────────┐
   │  平台：从「卖工具收订阅」→「从增长交易里分成」       │
   │  ① 卖服务器给服主（VPS 预付费）                     │
   │  ② 服主提现抽成（资金通道费）                       │
   │  ③ Pack 市场抽成（未来）                           │
   └─────────────────────────────────────────────────┘
```

#### 三条收入流

| 收入流 | 谁付钱 | 模式 | 落地状态 |
|--------|--------|------|---------|
| ① **服务器销售** | 服主 → 平台 | VPS 式预付费：按实例类型（micro/small/medium/large/xlarge）× 周期（月/季/半年/年）× 折扣 | 已落地（v4.29.x 系列） |
| ② **提现分成** | 服主 → 平台 | 服主从玩家赚的钱提现时，平台抽成（提现码审批流 + 7 天过期自动退费） | 已落地（v4.29.0） |
| ③ **Pack 市场抽成** | 开发者 → 平台 | 社区开发者上传 Pack，平台抽 10-15% | 未来规划 |

#### 关键洞察：这不是零和博弈，而是市场创造

传统面板的逻辑是"**存量博弈**"——平台收订阅费，服主自费运营，玩家不消费。这是一个**萎缩的市场**：服主烧不起钱就关服，玩家流失，平台收不到钱。

GSP 的逻辑是"**市场创造**"——平台赋能服主赚钱，服主能赚钱就会持续投入，玩家有消费渠道就会留存，平台从增长的交易里分一杯羹。这是一个**增长的市场**：

- 服主从玩家赚到钱 → 有动力持续运营 → 服务质量提升 → 玩家留存
- 玩家消费体验好 → 留存率上升 → 服主收入增长 → 服主扩实例
- 服主收入增长 → 扩实例 + 提现 → **平台两条收入流都增长**

**核心结论**：**服主帮平台运营，服主赚钱了平台才能赚钱。** 平台不是收割者，而是**市场制造者（market-maker）**——让原本不存在的交易发生，从新创造的价值里分一杯羹。

#### 类比

GSP 不是"又一个面板"，而是**游戏私服生态的 YouTube + Shopify**：

- **YouTube** 让创作者从广告分成赚钱（创作者不再为爱发电）
- **Shopify** 让小商家零代码开店（商家不再被技术门槛卡住）
- **GSP** 让服主从"为爱发电"变成"可持续经营"（服主不再烧钱关服）

#### B2B2C 的本质

| 层 | 谁→谁 | 交易 |
|----|-------|------|
| B2B | 平台→服主 | 卖算力 + 提供变现工具 + 资金通道 |
| B2C | 服主→玩家 | 卖商品/特权/道具 |
| 平台分成 | 服主→平台 | 提现抽成 + Pack 抽成 |

平台不直接碰 C 端，而是**赋能 B 端（服主）服务 C 端（玩家）**，从 B 端的增长里分一杯羹。这才是 B2B2C 的本质——不是平台两头赚，而是**平台让交易发生，然后从增长里分成**。

### 4.4 评委会问

> Q：提现分成这种模式，会不会有监管风险（二清/资金池）？
> A：当前实现是**提现码审批流**——玩家充值进入服主平台余额（不是直接进入服主银行账户），服主发起提现申请生成提现码，平台人工审批后线下打款，平台抽成在余额层完成（不触碰真实资金流）。这是国内私服生态最常见的安全做法，资金不沉淀在平台账户，规避二清风险。未来规模化后可接入持牌支付通道。

### 5.1 Panel-Daemon 双层架构

```

                       │ HTTPS
                       ▼
┌─────────────────────────────────────────────────┐

└─────────────────────────────────────────────────┘

                       ▼
┌─────────────────────────────────────────────────┐

│   22 services / 20 routes / 29 tables             │
└─────────────────────────────────────────────────┘
                       │ Bearer Token + WS
                       ▼
┌─────────────────────────────────────────────────┐
│  Daemon Node (127.0.0.1:8080, 公网禁用)            │

└─────────────────────────────────────────────────┘
                       │
                       ▼
              游戏进程（Minecraft/Palworld/...）
```

### 5.2 三大技术护城河

#### 护城河 1：Pack 配置驱动

新增一款游戏只需写一份 `pack.yaml`，业务代码零改动：

```yaml
# packs/minecraft-vanilla/pack.yaml 节选
pack:
  id: minecraft-vanilla
  display_name: 我的世界 Java版 (原版)
startup:
  command: java -Xmx{max_memory} -jar server.jar
  stop_command: stop
protocol:
  type: rcon
  default_port: 25575
business:
  shop:
    give_command: 'give {{player}} {{item}} {{count}}'
  cdk:
    redeem_command: 'give {{player}} {{item}} {{count}}'
  lists:
    whitelist_add: 'whitelist add {{player}}'
```

**结果**：12 款游戏开箱即用（Minecraft / Factorio / Palworld / ARK / RUST / DST / Terraria / Valheim / Zomboid 等），新增游戏的边际成本趋近于零。

#### 护城河 2：RCON 指令沙箱

`daemon/src/modules/execution_engine/ExecutionEngine.ts` 中的 `IExecutionEngine` 实现：

```typescript
async execute(server, command, context) {
  // 1. 安全性检查：防止 RCON 注入攻击
  if (context?.type === 'rcon') {
    const sanitized = this.sanitizeRconCommand(command);
    if (sanitized !== command) {
      this.logger.warn(`Command sanitized: ${command} -> ${sanitized}`);
      command = sanitized;
    }
  }
  // 2. 服务状态校验
  // 3. 按 Pack.protocol 分流到 RCON / stdin
}
```

所有用户自定义命令必须经沙箱白名单过滤，这是 Tebex 等外挂商店做不到的——他们只能信任服主输入。

#### 护城河 3：主从集群架构

- **Master 节点**：Panel 本机自带，零配置可用
- **Slave 节点**：通过邀请码 + 部署脚本一键注册到 Panel，WebSocket 长连接保活
- **横向扩展**：一台 Panel 可管理 N 台物理机的游戏实例，Slave 节点无状态无业务

## Slide 6 — 开发方法论：14 天 107 个版本

### 6.1 这是路演中最重要的一张

**14 天（2026-07-16 → 2026-07-29）**

**107 个版本（v3.2.0 → v4.32.0）**

**1 个开发者 + 1 套 AI 多智能体协作规范**

平均每天 **7-8 个版本**，每个版本都包含：方案文档 → spec 三件套 → 实现 → 独立审查 → 三重测试闸门 → 部署验证 → note 闭合。

### 6.2 8 阶段流水线（S0-S7）

每个功能版本都按以下流水线推进，**单向不可逆**：

```
S0 需求分析 → S1 多方案对抗 → S2 契约冻结 [V] → S3 模块化拆分
→ S4 并行开发 → S5 契约校验 → S6 合流交付 [V] → S7 运维变更
```

- `[V]` = 价值判断节点，触发**双重闸门**：独立审查 + 人类裁决（不可跳过）
- 上游产出物冻结后禁止回溯修改，强制走 s0601 契约变更流程

### 6.3 EC-7 信号协议

LLM 在每个判断性输出前必须执行 `ec7_self_check`，把"开放判断"改造成"选择题"或"判断题"：

| 级别 | 触发条件 | 行为 |
|------|---------|------|
| **L1** | 常规进度、闭合、无漂移 | 写 note，不打断人类 |
| **L2** | 阶段切换、里程碑 | NotifyUser（状态+决策+下一步+风险） |
| **L3** | 价值判断、架构分叉、不可逆锁定 | AskUserQuestion（必须给 2-4 个选项） |

**核心约束**：人类不填空，LLM 给选项。需要人类输入才能继续的节点，LLM 必须主动构筑选择/判断题。

### 6.4 GN-004 独立审查能力

任何 spec/plan 在 NotifyUser 之前必须硬性插入独立审查（不可由主 agent 自扮）：

```python
def spec_plan_gn004_gate():
    # GN-004 由 general_purpose_task 承载，prompt 注入审查 rubric
    gn004_result = launch(subagent_type="general_purpose_task",
                          role="independent_review", ...)
    result = handle_gn004(gn004_result)
    # 阻断→fix→rerun；警示放行→ask_user；通过→proceed
    assert result in ("通过", "警示放行且已处理")
    NotifyUser(file_paths=[spec_path, tasks_path, checklist_path])
```

**最少调用计数**：Spec/Plan 交付前 1 次 + 每个关键检查点 1 次 + 交付前 1 次 ≥ 3 次。

### 6.5 s0402 三重测试闸门

任何前端变更必须依次通过（顺序固定，不可跳关）：

1. **Test1 单测**：核心逻辑单元测试（如 290/290 PASS）
2. **Test2 E2E**：关键路径端到端全链路（Playwright）
3. **Test3 Mock 回归**：UI 层 Mock 模式回归验证

任何一项失败必须修复或获人类显式豁免，**禁止将"缺测试"自动视为"通过"**。

### 6.6 三层契约 + public/ 保护

- **数据契约**：`public/schema/` JSON Schema + zod 运行时校验 + ajv 元校验
- **接口契约**：`public/interface_stub/` TypeScript .d.ts 存根（27 个服务接口）
- **配置契约**：`public/config_template/` JSON Schema

`public/` 目录是契约的物理载体，**不是代码库的可变部分**——任何删除/修改/覆盖/移动操作必须先经人类显式授权，**不存在"零引用即可删除"的例外**。在工具调用路径上由 `ec7_action_gate` 强制执行。

### 6.7 Subagent 调度台账

任何涉及 subagent 调度的 Plan/Spec 必须包含独立的执行台账表：

| 字段 | 说明 |
|------|------|
| 阶段标签 | 与 tasks.md 中 Task 编号对应 |
| `[P]` 组 | 并行组标记 |
| subagent_type | 统一用 `general_purpose_task` |
| actual agent id | 真实拉起 ID |
| 第二落点 | 结论/产物落盘锚点路径 |
| 失败回退点 | 失败时回退到的已完成检查点 |
| 状态 | 待启动/进行中/已完成/失败 |

## Slide 8 — 关键决策点案例

### 8.1 决策案例 1：v4.14.1 配色全面 Apple 化

**背景**：v4.14.0 之前 UI 混用紫/粉/橙等"杀马特电竞色"。

**决策**：用户偏好苹果清新科技风，明确反对电竞配色。

**执行**：v4.14.1 一次性移除所有紫/粉/橙，统一为蓝青清新科技风，后续所有 UI 改动均按此基线。

**沉淀**：写入项目规则（[`.trae/rules/1.md`](../.trae/rules/1.md)）："主体颜色不建议使用深色配色"——成为永久约束。

### 8.2 决策案例 2：v4.19.0 Schema 基线重置

**背景**：Demo 期积累了 58 个 migration，历史包袱沉重。

**决策**：Demo 期结束，合并抛弃历史包袱，归档 58 个 migration，创建基线脚本 `20260808000000_baseline_v4_post_demo.ts`。

**风险**：现有生产库需要识别为"健康存量库"，不能误清洗。

**执行**：deploy.sh 适配健康存量库识别 + 新增 `npm run db:clean-demo` 数据清洗脚本。

**沉淀**：rules-0 §四-13「运行时接入闭合判据」——v4.11.0 假闭合事件（asset_service/execution_engine/commercial 等孤岛代码未接入运行时）直接沉淀为永久规则。

### 8.3 决策案例 3：v4.27.0 实例级绑定迁移

**背景**：玩家绑定从 `scope_type='game_type'`（跨实例全局）改为 `scope_type='instance', scope_ref=server_id`（实例级）。

**影响面**：28 项（20 项 P0 必须立即同步 + 5 项 P1 测试同步 + 3 项 P2 文档留痕）。

**流程**：s0601 契约变更适配 + GN-004 独立审查（3 轮，含 5 阻断 + 2 软阻断 + 数字同步修复）+ 人类授权全部落位 public/。

**结果**：生产库旧 game_type 绑定物理删除（不可逆），验证 0 条残留。

### 8.4 决策案例 4：v4.29.13 配额管理简化

**背景**：v4.28.0 全员服主后，role 级配额失效；v4.29.x VPS 预付费上线后，max_instances 失去意义。

**决策**：禁用实例/玩家配额，仅保留磁盘配额。

**保留**：public/ 契约层字段（受 rules-0 §四-10 保护）、resource_quotas 表结构、games.max_instances_per_user 系统配置——方便未来恢复。

**沉淀**：注释保留 + 恢复路径标注 `[v4.29.13 DISABLED]`。

### 8.5 决策案例 5：v4.29.0 经济体系整合 + 提现码审批（资金闭环落地）

**背景**：B2B2C 商业化需要"玩家充值→服主余额→提现→平台抽成"完整资金链路，但 v4.28.x 之前只有商店/CDK 单点功能，没有统一钱包、没有提现流程、没有平台抽成机制。

**决策**：v4.29.0 一次性落地**双货币模型 + 提现码审批流**：

- **双货币**：全局余额（钱包，跨实例通用）+ 实例点券（实例内消费）
- **积分/VIP**：区间等级，按消费累计
- **提现码**：服主发起提现 → 生成提现码 → 平台审批 → 线下打款 + 平台抽成在余额层完成
- **7 天过期自动退费**：避免长期挂账
- **统一交易流水**：所有资金变动可审计

**落地**：8 个经济 migration + 6 个经济服务 + 4 个每日定时任务（CDK_REFUND_SCAN / WITHDRAW_EXPIRE_SCAN / INTEGRAL_DAILY_DECAY / VIP_SUBSCRIPTION_SCAN）+ 前端 UserCenter/WithdrawApprovals/InstanceEconomyConfig 页面。

**风险防护**：v4.29.3 追加钱包异常扫描（单日大额流入 >200000 / 负余额 / CDK 批次 1h 兑换率 >80% 三规则）+ CDK 批量限流（单次 ≤100、每日 ≤1000）。

**这是资金闭环商业模式的物理实现**——不是 PPT 上的箭头，是真实跑在生产上的 6 个服务 + 4 个定时任务 + 完整审批流。
