# v4.13.0 实例详情页拆分与 GM Workbench 后端接入方案

## 一、背景

v4.12.0 完成了三层操作逻辑的核心目标（三基座差异化 + 角色门控上提 + 平台大盘），但以下三项因属于独立的大规模重构或需契约变更授权，未在 v4.12.0 内完成，遗留至 v4.13.0：

1. **`/instances/:id` 实例详情页未按角色拆分**：当前所有角色共享同一套 `ServerDetail` 组件，子 Tab 通过内部门控兜底，但路由层门控未上提，且信息架构未按角色差异化。
2. **GM Workbench 新增页面为占位**：`/store/players`、`/store/reports/revenue`、`/store/reports/playtime`、`/store/servers` 四个页面在 v4.12.0 中仅创建占位组件，后端 API 未接入。
3. **Instance_Assets 契约未扩展 Banner 字段**：Player Portal 的"服主自定义 Banner"功能依赖 `instance_assets` 表扩展 `banner_url` 等字段，属 `public/` 契约变更，需走 s0601 流程 + 人类授权。

## 二、目标

1. **实例详情页三视图拆分**：`/instances/:id` 拆分为 `/admin/servers/:id`（系统管理员）、`/store/servers/:id`（服主）、`/guild/servers/:id`（玩家）三套视图，按角色渲染不同信息架构。
2. **GM Workbench 后端 API 接入**：实现玩家列表（CRM）、流水报表、时长统计、服主实例列表四个后端 API，替换前端占位页。
3. **Instance_Assets 契约扩展**：新增 `banner_url`、`banner_link`、`shop_description` 等字段，支持服主自定义店铺外观。
4. **旧 `/instances/*` 路由清理**：迁移完成后保留 301 重定向，移除旧路由注册。

## 三、执行步骤

> 不区分优先级，不计人力工期，仅列开发事项与建议。

### 一、Instance_Assets 契约扩展（需人类授权）

1. **契约变更申请**：按 s0601 适配契约变更流程，向人类提交 `instance_assets` 表扩展申请，包含字段清单、类型、默认值、影响范围。
2. **数据契约扩展**（⚠️ 受保护路径，执行前必须经 `ec7_action_gate` 拦截并获人类显式授权）：在 `public/schema/panel-api-types.ts` 的 `GlobalAssetDto` / `InstanceAssetDto` 中新增字段：
   - `banner_url?: string` — 服主店铺 Banner 图片 URL
   - `banner_link?: string` — Banner 点击跳转链接
   - `shop_description?: string` — 服主店铺描述文案
   - `shop_theme_color?: string` — 服主店铺主题色（HEX）
3. **数据库迁移**：新增 migration `add_instance_assets_shop_fields`，为 `instance_assets` 表添加上述字段（均可空，默认 null）。
4. **配置契约更新**（⚠️ 若涉及 `public/config_template/`，执行前必须经 `ec7_action_gate` 拦截并获人类显式授权）：在 `public/config_template/` 下更新相关配置模板（如涉及）。
5. **Mock 同步**（⚠️ 受保护路径，执行前必须经 `ec7_action_gate` 拦截并获人类显式授权）：按 s0202 更新 `public/pre_generated_mock/` 下的 Mock 实现，返回包含新字段的模拟值。
6. **AssetService 扩展**：在 `panel/backend/src/modules/asset_service/asset_service.ts` 中扩展 CRUD 方法支持新字段。
7. **前端 AssetApi 扩展**：在 `panel/frontend/src/api/modules/asset.ts` 中扩展类型定义和方法签名。

### 二、实例详情页三视图拆分

8. **`/admin/servers/:id` 系统管理员视图**：
   - 承载：实例配置、Daemon 状态、部署命令、系统监控、玩家历史（player-histories）、审计日志。
   - 门控：`server_admin+`。
   - 信息架构：系统监控导向，强调资源占用、日志、配置变更历史。
   - 实现：新建 `pages/admin/ServerDetailAdmin.tsx`，从现有 `ServerDetail` 提取系统管理相关 Tab。
9. **`/store/servers/:id` 服主视图**：
   - 承载：商业化控制台（business）、VIP 管理、运营数据、店铺外观配置（Banner/描述/主题色）。
   - 门控：`instance_admin+`。
   - 信息架构：店铺后台导向，强调商品管理、玩家 CRM、收入数据。
   - 实现：新建 `pages/store/ServerDetailStore.tsx`，从现有 `ServerDetail` 提取服主相关 Tab。
10. **`/guild/servers/:id` 玩家视图**：
    - 承载：店铺首页（Banner + 描述 + 主题色）、商品列表（shop）、卡密兑换（cdk-redeem）、订单（shop-orders）、礼包领取（gift-claims）。
    - 门控：`user+`。
    - 信息架构：C 端电商导向，强调商品浏览与消费，屏蔽所有运维信息。
    - 实现：新建 `pages/guild/ServerDetailGuild.tsx`，从现有 `ServerDetail` 提取玩家消费相关 Tab。
11. **共享子组件抽离**：将 `ServerDetail` 中可复用的子组件（如实例基本信息卡片、商品列表、订单表）抽离到 `components/server-detail/` 下，三套视图按需组合。**使用 `React.lazy` + `Suspense` 懒加载策略**，确保三套视图按路由分割，避免整体打包（GN-004 H24 补强）。
12. **旧 `/instances/:id` 重定向**：
    - `/instances/:id` → 按角色重定向到对应视图（`server_admin → /admin/servers/:id`、`instance_admin → /store/servers/:id`、`user → /guild/servers/:id`）。
    - `/instances/:id/shop` → `/guild/servers/:id/shop`
    - `/instances/:id/shop-orders` → `/guild/servers/:id/shop-orders`
    - `/instances/:id/cdk-redeem` → `/guild/servers/:id/cdk-redeem`
    - `/instances/:id/business` → `/store/servers/:id/business`
    - `/instances/:id/player-histories` → `/admin/servers/:id/player-histories`
    - `/instances/:id/gift-claims` → `/guild/servers/:id/gift-claims`
13. **旧 `/instances` 列表重定向**：
    - `/instances` → 按角色重定向（`server_admin → /admin/servers`、`instance_admin → /store/servers`、`user → /guild`）。
    - `/instances/new` → `/store/servers/new`（仅服主可创建）。
14. **路由层门控上提**：
    - `/admin/servers/*` → `server_admin+`
    - `/store/servers/*` → `instance_admin+`
    - `/guild/servers/*` → `user+`
    - 移除旧 `/instances/*` 路由注册（保留重定向）。

### 三、GM Workbench 后端 API 接入

15. **玩家列表（CRM）API**：
    - 端点：`GET /api/store/players?instance_id=xxx&page=1&limit=20&search=xxx`
    - 返回：玩家列表（用户名、绑定游戏 ID、累计消费、在线时长、VIP 等级、状态）。
    - 实现：在 `panel/backend/src/api/routes/` 下新建 `store-players.ts`，从 `users` + `player_bindings` + `shop_orders` + `vip_users` 表聚合（直接操作 Knex `db` 实例，不需要 services 注入）。
16. **玩家操作 API**：
    - 端点：`POST /api/store/players/:userId/compensate`（发放补偿）、`POST /api/store/players/:userId/ban`（封禁）、`POST /api/store/players/:userId/adjust-playtime`（调整时长）。
    - 实现：复用现有 `commandDispatcher` + `executionEngineClient` 投递 RCON 指令。
17. **流水报表 API**：
    - 端点：`GET /api/store/reports/revenue?instance_id=xxx&days=30`
    - 返回：按日聚合的收入数据（日期、订单数、收入、CDK 兑换数）。
    - 实现：从 `shop_orders` + `cdk_redemptions` 表聚合（直接操作 Knex `db` 实例，不需要 services 注入）。
18a. **player_sessions 表 migration**（daemon 写入链路前置）：
    - 新增 migration `create_player_sessions_table`，创建 `player_sessions` 表。
    - Schema：`session_id`(PK) / `player_user_id`(FK→users) / `instance_id`(FK→instances) / `join_at`(datetime) / `leave_at`(datetime nullable) / `duration_seconds`(integer)。
    - 闭合判据：migration 文件存在 + `knex migrate:latest` 通过。
18b. **daemon 玩家加入/离开事件写入逻辑**（防假闭合关键步骤）：
    - 订阅 daemon 现有玩家事件总线或 RCON join/leave 事件，在玩家加入时 INSERT、离开时 UPDATE `leave_at` + `duration_seconds`。
    - **此步骤为 v4.11.0 假闭合教训的直接补强**：仅建表+API 而无 daemon 写入，API 查询将永远返回空数据，构成孤岛代码。
    - 闭合判据：`grep -rn "player_sessions" daemon/src/` 确认写入链路存在 + daemon 单测覆盖 join/leave 写入。
18c. **时长统计 API**：
    - 端点：`GET /api/store/reports/playtime?instance_id=xxx&days=30`
    - 返回：按日聚合的玩家时长数据（日期、活跃玩家数、总时长、平均时长）。
    - 实现：从 `player_sessions` 表按日聚合（直接操作 Knex `db` 实例，不需要 services 注入）。
    - 闭合判据：路由文件存在 + 路由聚合器挂载 grep + 数据源 grep `player_sessions`。
19. **服主实例列表 API**：
    - 端点：`GET /api/store/servers`
    - 返回：当前服主拥有的实例列表（实例 ID、名称、游戏类型、状态、在线玩家数、今日收入）。
    - 实现：从 `instances` 表按 `owner_user_id` 过滤，关联 `operations` 数据（直接操作 Knex `db` 实例，不需要 services 注入）。
20. **前端 API client 扩展**：在 `panel/frontend/src/api/client.ts` 中新增上述 API 方法。
21. **前端页面实现**：替换 `StorePlayers`、`StoreReportsRevenue`、`StoreReportsPlaytime`、`StoreServers` 四个占位页为真实数据页面。
22. **路由门控**：所有 `/api/store/*` 端点门控 `instance_admin+`，通过 `requireRole` 中间件校验。

### 四、Player Portal 店铺化呈现

## 四、范围边界

- 本方案仅拆分实例详情页 + 接入 GM Workbench 后端 API + 扩展 Instance_Assets 契约，不涉及底层 AssetService / ExecutionEngine 的业务逻辑重写。
- 不破坏现有数据契约，新字段均为可选（默认 null），保证向后兼容。
- 旧路径重定向保留，保证外部链接与用户书签在过渡期可用。
- Instance_Assets 契约扩展必须走 s0601 流程并经人类显式授权，不得由 LLM 自行编辑 `public/schema/` 下的任何文件。

## 五、风险与建议

- **实例详情页拆分影响面大**：`ServerDetail` 是当前最复杂的页面（738KB bundle），拆分为三套视图需谨慎，建议先抽离共享子组件，再分别实现三套视图，每步构建验证。
- **玩家时长统计依赖 `player_sessions` 表**：如该表不存在，需新增 migration 创建，并确保 daemon 在玩家加入/离开时写入数据。
- **服主店铺主题色动态应用**：需考虑 CSS 变量动态注入，避免影响其他店铺或全局样式。
- **契约扩展需授权**：`public/schema/panel-api-types.ts` 属受保护路径，扩展前必须通过 `ec7_action_gate` 拦截并获人类授权。
- **旧路径重定向保留期**：建议至少保留到 v4.14.0，给用户充足的迁移时间。
- **数据库迁移风险**（GN-004 H23 补充）：`instance_assets` 表扩展 + `player_sessions` 新建可能影响现有数据，执行前必须备份生产环境到 `backup/v4.13.0-pre-refactor-{date}/`（参考 v4.12.0 备份实践）。
- **daemon 写入链路回归风险**（GN-004 H23 补充）：daemon 新增 player_sessions 写入逻辑可能与现有玩家事件处理逻辑冲突，需回归测试现有玩家加入/离开流程。
- **前端 bundle 拆分风险**（GN-004 H23 补充）：三套视图拆分后，共享子组件抽离不当可能导致 bundle 反而变大（循环依赖、重复打包）。需设定 bundle size 目标 < 300KB/视图。
- **移动端视口守卫风险**（rules-0 §3.1.6，GN-004 H23 补充）：Player Portal 的 Banner 占顶部 ≥30% 视口高度，禁止使用 `height: 30vh` 强制，应使用 `min-height: 30vh` 或 `height: 30dvh`。
- **React Router v6 路由结构守卫风险**（rules-0 §3.1.1，GN-004 H23 补充）：三套视图拆分涉及大量路由重组，`<Routes>` 直接子元素只能为 `<Route>` 或 `<React.Fragment>`，`<Suspense>` 必须在 Layout 内包裹 `<Outlet />`。
- **角色门控审计文档更新风险**（GN-004 H23 补充）：v4.13.0 完成后须更新门控审计文档，记录 `/admin/servers/*`、`/store/servers/*`、`/guild/servers/*` 门控清单。

## 六、依赖 DAG 与并行策略

> 遵循 rules-0 §四-4：MAX_PARALLEL_PER_BATCH=2，MAX_PARALLEL_GLOBAL=3。每个 [P] 组附并行理由与失败回退点。

### 阶段一：契约扩展（步骤 1-7）

```
步骤1(契约变更申请[V]) ──阻塞──→ 步骤2(数据契约)
                                      │
                            ┌─────────┼─────────┐
                            ▼         ▼         ▼
                     [P1]步骤3   步骤5      步骤4
                      (迁移)    (Mock)    (配置模板)
                            │
                            ▼
                        步骤6(AssetService)
                            │
                            ▼
                        步骤7(前端API)
```

- **[P1] 步骤3 + 步骤4**（迁移 + 配置模板）：两者仅依赖步骤2，互不依赖。失败回退：回退到步骤2完成检查点，重做迁移或模板。

### 阶段二：实例详情页拆分（步骤 8-14）

```
步骤11(共享子组件抽离) ──→ [P2]步骤8 + 步骤9 ──→ 步骤10 ──→ 步骤12 ──→ 步骤13 ──→ 步骤14
                          (Admin视图)  (Store视图)  (Guild视图)  (重定向)   (列表重定向)  (门控上提)
```

- **[P2] 步骤8 + 步骤9**（Admin + Store 视图）：三套视图信息架构独立，Admin 强调系统监控、Store 强调店铺后台，无共享状态。失败回退：回退到步骤11完成检查点。
- 步骤10（Guild 视图）：构建依赖步骤11（共享子组件），可与 [P2] 并行启动构建；功能完整 E2E 验证依赖阶段一 `banner_url` 字段（字段为 null 时向后兼容，不阻断构建）。Player Portal 布局与前两者差异大，单独实现。

### 阶段三：GM Workbench API（步骤 15-22）

```
              ┌──→ [P3a]步骤15 + 步骤17 ──┐
              │    (玩家列表)  (流水报表)   │
步骤2(契约) ──┤                            ├──→ 步骤20(前端client) ──→ 步骤21(前端页面)
              ├──→ [P3b]步骤18 + 步骤19 ──┤
              │    (时长统计)  (服主实例)   │
              │                            │
              └──→ 步骤16(玩家操作) ────────┘
                   步骤22(路由门控) ──────────────→ (与15-19并行)
```

- **[P3a] 步骤15 + 步骤17**（玩家列表 + 流水报表）：独立聚合查询，无共享状态。失败回退：回退到阶段一完成检查点。
- **[P3b] 步骤18 + 步骤19**（时长统计 + 服主实例列表）：独立查询。失败回退：同上。
- 步骤16 依赖步骤15（玩家操作需先有玩家列表）。
- 阶段二与阶段三可跨阶段并行（实例详情页拆分 与 GM Workbench API 无依赖），全局并行 ≤3。

### 阶段四：Player Portal 店铺化（步骤 23-26）
