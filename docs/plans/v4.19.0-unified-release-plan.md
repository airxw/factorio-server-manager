## 四、M2：R3 审查遗留项修复

> 来源：[.trae/documents/20260725_v4.17.0_GN-004_R3_鉴权链路审查.md](file:///home/airxw/Documents/gsp/gameserver-panel/.trae/documents/20260725_v4.17.0_GN-004_R3_鉴权链路审查.md#L32-L43)

### 4.1 R3-3：`revokeAllUserTokens` 事务保护

- **文件**：[panel/backend/src/core/auth/tokenBlacklist.ts#L113-L136](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/core/auth/tokenBlacklist.ts#L113-L136)
- **问题**：SELECT `token_version` + 内存黑名单 + UPDATE `token_version+1` 三步操作未包在 knex transaction 内。DB 异常 + 旧用户（`token_version=0`）场景下黑名单失效
- **修复**：将 SELECT + UPDATE 包进 `db.transaction(async (trx) => { ... })`
- **注意事项**：内存黑名单操作（`this.revokeTokenVersion`）不应在事务内（内存操作无法回滚），结构应改为：

```ts
async revokeAllUserTokens(db: Knex, userId: string): Promise<number> {
  return db.transaction(async (trx) => {
    const user = await trx<{ id: string; token_version: number }>('users')
      .select('token_version').where({ id: userId }).first();
    if (!user) return 0;

    const currentVersion = user.token_version ?? 0;
    await trx('users').where({ id: userId }).increment('token_version', 1);
    return currentVersion; // 返回旧 version，由调用方决定是否入黑名单
  }).then(currentVersion => {
    if (currentVersion > 0 || /* 首次撤销 */ true) {
      return this.revokeTokenVersion(userId, currentVersion) ? 1 : 0;
    }
    return 0;
  });
}
```

### 4.2 R3-4：`selectActiveRole` 角色权限降级时撤销旧 token

- **文件**：[panel/backend/src/services/userService.ts#L780-L817](file:///home/airxw/Documents/gsp/gameserver-panel/panel/backend/src/services/userService.ts#L780-L817)
- **问题**：角色切换不撤销旧 token。用户先用 `instance_admin` 操作，切换回 `user` 后旧 JWT 仍在有效期内可继续 `instance_admin` 操作，审计归属混淆
- **修复策略**：角色权限降级（高→低）时强制撤销旧 token；同级或升级不撤销
- **实现**：

```ts
// 在 selectActiveRole 中，UPDATE 后、签发新 token 前：
const rolePriority: Record<UserRole, number> = {
  server_admin: 3,
  instance_admin: 2,
  user: 1,
};
const oldPriority = rolePriority[normalizeRole(row.active_role ?? row.role)] ?? 0;
const newPriority = rolePriority[targetRole] ?? 0;

if (newPriority < oldPriority) {
  // 权限降级：撤销旧 token
  const blacklist = getTokenBlacklistService();
  await blacklist.revokeAllUserTokens(this.db, userId);
}
```

### 4.3 R3-11 问题 1：`updateUserRoles` 契约/实现不一致

- **来源**：[R3 审查记录 SB-R3-M1](file:///home/airxw/Documents/gsp/gameserver-panel/.trae/documents/20260725_v4.17.0_GN-004_R3_鉴权链路审查.md#L25-L30)
- **问题**：契约声明 `activeRole ∉ roles` 时抛错，当前实现却会静默降级到 `roles[0]`，调用方行为预期与真实运行结果不一致。
- **修复**：在 `updateUserRoles` 中显式校验 `activeRole ∈ normalizedRoles`；不满足时抛 `InvalidCredentialError`，与 `selectActiveRole` 语义对齐。

### 4.4 R3-11 问题 2：`updateUserRoles` 撤销失败不回滚

- **来源**：[R3 审查记录 SB-R3-H1](file:///home/airxw/Documents/gsp/gameserver-panel/.trae/documents/20260725_v4.17.0_GN-004_R3_鉴权链路审查.md#L18-L24)
- **问题**：角色降级后若 `revokeAllUserTokens` 失败，当前逻辑可能静默继续，导致旧 JWT 仍保留高权限窗口。
- **修复**：`updateUserRoles` 中对撤销结果做强校验；若应撤销但未撤销成功，则回滚事务或打出 CRITICAL 级告警并显式阻断流程。

### 7.2 阶段二：创建基线脚本

**文件**：`panel/backend/src/db/migrations/20260808000000_baseline_v4_post_demo.ts`

- **数据来源**：基于当前开发库（已运行全部 v4.17.0 迁移）的 SQLite 终态 Schema 提取
- **内容**：`.up()` 方法中包含所有表的 `createTableIfNotExists` 语句（含全部列、索引、外键约束）
- **特点**：
  - **只含 `createTable`**：不含 `ALTER TABLE`、中间态数据迁移等历史包袱
  - **不含 `role` 列**：`users` 表只有 `roles`(JSON) + `active_role`，不创建旧 `role` 列——M3 的 DROP COLUMN 被此基线脚本吸收
  - **不含测试数据**：`.up()` 仅插入系统运行必需的字典数据（角色权限模板 `role_permission_templates`、权限点 `permission_points` 等），**绝对不插入**任何测试账号或演示实例数据
  - **使用 `createTableIfNotExists`**：确保对已存在表的存量部署无副作用
- **`.down()` 方法**：必须抛出异常 `throw new Error('基线迁移不可回滚 (Baseline migration cannot be rolled back)');`，严禁使用 `DROP TABLE` 以防误触清空整个数据库。

### 7.3 阶段三：数据清洗

通过独立脚本 `scripts/db-clean-demo.ts`（`npm run db:clean-demo`）执行：

1. **清理 Demo 账号**：

### 7.4 阶段四：存量部署平滑过渡

对于已运行的存量部署（v4.17.0 已部署），按以下步骤无感升级：

```
1. 备份 panel.db
2. 清空 knex_migrations 表：DELETE FROM knex_migrations;
3. 注入基线记录：
   INSERT INTO knex_migrations (name, batch, migration_time)
   VALUES ('20260808000000_baseline_v4_post_demo.ts', 1, datetime('now'));
4. 运行 npm run db:clean-demo（数据清洗）
```

**原理**：Knex 启动时检查 `knex_migrations` 表，发现基线脚本已在执行记录中 → 跳过建表 → 只执行 `20260808000001_system_mode_and_preflight.ts` 等后续增量。

**deploy.sh 适配（校准后）**：在 `run_migrations` 步骤之前增加“健康存量库识别”闸门，禁止只凭 `knex_migrations` 表存在与否就直接注入 baseline：
```bash
# 检测是否为基线重置版本（v4.19.0+）
if [ ! -f "$INSTALL_DIR/panel/backend/data/.baseline_v4_applied" ]; then
  HAS_TABLE=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM sqlite_master WHERE type='table' AND name='knex_migrations';")
  HAS_USERS=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM sqlite_master WHERE type='table' AND name='users';")
  HAS_SYSTEM_CONFIG=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM sqlite_master WHERE type='table' AND name='system_config';")
  HAS_BINDINGS=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM sqlite_master WHERE type='table' AND name='bindings';")
  HAS_V417=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM knex_migrations WHERE name='20260807000001_unify_bindings_and_multi_role.ts';" 2>/dev/null || echo 0)
  HAS_V418_INIT=$(sqlite3 "$DB_PATH" "SELECT count(*) FROM knex_migrations WHERE name='20260808000001_system_mode_and_preflight.ts';" 2>/dev/null || echo 0)

  if [ "$HAS_TABLE" -eq "1" ] && [ "$HAS_USERS" -eq "1" ] && [ "$HAS_SYSTEM_CONFIG" -eq "1" ] && [ "$HAS_BINDINGS" -eq "1" ] && { [ "$HAS_V417" -eq "1" ] || [ "$HAS_V418_INIT" -eq "1" ]; }; then
    # 仅对“核心表齐全”的健康存量库注入 baseline；
    # 若库处于半升级/漂移状态（核心表缺失、关键迁移不存在、人工修补痕迹明显），必须阻断并人工介入。
    echo "[deploy] 基线重置：清空 knex_migrations 并注入基线记录..."
    sqlite3 "$DB_PATH" "DELETE FROM knex_migrations;"
    sqlite3 "$DB_PATH" "INSERT INTO knex_migrations (name, batch, migration_time) VALUES ('20260808000000_baseline_v4_post_demo.ts', 1, datetime('now'));"
  elif [ "$HAS_TABLE" -eq "0" ]; then
    echo "[deploy] 全新安装：跳过基线记录注入..."
  else
    echo "[deploy] 检测到异常存量库，拒绝自动注入 baseline，请先人工核对 schema/迁移状态。"
    exit 1
  fi
  touch "$INSTALL_DIR/panel/backend/data/.baseline_v4_applied"
fi
```

### 7.5 对 P4 PostgreSQL 迁移的铺路效应

- **翻译工作量**：从翻译 50+ 个含 SQLite 特有语法的增量脚本 → 翻译 1 个基线脚本 + 若干增量
- **语法转换**：基线脚本中只需改造 `increments` → `SERIAL`、`datetime` → `TIMESTAMP` 等关键差异
- **测试成本**：从验证 50+ 个迁移的幂等性与顺序 → 验证 1 个基线脚本的结果正确性

### 7.6 执行注意事项

- **归档 ≠ 删除**：历史 migration 文件移到 `docs/archive/` 永久保留，可随时查阅
- **v4.17.0 必须先部署**：`20260807000001` 必须在归档前已在生产执行
- **幂等性**：基线脚本使用 `createTableIfNotExists`，重复执行无副作用
- **`.baseline_v4_applied` 标记文件**：防止每次部署都重新注入 knex_migrations 记录
- **验证分层**：M5 必须分别验证“全新库 / 健康存量库 / 异常库阻断”三条路径，缺一不可

## 十五、风险与建议

### 10.1 风险

1. **M5 基线重置破坏性**：归档 50+ migration 后若基线脚本遗漏任何表/列/索引，全新安装会缺少结构。**必须**用"删除 panel.db → 运行迁移 → 逐表对比 Schema"方式验证完整性。

2. **M5 knex_migrations 表操作不可逆**：存量部署 `DELETE FROM knex_migrations` + `INSERT` 基线记录后无法回退到旧 migration 体系。**必须**先在备份数据库上验证。

3. **v4.17.0 未部署，v4.18.0 契约已入 public/**：如果 v4.17.0 部署时携带了 v4.18.0/v4.19.0 的契约类型（`InitPreflightResponse` 等），前端引用但后端未实现 → 运行时 404。可接受风险：前端代码不引用即可。

4. **M3 `users.role` 代码引用残留**：若任何代码路径仍有 `role` 回退逻辑（如 `row.role ?? row.active_role`），虽然 M5 基线新安装不创建此列，但存量部署的列仍存在 → 可能静默读到旧值。**必须**先完成 M2 鉴权链路加固 + Grep 全量排查。

5. **M1 `detectInitStatus` 扩展后误判**：已初始化部署升级时 `system.mode` / `system.preflight_passed` 缺失会导致 `needs_init=true`。**已在 migration 中通过"检测已有 admin 状态自动 seed 配置项"缓解**。

6. **public/ 删除操作需授权**：M3 涉及删除 `player-bindings-schema.json` 和修改 `user-schema.json`，需经 `ec7_action_gate` + 人类显式授权。

7. **数据清洗不可逆**：`db:clean-demo` 截断流水表后数据无法恢复。执行前必须确认已备份。

### 10.2 建议

1. **M5 必须先于所有模块执行**，因为基线脚本决定了 migration 目录结构和其他模块的 migration 时间戳
2. M2 和 M4 可先行（改动小、独立），M1 和 M3 可与 M5 并行推进
3. M3 执行前先跑一次全量 Grep `\.role\b`（排除 `roles` / `active_role`），确认无遗漏
4. 基线脚本提取 Schema 时建议用 `sqlite3 panel.db .schema` 导出后人工复核
